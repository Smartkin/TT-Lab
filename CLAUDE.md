# CLAUDE.md

TT Lab is a modding toolkit/editor for **Crash Twinsanity** (PS2 and Xbox). It unpacks the game's disc files into an editable project of JSON assets, lets you edit them in an Avalonia UI with a 3D OpenGL viewport, and repacks them into game archives/ISO.

## Build & run

```bash
dotnet build "TT Lab.sln"
dotnet run --project "TT Lab/TT Lab.csproj"
```

- Targets .NET 8 (`global.json` rolls forward to newer SDKs).
- The build has around 3.4k pre-existing warnings, so only errors and new warnings in code you touched matter.
- Tests: `dotnet test "TT Lab.Tests/TT Lab.Tests.csproj"` (xUnit) and `python -m unittest discover -s tests` in `TT Lab/BlenderTools`. They never use game data. Build made-up data in the test instead (see `Support/TestAnimations.cs`).
  - `Support/TestProject` opens an empty project with the base packages in a temporary directory. `BuildProjectTree` creates the package folders the way opening a project does. Tests using it must be in `[Collection(ProjectCollection.Name)]`, because the opened project is global (service locator plus CWD).
  - `TT Lab` exposes its internals to the test project.
  - UI tests use `[AvaloniaFact]` and run in the headless `Support/TestApplication`, which renders with Skia (so bitmaps encode, textures need that) and has the app's `ViewLocator`, Dock theme and view registrations, so real editor panels and tabs can be shown and driven with key and mouse input. Tests creating ReactiveUI objects have to be `[AvaloniaFact]` too, so they run after the application set ReactiveUI's schedulers. The main thread scheduler is `Support/TestMainThreadScheduler`, not `AvaloniaScheduler`: the session resets `Dispatcher.UIThread` between tests, a thread pool thread asking then gets a dispatcher claiming every thread, so a code editor's live check finishing after its test ran on the pool thread, made Avalonia's `MediaContext` on that dispatcher and no later test's window laid out after `Show()` (the Windows CI runner's failures, `taskset -c 0` reproduces them). Wait for views and closed tabs by polling, not with fixed delays. Clicks and `InputHitTest` go by what the compositor got last, and a commit waits until the render timer (a dispatcher timer in the headless session) has taken the one before it: a test showing windows right after another test hit nothing in them, so tests that click run `Dispatcher.UIThread.RunJobs()`, `AvaloniaHeadlessPlatform.ForceRenderTimerTick()` and `RunJobs()` again first (`PrefabDragAndSearchTests.Render`).
  - Rendering code that needs a GL context isn't tested, but its math is (`Rendering/`: camera projection, gizmo picking and dragging, splines).
  - Add-on tests import its modules without Blender through the fakes in `tests/fakes.py`.
- CI (`.github/workflows/build.yml`) only runs when started by hand (`workflow_dispatch`, the Actions budget is small). It runs both test suites on Windows and Linux, then publishes a framework-dependent build for `win-x64`/`linux-x64` as an artifact. Publishing for a runtime makes a single file (`PublishSingleFile` in `TT Lab.csproj`, symbols embedded in Release, no documentation files): only the native libraries stay next to the executable (bundled ones get extracted elsewhere, where Veldrid's SDL loader doesn't look), with `BlenderTools/dist` and `tools/`. Assemblies have no `Location` there (`EnableSingleFileAnalyzer` warns about it). Nothing is read from next to the executable but `settings.json`, `layout.json`, `tools/` and the add-on: `Media` (shaders, icons, pictures, not its unused fonts) and `Images/SadTransparent.gif` are embedded, read by their paths through `Util/ManifestResourceLoader` (which resolves shaders' relative includes, `ShaderSourceTests`), and TwinTech embeds its `.lab` definitions and three JSON files (`Libraries/EmbeddedFiles`, by file name). `_WINDOWS`/`_LINUX` come from the OS doing the build, so each platform has to be built on its own OS. `scripts/package_addon.py` zips the Blender add-on without the uv environment. `scripts/fetch_tools.py --os Windows|Linux --out publish/tools` downloads the twinstudio tools (twinmusic, twinpss: https://github.com/Smartkin/twinstudio/releases, zips named `<tool>-windows-latest.zip`/`<tool>-ubuntu-latest.zip`, each a bare executable with a `resources/` folder) into `tools/<tool>/` next to the published build, which is where `Tools/ExternalTools` looks for them (`AppContext.BaseDirectory/tools`; a local `TT Lab/tools/twinmusic` and `twinpss` are git-ignored and copied to the output, only those: the repository ignores case, and ignoring `TT Lab/tools/` hid the sources in `TT Lab/Tools/`, which were never committed). Tools > Install the tools does the same from inside TT Lab (`ExternalTools.InstallAsync`: the latest release's zip for this system, unpacked into the tool's folder in place of what's there, the executable bit set). The tools take no file on their command line, so opening a disc file starts the tool with the path as an argument anyway and on the clipboard.
- Platform-specific code is gated by `_WINDOWS` / `_LINUX` defines set in `TT Lab.csproj`. Native libraries (`PS2ImageMaker`) in `TT Lab/Libraries/Native/{Windows,Linux}` are copied into `runtimes/*/native` by the `CopyNativeLibs` target (an absolute `-o` folder included, they used to go into a folder of that name inside the project). When publishing for a runtime, the `PublishNativeLibs` target copies them next to the executable instead.
- The app requires OpenGL 4.6 (see `Program.cs`).

## TwinTech (game formats)

- Names and descriptions follow what the decompilation (`twinsanity-reversed`, `include/game/*.h`) found a value does; values it shows are never read keep `Unused`/`Leftover` names.
- `TwinsanityInterchange/Interfaces`: every game item is an `ITwinItem : ITwinSerializable`, implementing `Read(BinaryReader, int length)`, `Write(BinaryWriter)`, `GetLength()` and `Compile()`. `GetLength()` must exactly match what `Write` emits. Containers implement `ITwinSection`.
- `Interfaces/Items/**` defines platform-agnostic `ITwin*` interfaces (for example `ITwinTrigger`). `Implementations/PS2/**` (`PS2Any*`) and `Implementations/Xbox/**` implement them. `Implementations/Base/BaseTwinItem` and `BaseTwinSection` hold the shared logic. A section maps child item IDs to concrete types via `idToClassDictionary`, and anything unmapped falls back to a raw `BaseTwinItem`.
- `Common/` holds shared structs (`TwinTrigger`, `Vector3/4`, and so on) that implement `ITwinSerializable`.
- `Enumerations/Constants.cs` holds section and item IDs (`LEVEL_CODE_SECTION`, `LAYOUT_TRIGGERS_SECTION`, ...). `Enums.cs` holds game enums.
- `PS2Hardware/` contains the VIF/GIF/DMA packet code for PS2 model data. `TwinVIFCompiler` and `TwinSkinPacketDecoder` pack and read models, skins and blend skins exactly the way the game does, which `VifCodecTests` checks. A packet goes out with one DMA tag whose size field holds 65535 quad words: `TwinVifPacket.Writer.Finish` refuses more (the overflow once sent a fifth of a 35k vertex skin and the game hung waiting for the rest), so `PS2ItemFactory` spreads a part's batches over several sub skins or sub models of the same material when they'd go past `TwinVIFCompiler.MaxPacketBytes` (`SkinBatchBytes`/`RigidBatchBytes` are what the compiler writes per batch). The game draws every model of a blend skin's sub blend with the first model's shape factors (`FUN_001c1ac0`, the scale of the shapes' byte offsets), which every retail sub blend's models share, so `PS2ItemFactory.GetFittingBlendShape` fits one scale over all of a part's batches. `Libraries/` contains ADPCM, swizzling, hashing, quantization and the Xbox's DXT5 codec (`Dxt5`). A picture of more than 256 colors made into a palette texture (`PS2AnyTexture.FromBitmap`) gets its palette from `ImageQuantizer`: a median cut of every mip level's colors (the GS draws every level with the one palette) that splits the group with the most error where it drops most, refined by k-means, colors told apart with the eye's weights (green most, blue least, alpha like green); the pixels get Floyd-Steinberg diffusion of their color at 0.8 (never of alpha, cut-outs keep their edges, see-through pixels pass none on) and its mips average the picture (taking every other index aliased). Pictures of 256 colors or fewer keep their exact palette and their mips every other index, so the game's textures still come back byte-identical (`TextureTests`).
- **Xbox** (`Implementations/Xbox/**`): every file of the Xbox disc TwinTech knows reads and writes back byte-identical (`XboxFormatTests` covers each quirk with made-up data).
  - Most Xbox items subclass the PS2 ones. The Xbox's behaviour classes only swap the command table (`XboxBehaviourGraph.GetAgentLabDefs`, some commands take more arguments), the PS2 classes have the virtual hooks (`Defs`, `GetSize`, `Create*`) for it.
  - Models, skins and blend skins are plain vertexes drawn as triangle strips, one strip per group (`XboxSubModel`, `XboxSkinnedGeometry`). Normals are packed 11:11:10 signed fractions. A skinned vertex refers to up to 3 joints of its strip's palette by vertex shader register (16 + 4 per palette slot). Unused slots hold leftovers of the tools' memory (registers past the palette, weights near 0) which are kept for writing but read as joint 0 with no weight, like the PS2 version's. `ITwinStripGroups` marks Xbox geometry.
  - The Xbox's tools joined strips without keeping their triangles facing one way, the game draws them without culling.
  - Textures are DXT5 with only the largest mip (level textures) or plain BGRA (menus, fonts). The first header word is the length of the PS2 texture they were made from, and textures embedded in PTC files work out their length from it.
  - Fonts store every character's box as fractions of its page. Sounds are 16 bit PCM. Unknown header bits (dynamic scenery, trigger behaviours, the order of a scenery's lights) are kept as read, several of them only the Xbox version sets.
- PS2 textures (`PS2AnyTexture.FromBitmap`) get the game's layouts. The header has the texture's size twice, in blocks of 64 of the 32 bit pixels it uploads, which is what the game reserves GS memory by; 32 bit textures upload their whole image and textures without mips have their palette where the game's have it (`UnmippedClutPointers`). A wrong size made textures overwrite each other or go missing in game. The rest of the header is what the tools had in memory (`TwinTextureLeftovers`: the signature's low half, a slot number unique in each chunk, reserved words and 32 bytes after the header), worked out from every texture of the game. It's written back as read (`ITwinTexture.Leftovers`, kept in `Texture.Leftovers`). The PSM files' icons have zeros where chunk textures have an address of the tools' memory, textures made in TT Lab get the chunks' values.
- Behaviour starters get their script ID and their first assigner the ID two past theirs in `Compile()`, like every starter of the game. With a starter the `[Priority]` attribute is the starter's, `[GraphPriority(n)]` holds the graph's own priority (0, 1 or 3).
- `Implementations/PS2/PS2SaveIcon` is the PS2 memory card icon the game's saves get (`Startup\Crash.ico`, Uka Uka's mask; the Xbox disc has none), in ps2iconsys' layout, which accounts for every byte of the game's: a header (shape count, texture type), triangles of 3 corners each with a position per shape and a normal (X, Y, Z in 4096ths with Y going down, and a word the tools wrote 0 into), a UV in 4096ths and an RGBA color, the animation (a header, then every shape's keys of a time and a weight) and a 128x128 texture of 16 bit texels (5 bits of red, green, blue from the lowest, the alpha bit), run length encoded when the texture type's bit 3 is set (a count below 0xFF00 repeats the next texel, a larger one is 65536 minus it texels as they are; the encoding read is written back while it still decodes to the texels). It reads and writes back byte for byte (`SaveIconFormatTests`).
- Animations (both versions) count channels in their flags: every joint its amount (9, or a facial joint's shapes) and how many are animated (`animated << 4 | static`), the header the amount per joint. `Write` works them out, so animations made in Blender get them right.
- `AgentLab/` is the compiler/decompiler for the behaviour scripting language (AI graphs, starters, command sequences). The pipeline is `AgentLabLexer` → `AgentLabParser` (AST in `AbstractSyntaxTree/`) → `AgentLabSymbolTableBuilder` → `Analyzers/` → `AgentLabCompilerNodeVisitor`, which emits `ITwinAgentLab` objects. Visitors register handlers with `Visitors.Add(typeof(Node), VisitX)`. Reference resolution is abstracted behind `Resolvers/Interfaces`, which TT Lab implements in `TT Lab/Assets/Code/Resolvers`.
  - `ActionDefinitions{Ps2,Xbox}.lab` are **generated** by `LabActionGenerator.py` (run it in `TwinTech/`, it writes both) from `AgentLabDefs{PS2,Xbox}.json`. Edit the JSON and regenerate instead of hand-editing them. A command's `Arguments` are its dword types (`single`, `int32`, `hex`, or the tagged `tfloat`/`tint`/`tangle`), `ArgumentNames` its parameter names, `ArgumentFields` (by argument index) the fields of the dwords the game packs (flags, bytes, halfwords: `Name`, `Bit`, `Width`, `Type` `bool`/`int`/`sint`, together covering all 32 bits) and `Aliases` the names the command went by before, which old scripts still compile under (`AUnknown_N`, and the earlier name of a renamed command). `ConditionDefinitions.lab` is hand-maintained, one line per condition index, with the old names as aliases. Every command and every condition of the PAL executable has a name now; the ones found by reverse engineering (`Ghidra Stuff/AgentLab_RE`, `data/decisions.json` holds each with its confidence and what the code does) are mostly educated guesses, the ones the user had are kept.
  - Packed parameters are declared as `name { int slotCount : 4, bool blendTimeGiven, sint slotA : 16, ... }` (fields from bit 0 up, widths adding up to 32) and written in scripts as `{slotCount = 1, blendTimeGiven = true}` (any order, the fields left out are 0, `{}` for none; a plain int or hex literal is still taken for the whole dword). The decompiler prints the fields that aren't 0 in declaration order, `unused*` ones in hex, so scripts stay byte exact. The symbol pass checks the names, types and the range of literal values, the compiler packs them (`PackFields`), `PackedArgument.Format` unpacks them and completion suggests the fields inside the braces (`AgentLabCompletionKind.Field`).
  - A state's child behaviour is a name (`state S(COM_X)`, `BehaviourReferenceNode`) or a string for what only the resolver understands (`IStateGraphResolver`: a URI in TT Lab, an index in the default one). The decompiler writes bare what lexes as an identifier and isn't a keyword or a token type's name (`AgentLabLexer.IsReservedKeyword`), the rest quoted. `AgentLabCompletion.GetBehaviourReference` finds the reference at an offset, name or string.
  - What the game does with the bytecode (verified in the PAL executable): a body passes when its condition's result is above the threshold (`if X(p) > t`, `<` inverts), and among the passing bodies the largest `(result - threshold) * weight` runs, `weight` being 1/threshold unless written. `window` (the condition's first float) is a time window in seconds only the event conditions read, never a check interval. `else` is the fallback body (condition 2) and `completion` the first body of a state with bit 10, run when its control packet or child behaviour finishes (condition 0, never evaluated). `restart = true;` (body bit 8) makes a jump to the same state re-enter it. `[Interrupting]` (state bit 11) keeps the state's conditions evaluated while its child behaviour runs. State bits 5-9 (small leftover numbers, dropped: old scripts' `[Unknown(n)]` is accepted and ignored) and 13, and assigner locality/status/preference, are never read. An assigner's `RefListIndex` is the instance's RefListIndex a `GLOBAL_AGENT` receiver is, not an object. Tagged arguments (`TaggedValue`) are a literal of the parameter's type or `Prop(n)`, an instance property index; `Raw(0x...)` keeps bits as they are and hex literals always do. Many commands take a "designator" byte: a starter receiver index below 0xDE, or 0xFB the focus object, 0xF8/0xF7 AgentRef1/2, 0xF2 the player, 0xF4 the originator, 0xF6/0xFC the focus position, 0xFD/0xFE the next/current key, 0xFF none. The old spellings (`NonBlocking`, `interval`, `unknown`, `>=`, `GlobalObjectId = "uri"`) still compile, projects store behaviours as script text. Floats print so they lex as floats and reproduce their bits (`-0.0`, `2.0`), and bits no literal reproduces (NaN, infinities, denormal leftovers, `int.MinValue`) print in hex or `Raw(0x...)`; control packet data is written in float slot order. Every script of the PAL archive round-trips byte-identically but for those bits (`Ghidra Stuff/AgentLab_RE/scripts/harness`, modes `roundtrip`, `context`, `sample` and `locate`).

## TT Lab (editor)

### Project lifecycle (`Project/Project.cs`, `ProjectManager.cs`)
- **Create**: copy the disc contents, then `CreateBasePackages()` (Base, Global PS2/Xbox, PS2/Xbox packages), then `UnpackAssetsPS2()` and `UnpackAssetsXbox()`. Both go through `UnpackAssets`, which parses the chunks and runs `AssetResolvers/*` over each of them through `ResolverManager.PerformResolve`. The resolvers turn `ITwinItem`s into `IAsset`s, OGIs, textures, sounds, skydomes, behaviour command sequences, instance templates and OGIs' animations named after twinsanity-editor's names of their IDs (TwinTech's `Enumerations/DefaultHashes`, the tables of its `DefaultHashes.cs` for those kinds as it has them, folders like `Crates/` included; `RetailNames` leaves the folders out of the asset's name, which is its file's, but where two names of a kind would be the same; models, skins and blend skins are parts of OGIs, and the textures whose IDs the game reuses are keyed by a hash the editor never computes), the rest and IDs without a name the way they were (objects, behaviours and collision surfaces keep the game's own names, which the editor's are copies of, but for 5 IDs the game reuses for other scripts). The PS2 version's files come from its `.BD/.BH` archive, the Xbox's are loose on the disc (`GetXboxDiscFiles` takes the Startup, Levels, Extras and Language folders, like the PS2 archive holds). Unpacking the Xbox disc enables its packages.
- **Open** (`Project.Deserialize`): every package folder's asset JSON files are read in parallel (`AssetDeserializerFactory.GetAssets`). A second file of an asset's URI (a file manager's copy) is left out with a warning, the first by path kept, and a file that doesn't read fails the opening with its path (`ProjectException`); a copy used to hang the opening for good, the lock every file waited for held by the one that threw. Failures are reported in Debug builds as well, they went nowhere and the opening looked stuck.
- **Both versions in one project**: their assets share IDs, so `AssetManager.GetUriByTwinId` only matches assets of the requester's package and the packages it depends on (then the ones depending on it), and code scanning every asset of a type for an import uses `GetRelatedAssetsOf<T>(package)`. `Project.GetPlatform(package)` tells which version a package is. The game also reuses texture IDs for other pictures in other chunks' sceneries (the hubs' 64x32 `671573F7` is a 128x64 texture of l03beach's scenery), so among the assets with the ID the lookup takes the requester's own folder (`AdditionalPath`: a scenery's material gets its scenery's texture, a PSM's its own) first, then the package's shared ones, and another chunk's folder last, in URI order; the order they were added in decided before, and the hub's `lambert46`/`lambert48`/`AC_AC_AC_lambert228` materials got the Totem's textures, which drew their model (the whack-a-worm HUD sign) from the wrong corner. Projects created before 2026-09-29 have those links baked in and have to be created again.
- **Build**: `PackChunk` and `PackAssets(platform)` (`PackAssetsPS2`, `PackAssetsXbox`) call `ResolveChunkResources(factory, section)` on each chunk's assets, using the platform's `ITwinItemFactory` to create game items. `XboxItemFactory` extends `PS2ItemFactory`, mapping its items and sections to the Xbox classes through `Create<T>`/`CreateSection<T>`, and has its own graphics, sounds, fonts and script descs. Assets the owner writes itself (`SkipExport`, a PSM's PTCs) aren't written on their own.
  - PS2: `.rm2`/`.sm2` files under `<project>/build/archives`, then `CreatePs2ArchivesAndIso` packs them into the disc folder's archive and produces the ISO.
  - Xbox: `.rmx`/`.smx` and global files under `<project>/build/xbox/files`, then `CreateXboxGame` copies the disc into `build/xbox/game` with the built files in place of theirs (the Xbox's file system ignores case, chunk paths are lowercase) and `XboxImageMaker` writes it as an XDVDFS image to `build/image`. Files already the same as their source aren't copied again.
- **Build profiles** (`Project/Build/BuildProfile.cs`, `BuildProfileLibrary`, one JSON each in `<project>/profiles`, hidden from the tree): the version to build and the chunks left out (`ExcludedChunks`, URIs, so new chunks get built). The Build menu's "Build..." opens `BuildDialogViewModel`/`Views/BuildDialogView` (profiles to pick, make and delete, a PS2/Xbox choice, every chunk of that version with a checkbox and a filter; `Preferences.LastBuildProfile` remembers the last one built with) and `ProjectManager.Build(profile)` runs `Project.Build` → `PackAssets(platform, profile)`. A chunk left out isn't written (`Project.LeftOutChunks`): its files stay while the build folder has them, the Xbox game takes the disc's file, and since the PS2 archive is made of `build/archives` alone, a left out chunk never built gets its files from the disc folder's `Crash.BH`/`BD` (`Project/Build/DiscArchive`, the last build's archive or the game's own, paths matched without case or separators) and is only written when that lacks it too, so a small profile on a fresh project builds its few chunks; every built chunk's links to it are dropped from the file without touching the asset (`ChunkLinksData.Export` reads `ITwinItemFactory.ExcludedChunks`, records what it linked in `LinkedChunks`), the cache keeping a `link:<uri>` dependency per linked chunk (`kept`/`dropped` against `BuildCache.ExcludedChunks`) so a chunk is rebuilt when a profile changes which of its links are dropped. Every build logs its total time. **Build failures** are `BuildException`s naming what failed and where (`WriteChunk` wraps each chunk resource as "<asset> of <chunk>", `ResolveGlobalAssets` each global file), a data file that can't be read names itself (`AbstractAssetData.Load`), and `ProjectManager.RunBuild` (every build menu entry goes through it) logs them as errors, a line each, in every configuration, then hands the project back (`WorkableProject`). It only caught them in Release builds before: in Debug a chunk's exception went nowhere, the build looked stuck after the chunks without the failing asset and the project stayed locked. The cache is saved and the empty chunk folders removed even when a chunk fails. A stored key renamed without converting the project does exactly that to every asset of the type (`[JsonProperty(Required = Required.Always)]`).
- **Build cache** (`Project/BuildCache.cs`, manifest in `<project>/build/cache/manifest.ttcache`): every chunk and global file records the assets it read, which `AssetManager.RecordAccessedAssets` collects from `GetAsset`/`GetAllAssetsOf` calls on the current async flow, and is skipped when none of their fingerprints (metadata JSON + data file hash) changed. Assets loaded when the build starts count as changed, and so does what was built from them while they stay loaded (they were recorded as volatile, which matched volatile, and a chunk built while its scene was open never got built again until the scene closed). Rebuilding TT Lab or changing its definition files invalidates the whole cache (the fingerprint is TT Lab's and TwinTech's module version IDs, which deterministic builds derive from their contents, embedded files included). Code that makes build output depend on anything other than assets fetched through `AssetManager` must add it to the fingerprints, or builds go stale.
- **Playing in PCSX2** (`Tools/Pcsx2`, the PS2 version's PAL 1.01, NTSC 1.00 and NTSC 2.00 releases: `GameRelease.Detect` tells them apart by SYSTEM.CNF's boot file and version and checks the executable's CRC, and holds each one's addresses, found by matching the PAL release's functions in the NTSC ones; the PAL addresses are given here): the chunk viewport's toolbar has Play, Reload and Stop (`ViewportViewModel.GameLaunch.cs`, Play disabled with the reason as its tooltip for chunks `Pcsx2Service.WhyNotPlayable` turns down, Reload and Stop only while the game runs, following `Pcsx2Service.Playing`), what PCSX2 and disc image it uses and whether saving reloads are in Preferences > Direct Game Launch. Play builds the chunk and the chunks it links (`Project.PackChunk`), fills `<project>/build/pcsx2` (`Pcsx2DevFolder`: every file of the disc's archive on its own in upper case, the way the game asks for them, the build's files over them, and the `Crash6` sound banks, which the game streams through the same loader and had no music without; only what changed gets written, moved into place) and boots it in PCSX2 in a window of its own (`Pcsx2Install`: the Flatpak, `pcsx2-qt` on the path, its install in Program Files on Windows, or the executable picked; its settings in the Flatpak's config, `~/.config/PCSX2`, `Documents\PCSX2` on Windows or next to a portable one; the disc image picked or the project's built ISO: the game streams its videos from it with `sceCdSearchFile`, past the patched loader, so an image of another release plays as well). The executable is patched (`GameExecutable`, verified in the PAL executable, `Ghidra Stuff/Engine_RE`): the loose loader's `cdrom0:\` (0x3069c0) becomes `host0:\`, so PCSX2's host file system (rooted at the executable's folder) serves the folder; the built-in launch arguments (0x2ec400, `Main` always parses them and never what the emulator passes) lose `batch=Crash6\Crash`, so no archive is used; the start chunk comes from unused bytes after .vutext (0x2e6ed0) that the code filling `G_StartChunk_Path` (0x178930) is pointed at; a word appended keeps the PS2 CRC (the XOR of the file's words) at 77AB0001 (NTSC 1.00 77AB0002, 2.00 77AB0003), so one game settings file per release (`gamesettings/77AB0001.ini`, PCSX2 names it by the CRC alone for an overridden executable; only TT Lab's keys set: `HostFs`, `EnablePINE`, `PINESlot` 28111, `SaveStateOnShutdown` off and `[UI] ConfirmShutdown` off, `Pcsx2Install.WithKeys`: the game settings layer over PCSX2.ini, UI keys included, so closing the game's window ends the run without PCSX2 asking first while other games still ask) serves every chunk. TT Lab drives the game through PINE (`PineClient`, refused until the virtual machine runs; a Unix socket in the runtime folder on Linux, the Flatpak's reached through `/proc/<pid>/root`, a TCP port on Windows): the game controller's states (`RunningGame`: `G_GameController`+8 holds the next state in bits 50-55, applied the next frame; the NTSC releases' controller lacks the PAL one's first 8 bytes, the states are at +0 and the start's timer at +0xC, the state numbers are the same) go the way the main menu's new game does (`Pcsx2Session.NextOnTheWayToPlaying`): from the logos (4) to loading the start chunk (6, `FUN_00173d10` drops every chunk and loads `G_StartChunk_Path` with its links), from the title (7, "press start" over the start chunk) to a new game (10: the game's data made again, the player in character slot 0), from the intro movie's state (14, the movie only starts 0.6 s in) to starting to play (11, the player gets control) and on to playing (12), where the start's timer (+0x14) is zeroed so neither the level's title card nor the autosave notice comes up (making autosave look on could save into the user's slots). The title's character slot 4 plays its cinematic: going from the title straight to playing kept it running, and the beach got stuck after its "THREE YEARS AGO...". About 25 s from booting to playing. Once the game plays the session asks PINE for the status every second (`Pcsx2Session.WatchAsync`): PCSX2's shutdown waits for its PINE server, which waits for its client's next request, and with TT Lab's connection idle closing the game's window left PCSX2 running without a window while TT Lab still played it; a shut down game or a connection PCSX2 closed or refuses ends the session like PCSX2 closing (`HasStopped`), and a PCSX2 still running 5 s later is closed. Saving anything while it plays (`DocumentViewModel.Saved`, when reloading after saving is on) or Reload builds the start chunk, its links and the chunks the game has loaded again (`G_ChunkManager`: the count in the low half of its first word, the chunk metas after it; dropping every chunk only zeroes the count, the old pointers stay), copies what changed (Windows doesn't replace a file the game has open, the move is tried again for 5 s) and, when anything did, asks for state 6 and then the same new game: a full reload of the chunks' files (about 12 s), the player back at the start chunk's start. Startup files (`Default.rm2`, fonts) are only read at boot, playing again picks them up. - Creating, opening and saving the project still rely on `Directory.SetCurrentDirectory`. Asset data load/save, `SerializableAsset.Delete`, package/chunk serialization (`SerializationFlags.SetDirectoryToAssets` does nothing anymore), new folders (`AssetDataFactory.CreateFolderData`) and the whole build (global files through `IAsset.ExportToFile(factory, directory)`, `ResolveGlobalAssets` handing each folder's absolute directory down) resolve absolute paths and leave the CWD alone, so they work from any thread: saving a chunk set the CWD to the project's assets, and a build running meanwhile failed writing Extras or wrote its global files there (`BuildDirectoryTests`). A lot of older code is still relative to the CWD. Never change it from code a build or project creation runs in parallel.
- **Parallel builds**: `WriteChunks` builds the level chunks in parallel. Each chunk gets a factory of its own (`ITwinItemFactory.ForChunk`), whose `ChunkResolution` resolves every asset into a section once (an instance resolves its object, the next instance of it doesn't), guards against assets referring back to themselves and hands objects the references of the objects and graphs under them. Compiled behaviours are shared by the chunks of a build (`CompiledBehaviours`). Each chunk also gets an `AssetDataScope`: the data it loads and the internal assets that data makes stay in the scope (removing one, like a scenery's data deleting its collision and dynamic scenery when it's released, takes it out of the scope), which releases them once the chunk is written, so chunks never touch each other's data or the data editors have open (a build only reads that). `MemoryGate` starts more chunks while TT Lab is within `Preferences.BuildMemoryBudget` (2048 MB) and collects when it gets close. Asset storage takes a lock on every access.
- **Creation** stays within the same budget through a `MemoryGate`. The PS2 archive is read a file at a time, chunks are read for their behaviour starters and dropped, then read again a few ahead of resolving them. `CreationWriter` imports and writes every asset in parallel as soon as the disc's chunks are resolved and lets go of its data, each version of the game before the next disc is read, and the disc's variants are merged into their assets as chunks' overrides (see Chunk overrides). Internal assets get imported when a write first looks them up (`AssetManager.HookLookups`) and let go of once no write uses them, kept in their data file first because another write can find the same one by its ID (two OGIs, one rigid model); those files go with the internal assets. So `Import` must only read other assets' metadata and never touch the CWD, and writing an asset may only read the data of the internal assets it's made of.

### Assets (`Assets/`, `AssetData/`)
- `IAsset` / `SerializableAsset` is an asset's metadata (ID, URI, package, references, variation). It is serialized to `<Name>.json` with Newtonsoft (`MemberSerialization.OptIn`, `[JsonProperty(Required = ...)]`).
- `AbstractAssetData` subclasses hold the payload, stored in `<Name>.data` (JSON). Data is lazy: `asset.GetData<T>()` loads it, and `Serialize(SaveData)` saves and then **disposes** it unless `PreserveData` is passed.
- A new asset type usually needs:
  - an `Assets/<Category>/X.cs` class with `Section`, `IconPath` and `GetData()`, which recreates the data when `!IsLoaded || Disposed`;
  - an `AssetData/<Category>/XData.cs` class with a `[JsonConstructor] internal XData() : base(null)` ctor, an `Import(...)` that reads from `GetTwinItem<ITwinX>()`, and an `Export(ITwinItemFactory)`;
  - a resolver in `AssetResolvers/` and a factory method in `ITwinItemFactory`/`PS2ItemFactory`/`XboxItemFactory`.
- **Data lifetime**:
  - Open editors own the data they use: a document's property graph loads every linked asset's data, and `Save()` keeps it loaded (`PreserveData`).
  - When an editor closes, `EditorsViewModel.ReleaseUnusedAssetData` calls `UnloadData()` on every asset no open editor references (`TabbedEditorViewModel.GetReferencedAssets`). `UnloadData()` detaches without disposing, because renderers may still hold the data.
  - Closing a tab with nothing to save leaves its asset's data alone, and discarding changes disposes it only when no other open editor uses the asset, else just detaches it (`TabbedEditorViewModel.DiscardData`; a discarded chunk's resources always go back): a chunk's view of a behaviour, model, picture or sound shares the asset's data object, and the behaviour's own tab closing disposed it, which emptied the script the chunk's inspector showed (`BehaviourGraphData.Dispose` clears `Graph`).
  - Internal assets (`IsInternal`) are never serialized. Loading an owner's data recreates them, so any code creating one must set `InternalOwner` to the asset whose data creates it; `AssetManager.RemoveOrphanedInternalAssets` drops them once their owner isn't loaded.
  - Project creation removes all internal assets once a disc's assets are written.
  - Assets never saved (`IsUnsaved`: a layout's instances until their chunk gets saved) keep their data, there's no file to load it back from. When a scene's tab closes, the instances made for its chunk that it no longer lists (their placing undone, the chunk closed without saving) leave the project (`AssetDeletion.ForgetUnsaved`): they stayed in the project tree and couldn't be opened. A tab whose data fails to load logs why and closes, it stayed loading for good.
- **Deletion** (`Assets/AssetDeletion.cs`): every asset referencing a deleted one is fixed by `DeletedReferenceFixer`, which walks the data by reflection and follows each `LabURI` member's `[OnReferenceDeleted]` policy: replace with a placeholder from `PlaceholderAssets` (the default), clear, or remove from the list. Annotate new `LabURI` members whose placeholder wouldn't make sense. The placeholder texture is boat guy (`MiscUtils.BoatGuyPath`, `Media/boat_guy.png`, 128x128), the picture the viewport draws for parts without a material, in the layout textures TT Lab makes get (`Texture.UseGameLayout`: a palette and mips for the sizes the game's tools laid out, every color otherwise).
- **Textures** are PNGs that go through Skia unpremultiplied (`TextureData.FromPng`, `GetPngBytes`); Avalonia's bitmaps premultiply what they load and save and lose the color of transparent pixels, so `TextureData` keeps the exact pixels and only shows them through its `Bitmap`. `Texture.ReservesMemory` keeps the header's second size at 0 for Crash's textures every chunk has.
- Shader vectors (`LeftoverVector`, `ShaderColor`, `UvScrollSpeed`) often hold leftover bytes that are NaN as floats (every UI shader has them), and Newtonsoft would write them all as the same NaN, so `LabShader` stores their bits (`BitsVector4Converter`). What the PAL executable does with a shader's other values (`Ghidra Stuff/Engine_RE`): `LeftoverVector` is bits of the tools' strings, only compared when equal shaders get merged; only `ShaderColor.X`'s integer part reaches the VU1 program (0, the UI's materials 1); `UnusedValue` (the byte after the depth test, 4 or the UI's 6) and `UnusedFlag` are never read; `AlphaCorrectionValue` is the settings' "no FBA" bit (56, `SettingNoFba`, the GS gets FBA = bit ^ 1): on, the pixels keep their alpha, off sets its top bit, which keeps the characters' shadows off them (see Character shadows); `AntiAliasing` is the GS's PRMODE AA1; `AnimationDrivesColor` makes the animation's color track set `ShaderColor` every frame. A material's `DmaChainIndex` is which of the game's 28 render buckets its draws go into, drawn in bucket order: 0 skydomes, 2 opaque scenery and objects, 3 opaque global objects, 6-19 alpha-blended, 20 decals and layered materials, 22 particles, 24 the UI, 26 fonts. A bucket has no GS state of its own: every material sends its shaders' PRMODE, FBA, ZBUF (with the depth mask), ALPHA, TEST (the depth test always on), TEX1 and CLAMP with every draw (`SetShaderSettings`). What's fixed is what the game's code puts in (`RenderBuckets`): the frame's setup and clear at the head of 0 (`FUN_0019f958`), the debug drawing in 4 (off in retail), the characters' shadows in 21 (`FUN_001f1a10`, see Character shadows), the particle pages' shaders in 22 (the particle code makes them, whatever the page material says), the Distortion particles in 23 and the movies in 27. The material's first 8 bytes (`ActivatedShaders`, a bit per shader type) are the key of the VU1 programs its bucket has loaded (`RenderMaterial`): the same key as the last material drawn in the bucket skips loading the shaders' programs and 1 never loads them, so `MaterialData.Export` writes `DeriveActivatedShaders` (the bits of the shaders' types, what all 10487 Xbox and every PS2 material have). The inspector shows the types the material's shaders have, following them (`ActivatedShadersFieldViewModel`), not the stored bits: only building writes those, and `AppliedShaders.UnlitBillboard` is `StandardUnlit`'s bit, a flags editor ticked both. TwinTech reads every shader type the game's reader does (the decomp's shaderclasses.cpp): 0x18 `ScreenCopy` (one float, the Distortion particles' shader) and 0x1C `WaveDeformation` (a speed and an amplitude, the decomp's WaveShader) had no members and were read without their values, the rest of the shader from the wrong place; no retail material has them, and their applied shaders bits are ones no other type has (0x20000, 0x100000), the game only compares the keys (`ShaderTypeTests`). The alpha presets (`TwinShader.AlphaBlendPresets`, `G_AlphaRegPresets` filled by `FUN_001daa68`) are 0 Mix (Cs - Cd)·As + Cd, 1 Add Cs·As + Cd, 2 Sub Cd - Cs·As, 3 Brighten Cd·As + Cd, 4 Darken Cd - Cd·As, 5 Scale Cd·As, and zeros past them on PS2 (Replace: the source as it is); the blended retail materials only use 0-2. `Rendering/GsBlending` turns them into GL's blend state for materials and particles. Shader animations (`TwinShaderAnimation`: six tracks U, V, R, G, B, A in 1/4096ths, static or per frame, looping at the header's frames per second, `AnimateShader` 0x297260) still run in retail: the `FromAnimation` scroll modes take the U and V tracks as the UV offset and `AnimationDrivesColor` the color. TT Lab edits them on a timeline in the material's inspector (`ShaderAnimationEditorViewModel`, `Controls/ShaderAnimationTimeline`: a lane per track with its keys, the selected track's curve whose keys drag up and down (a static track's line as a whole), a row per track to make it animated or static and type its value at the playhead, frames put in as copies and taken out, the frames per second (no playback of its own, the material's preview plays it) and switches for what the shader takes from it: `MovesU`/`MovesV` set its X/Y scroll settings to `FromAnimation`, `DrivesColor` its 'animation drives color', one step each; the tracks it doesn't take are gray and read-only until their switch is on: their rows disabled with a tooltip naming the switch, their lanes and curve gray and their keys not dragged, `TimelineTrack.Used`). Every edit replaces the shader's animation with an edited copy made through the game's bytes (`ShaderAnimationTracks`: values where the game reads them, from the first settings' indexes, and the frame count the game times by following the frames while it was theirs), so leftovers stay and a drag is one step; the TwinTech classes have no nodes of their own. The viewport plays them (`ShaderAnimationSampler` samples the tracks at the render context's `Time`, `TwinMaterial` hands them to the shaders as `uv_offset` and `animated_color`). **Cloth deformation** (types 0x17 `UnlitClothDeformation`: `IntParam` mode, `FloatParam` speed and one amplitude; 0x1A `UnlitClothDeformation2`: mode, speed, an amplitude per axis, `ReadPrecompShaderType_0x17`/`_0x1A`): the game keeps 16 rows of 3 phases, each starting at a random angle in [0, π), and every frame (`FUN_001d1cf0`) moves them all by speed × time × 2π (mode 2: × time, wrapped past 10π), hands VU1 sin of each (modes 1 and 2 cos, mode 2 times cos of a second random set sped up 2, 2.3 and 2 times) as 16 quad words next to the amplitudes (`FUN_001d1948`). The VU1 programs (0x21 and 0x1E, disassembled in `Ghidra Stuff/Engine_RE/VU1`, `vudis.py` is the disassembler) move every vertex by the amplitudes times a wave per axis whose row is the low 4 bits of the float bits of the coordinate × 0.000373 (`MTIR` of the scaled position): a hash of the position, so vertexes at the same spot move together and nothing tears. `MainPass.vert` (`ClothOffset`) does the same with `floatBitsToInt` and fixed pseudo-random phases (`twin_material.deform_mode/deform_speed/deform_amplitude`). The **environment map** (type 0x16, VU1 program 0x1D) is no sphere map: per vertex H = normalize(normalize(eye − P) + N), d = normalize(L0·H, L1·H, L2·H) with L the chunk's three strongest directional lights in the object's space (the light controller's slots 4-6, transposed into the object block by `SetRigidModelRenderDMA`), and the picture is read at (0.5 + 0.5 d.x, 0.5 − 0.5 d.y) clamped, plus the material's scroll: a lookup by the half vector's agreement with the two strongest lights. `MainPass.vert` (`EnvironmentUv`) does it in world space with `RenderContext.EnvLights` (`Rendering/EnvLights.Of`, set from the scenery's `DirectionalLights` when its objects are made, defaults without any).
- **Character shadows** (verified in the PAL executable, `Ghidra Stuff/Engine_RE`): an instance's shadow node (`FUN_001caba0`) casts while the instance has its shadow (`InstanceState.ShadowActive`, every Crash instance has it), is visible and is in a scenery cell drawn this frame (instance flags 0x1000, 0x400, 0x200), its shapes, capsules between two joints, spheres and a plain one (`FUN_001c9130`/`FUN_001c9328`), cast from a point along a fixed direction above it into its chunk's list of up to 100 (`FUN_001cc460`). A chunk draws its list (`FUN_001f1a10`, `FUN_001ed468`: it and its linked chunks) only while its flag 0x800000 is set, which the scenery's draw sets when the cells in view hold instances or dynamic scenery (`FUN_001ed2e8`, every SM2 file has 0x20000 or 0x30000, the scenery reader takes its first word as the chunk's flags). Bucket 21's pass (`StartShadows`/`ApplyShadows` in the decomp's `shadows.cpp`) copies the screen's alpha top bit and its depth into a half size buffer, draws the shapes' volumes into it where that bit is clear (DATE) and in front of the depth, and takes a quarter of it away from the screen. So shadows fall on what a material without FBA drew: every retail scenery material, most objects and creatures; the characters casting shadows keep FBA so theirs don't darken them. New shaders get no FBA (`LabShader.AlphaCorrectionValue` on, shown as Receives Shadows), skins made in Blender keep it (`TlmMaterials`); the new chunk's ground had FBA and Crash cast no shadow on it, projects made before keep that `Ground` material until it's ticked.
- **Scenery lights** (`TwinTech/Common/Lights`, verified in the PAL executable): the header's low byte is the type the game lights by (`LightType`, written from the class), bit 8 `Enabled` is never read. The game lights an object once per instance at its position (`GatherStrongestLights` 0x1c7f50 from `FUN_001fe290`) with the lights whose bit the scenery root's `LightsEnabler` has, in the scenery's order of lights (`LightOrder`, else kind by kind): ambient lights add `Color` × `Intensity`, the others give a direction and an intensity there (directional: `Direction` and `Intensity` as they are; point: the way to the light times the falloff 25 / (d² + 25), no unit vector, and the intensity times the falloff `AttenuationPower` times; spot: that, nothing while the dot product of that way with -`Direction` is below `OuterConeCosine`, fading in up to `InnerConeCosine`, times that dot product to the power of `SpotExponent`'s low byte) and the 3 of the highest intensity are kept, a light only taking the place of a weaker one. Their colors become `Color` × intensity × 0.5 and the ambient is halved (`FUN_001c7d50`); the lit VU1 programs (shader types 2, 4, 12, 15, 16, `MaterialFactory.IsLit`; 0x2dbeb0, 0x2e3b40) give a vertex min(255, its color's bytes × (ambient + Σ color × max(0, direction · normal))), neither vector normalized, which the GS takes as twice the texture at most. Scenery materials are never lit. Without lighting (no lights, or a root without their bits) lit objects are black, which new chunks were: every retail scenery has lights and its root the bits of all of them and no others, so the lighting follows the lights (`SceneryData.HasLighting` is whether there are any, written as the file's flag) and the build gives the root those bits (`SceneryData.RootLights`). Retail colors add up to 1 with the brightness in the intensity (every scenery has one ambient light of a third grey at 3 to 6). A spot light (`SpotLight`, the tools' negative light) shines along `Direction` within `ConeAngle` (65536ths of a turn) fading out over `FalloffAngle`, but the game lights with `InnerConeCosine`/`OuterConeCosine`, which TT Lab makes again from the angles when a file's angles changed (`SpotLight.ConeCosines`). A directional light's `Direction` is a unit vector pointing at where the light comes from. `BoundsMin`/`BoundsMax` are the tools' boxes the game works out again at load (`ComputeBounds`) and never reads. In TLM files a light's node points its Z axis along its direction (the add-on's arrow), the stored `Direction` is kept while the node still points along it, a stored direction of no length (the add-on writes lights made in Blender with one) while the node isn't turned. TT Lab draws lit materials the same way (`Rendering/Lighting`: `SceneLights.At` gathers a `LightSet`, `InstanceBuffer.LightSetOf` writes one per object and frame for the instances to index, gathered where the nearest `ILightAnchor` (`OGI`) or the topmost parent is; `MainPass.vert`'s `LitColor`, skinned normals included): a chunk's viewport with its scenery's lights (`RenderContext.Lights`, made again whenever a light changes), single models and the material preview with `SceneLights.Default`. That's what new chunks get (`DefaultLights`: a third grey ambient light at 4.5 and a third grey directional light at 3 from above, also every new light's values; new chunks also get Crash, a 20 unit checkered ground with its collision and scenery bounds of the game's size, `AssetDataFactory.CreateChunkData`). The chunk's inspector edits the scenery's lighting: the light classes are foreign types (`ForeignPropertyAttributes`: hints, `Enabled`, the bounds and leftovers hidden, a spot light's angles in degrees with the cosines following, `SpotConeCosineChange`, a light's color picked as a color, `LightColorFieldViewModel`: the hue at full brightness, a picked color stored adding up to what the light's did, the brightness left to the intensity), new elements start as `DefaultLights` (`DocumentMetadata.RegisterFactory`). The viewport shows them in the Lights layer (`SceneryLightVisual`: a sun icon, a directional light's arrow the way its light goes, a point light's reach where its falloff halves the intensity, a spot light's cones) for the gizmo to move and turn (`LightDirectionRotation`, a viewport object's `IRotationConverter`: the direction keeps its length), and its menu places lights at the cursor (`CreateLight`).
- **Collision tree** (`AssetData/Instance/Collision/BvhBuilder.cs`, `BvhStats`; the game's `CheckCollisionRayCast` 0x27fb58, `FUN_0027f310`): the nodes (`TwinCollisionNode`, the tools' collision triggers) are the boxes of a binary tree, an inner node's `FirstChild`/`SecondChild` are its children's indexes, a leaf's are both `~group`, a group (`TwinCollisionGroup`: `Count`, `FirstTriangle`) a run of the (reordered) triangles of `Triangles` over `Vertexes`. A query tests the segment against both children of every box it enters and every triangle of every leaf it reaches, a box query gathers at most 256 leaves. The retail files are balanced trees halved by triangle count until 30 or fewer (leaves of 13-31, all at the same depth, ~7-10% sibling overlap), which `Strategy.MedianBestAxis` with 30 makes again within a few boxes and the same cost per ray; `Sah` (binned) is there for comparison. The Command Interface's `bvhstats <chunk.rm2>` measures a retail tree against every strategy under the game's ray walk.
- **Collision surfaces** (`Enums.SurfaceCollisionFlags`, `ITwinSurface`, `CollisionSurfaceData`): the game plays a surface's sounds and particles by contact kind (0 impact, 1 and 2 steps, 3 land, 4 hard impact, 5 scrape: `Impact*`, `Step*`, `Land*`, `HardImpact*`, `Scrape*`), objects landing on it play 0 (4 when hard) and 5 while scraping, scripts play any kind with `DoSound`'s bits 19-22 (`unused3`, 0xF plays the slots), and the player's own footsteps come from the character's sound table by surface ID. Of the 10 floats (`PhysicsParameters`, `SurfacePhysics` indexes them) five are the kinds' volume scales (-1 leaves the volume) and the rest are read too: index 5 (`Unread5`, `UnreadValue5` captioned Ground acceleration) how fast a character's velocity gets to what it's steered at, in units/s² (1000000 on most, 5 or 2 on slippy ground, 120 on liquids), `Friction` (6: rigid bodies' grip, with their own friction, 1 on most, 0.05 on ice; the characters steer in the air by 10 + 40 times it), `Restitution` (7: what rigid bodies' bounce is multiplied by, 0.5 on soft grounds, 0.1 on liquids), 8 and 9 (Downhill pull and Downhill pull slope) how hard ground steeper than the slope (the ground normal's Y below 9) pulls a character downhill, and the `UnusedVector` (Flow) is a velocity along X and Z the surface carries the characters along at ((0, 0, 0, 1) in retail). The flags are one bit per ray cast (`SolidToPlayerProbes` 4, `BlocksCamera` 5, `SolidToObjects` 6, `BlocksLineOfSight` 7), `SendsContactMessageToObjects` (8: a rigid body touching it hands its agent the surface's contact message, `DynamicBody::SurfaceContact`) and `SendsContactMessageToPlayer` (9), both on the deadly surfaces, `Sticky` (10: packs snow on the Rollerbrawl's ball), `LeavesFootprints` (11, captioned Soft: Nina clings to walls of it and skid trails are laid on it, footprints go by surface ID) and `SolidToPlayer` (20); bits 0-3 are the tools' tags and bits 12-19 are set on every surface, none of them read. The game copies the default chunk's surfaces into one table of 128 (`SurfaceTable`, no room check) that every chunk's collision finds them in by ID, see Layout indexes. The volumes live in the `PhysicsParameters` array. The `ContactMessage` (`TwinContactMessage`, the game's ContactMessage, which the scripts' damage commands send too) is a point, the `Kinds` of hit the contact is (`Enums.ContactKinds`, named after what sends each in retail: the surfaces (FallingThrough 0x4, Electric 0x80, GenericHit 0x400 the instant death, Burning and Sinking 0x800008 lava, Water and Sinking 0x2800000 drowning, Water 0x2000000), the engine (a crush, hitting back, particles with collision spheres burning a character) and the scripts' CreateDamage; nothing but the scripts' conditions tests them, besides the drowned staying still and lava melting the Rollerbrawl's snow, each check box's tooltip names its condition (the members' `[Description]`, `EnumCaptions.HintOf`), bits nothing sends or tests get none; rigid bodies touching the level's collision are told of a surface with any kind whatever its flags) and the `Damage` (100 on the deadly surfaces, 0 never reaches the agent's script), then 11 bytes of the tools' memory. The particle IDs (`ImpactParticleSystemId` kind 0, `StepParticleSystemId` 1 and 2, `HardImpactParticleSystemId` 4; land and scrape have none, `GetSurfaceParticle` 0x282160) are indexes into the default chunk's particle systems: the game plays entry index + 1 of its table of systems (`FUN_00223ad0`), which the default chunk's fill first, 0xFFFF none (new surfaces). The inspector names them and picks them from the default chunk's list (`DefaultParticleSystemFieldViewModel`, `->` shows the system in the default chunk), an index past the list shows as broken.
- **Instance state flags** (`Enums.InstanceState`): the engine reads bits 0-18 but 4 (`PlayableCharacterCanMoveAlong` only sets a context bit nothing reads). `TracksMovement` (5) gives the instance a node keeping its previous transform, `SyncCrossChunkState` (6) a persistent flag slot of its chunk (scripts' `CheckPersistentFlagCondition`), `PersistentFlagInChunkStore` (7) keeps that flag in the chunk meta's own store, `SnapToGround` (18) places the instance on the ground below when created. Scripts test any bit of their instance's state with `SoftFlagSet(n)` (condition 67, retail's `CheckInstanceFlagSet`), so bit 4 and bits 19-31 (`Unknown4` to `Unknown16`), which no engine code reads, are the scripts' own, captioned SoftFlag4 and SoftFlag19 to SoftFlag31: the retail creatures', drones', bats' and penguins' scripts read 19-31 as options of their instances (each set on 9 to 681 of the PAL version's instances), no retail script tests 4.
- **Instance properties** (the game's `PropertyList`): instances, templates and objects keep three lists the class of the object's type copies into its property holder (the rest go to extras): tagged values (`TaggedProperties`: an int, an angle or a float, or another property's index, `Common/AgentLab/TaggedValue`; the tools left a few raw words of no valid type), floats and ints. TT Lab keeps a tagged value's word (`TaggedProperty`) and edits it as text the way scripts write tagged arguments (`TaggedPropertyFieldViewModel`: an int as it is, `Float(x)`, `Angle(x)` in degrees, `Prop(n)`, `Raw(0x...)`; a plain number keeps the value's type). The class of the object's type keeps a fixed share of each list (`ObjectInstanceData.ClassProperties`: characters 9 tagged values, 56 floats and 3 ints, crates 0, 3 and 2, ...) and puts at most 7 more values of all three together aside (`PropertyExtras`, unchecked: more overwrite the game's memory), which building refuses (`CheckExtraProperties`). An instance's rotation is three signed words of 65536ths of a turn (`GetRotationXYZ` takes the whole word), edited in degrees, and its `SpawnScript` is the starter of the graph its agent runs whenever it starts (without one its object's first behaviour slot).
- **Layout indexes** (`Assets/Factory/LayoutIndexes`, the decomp's `instancesection.cpp`): the game numbers a layout's elements of a kind in the order it reads them and the build writes them by ID, so building a chunk gives each layout element its place among the chunk's elements of its kind and layout (`ExportTwinID` while the chunk's `LayoutIndexes.Current` is in use, the IDs outside a build) and references are those places: an element taken out (a gap in the IDs) made every reference past it point at the next one. Positions and paths are one list per chunk, the layouts' after each other: the chunk's own layouts (0-2 and 7) find positions from its start, the others past the positions of the last own layout before them that has any (`PositionReference`, `ChunkEntry::OtherLayoutPosition`), paths are found from the start (`PathReference`), and only those of layouts read before. Instances, triggers and cameras find instances among their own layout's (`InstanceReference`), AI paths their positions in the chunk's one AI layout (`AiPositionData.CheckAiLayouts`); the build refuses what the game can't find (retail never crosses a layout). Every chunk's collision finds the default chunk's surfaces by ID, so those have to be numbered without gaps (`CollisionSurfaceData.CheckPlace`, making a surface fills the lowest gap). New elements get the lowest ID free among their kind of their layout of their version's chunk (`TwinIdGeneratorServiceInstance`, by chunk path, package and layout): the PS2 and Xbox chunks of a path were numbered together, and one version's left the other gaps.
- **TT Lab model files** (`.tlm`, spec in `TT Lab/BlenderTools/TLM.md`): models, rigid models, meshes, skins, blend skins, OGIs, scenery, dynamic scenery, collision, skydomes and the save icon are stored as a JSON tree of nodes with their arrays in binary data next to it, written and read through `AssetData/Graphics/TlModel/` (`TlmFile`, `TlmNodes`, `TlmTreeNode`, `TlmMeshes`, `TlmAnimations`, `TlmMaterials`). The file is the asset's data file itself (`DataExt => ".tlm"`). Users edit them in Blender through the add-on's own importer and exporter, so:
  - A node has a `kind`, a `name`, its Twin Tech values in `data` (the same keys the add-on's panels edit) and a transform relative to its parent. Names are cosmetic, the hierarchy is only read where it means something: an OGI's bodies, exit points and collision hulls name the joint they follow, a scenery LOD's levels are the meshes under it, and a scenery's placed meshes and LODs are whatever has a mesh anywhere under its root but the collision and the dynamic scenery (`SceneryData.ReadPlacements`; a LOD's level moved out of its LOD is one too), each with the tree node it was in (`Node`) and its place among them (`Order`). TT Lab writes them under the root's `Meshes` (`scenery_meshes`) and `LODs` (`scenery_lods`), numbered in their group (`AddPlacementNodes`): they were one list under the root, which Blender showed as one long list. The add-on gives what's made in Blender under them their kind (`tlm_blender.role_of`, by the role of what it's in: a mesh in either group is a placed mesh, an empty in `LODs` a LOD, a mesh under a LOD its level). Skins and shapes have no transform, the add-on bakes where their object is under the root into the vertexes (a modder's mesh is usually rotated and scaled against the skeleton), and works a body's or exit point's transform out from where the object follows its bone (Child Of constraint or bone parent) with the armature at rest (`_attached_placement`). An exit point's game matrix is the node's `matrix`, carried by the add-on without showing it, like the bones' binds. A blend skin has as many shapes as its mesh has shape keys (`BlendsAmount` is derived), the add-on writes every key's weights into the facial animations.
  - **Collision hulls** (`TwinCollisionHull`, the game's `ModelCollisionData`, verified in the PAL executable's `HullsIntersect`/`BuildBoxHull`/`PackBuiltHull`): convex hulls OGIs keep on their joints (`OGIData.CollisionHulls`/`CollisionHullJoints`, joint 0xFF = the model's space; the game makes a box of the OGI's bounds for OGIs without any), dynamic scenery models and chunk links (`TwinChunkLinkHull`) carry them too. The blob is vertexes, one outward plane per face (`n·p + w ≤ 0` inside), the unique edge directions and face normals (the separating axes of the SAT test: A's normals, B's normals, cross products of both hulls' edge directions), the faces' offsets, the faces (count then vertexes, counter-clockwise from outside) and the edges (vertex pairs). The retail files have no per-hull collision surface (the loader reads one only in another file mode). `hull` nodes in the files, wire meshes in Blender: TT Lab keeps the game's planes and axes while `twin_vertices`/`twin_faces` match and the node has no transform, else bakes the transform and works them out like the game's builder (`ComputeFromFaces`). The OGI viewer draws them (`Rendering/Objects/OGI.DrawPrimitives`). The game collides them as convex (separating axes, a point or sphere behind every face's plane) and copies a hull's vertexes into 64 places on its stack (`HullsIntersect`) and a distance per plane into 64 (`SphereInPlanes`), with no check (retail hulls have 24 vertexes and 33 planes at most): TwinTech refuses writing more (`TwinCollisionHull.MostVertexes`/`MostPlanes`), the add-on writes a hull that isn't convex as its convex hull with a note (`hulls.is_convex`, `tlm_blender._convex_hull`: Blender's, coplanar triangles joined) and refuses one past 64 vertexes or faces (`hulls.check_hull`). A chunk link's hulls are loading zones (`LoadLinkedChunks` 0x2aa118: the linked chunk only loads while the player's position is inside one of them, `IsPointInsideHull` reads only the planes; a link without hulls always loads its chunk), 55 of the PAL version's 337 links have them, all boxes. TT Lab keeps them as `ChunkLinkHull` (JSON, still under `ChunkLinksCollisionData`): a `Placement` the gizmo moves (a box's half extents are its scale) with the corners relative to it, and the game's hull kept while the corners are still where it has them (`ToTwin`). The chunk editor draws them (`LinkHullVisual`, the "Link hulls" layer) and the inspector lists them under the link, new ones are 2 unit boxes.

The add-on imports it as a mesh whose shape keys are the shapes and whose shape keys' value curves are the animation (the basis's keys and the frames' order kept on the root, `SAVE_ICON_PROPERTY`), and its material from the embedded image (`_embedded_material`, an embedded material of any file now comes in with its image, and `_png_bytes` hands an unchanged packed image back as it is); shape keys are written for skins and for what's `shaped`. Building writes `Crash.ico` from it (`SaveIcon.ExportToFile`). The retail icon comes back byte-identical through Blender even without `exact`. Its editor has a viewport like a model's (`SaveIconData.GetViewportObjects`, `Rendering/Objects/SaveIconPreview`): the icon upright on the floor grid, the texture (no asset, `TextureService.SetTexture` keeps it under the icon's URI) times the corners' colors as fractions of 255, in the frame the Animation panel plays (`SaveIconAnimationViewModel` on `SaveIconData.Icon`, like the OGI's animations: a slider, play, pause, stop, loop and a speed, the shapes' weights at the frame; it starts playing by itself, the browser plays the icon all along, and says why a still icon has nothing to play) the way PS2IODB's player does (its timing was compared with the PS2 BIOS): 60 frames a second times `AnimationSpeed`, looping over `FrameLength` (`PlayOffset` unused), whole frames, every frame's keys joined by straight lines with the first and last weight held, every shape times its weight over the weights' sum (the first shape alone while they add up to nothing). Blender shows shape keys over the first shape instead, so when the animation changed in Blender (the root keeps every curve's keys as imported) the add-on writes the first shape's weight as one minus the others' at every time any of them has a key (`save_icon.basis_keys`), which makes the weights' sum 1 and the console's blend Blender's; unchanged, its keys stay as read. An icon animated in Blender while its `FrameLength` is still 1 (the retail icon's: one shape, nothing to play) gets the frame of its last key as its length, with a warning, or it would loop over one frame.

The game draws a skin's parts with their materials' VU1 programs (the decomp's `SetSkinDMA`): every PAL and Xbox skin and blend skin has a material whose first shader is `LitSkinnedModel` (NTSC's beach has one StandardLit part, Cortex's in the training cutscene, which PAL made `LitSkinnedModel`), and a skin of TT Lab's drawn with a StandardUnlit one hung the game: `TlmMaterials` keeps a file's materials by index and use, so a Blender material a rigid part and the skin share becomes one of each kind (found again by its Blender ID and kind), a skin's placeholder is skinned, and a skin drawn with a project material of another first shader is warned about when the file is read and when it's built (`TlmMaterials.CheckDrawsSkins` from `SkinData`/`BlendSkinData.Export`), not while a project is created (`AssetManager.IsCreating`: the files of skins two models share are read back while their materials are written and let go of, and the check found no shaders on PAL's Aku Aku).

Blender's weights add up to anything (it scales them to 1 when deforming), TT Lab normalizes the 3 strongest (`TlmMeshes.ToJointInfo`), the game's stay while the shares match. Normals of zero length always stay. The add-on keeps the vertex order and writes a vertex once more for every other value its corners need.
  - Values the game stores next to what the file shows (bounds, joint world transforms, inverse bind matrices, the matrices of exit points and placed scenery, collision order) are kept in the node's data and reused while they still match (`TlmNodes.KeepStored`, `OGIData.IsSamePose`), so unedited assets round-trip byte-identical. Bones rest where the joints' bind poses put them without the scale bones can't have.

Everything else, including every part made in Blender, gets new strips from `MeshProcessor/Stripifier`. Rigid models flip the triangles ending on an even position of their batch, skins the ones ending on an odd position of their strip (a strip starts two vertexes before one that draws after two that don't).
  - Xbox parts (`StripLayout.IgnoresFacing`) have one batch per strip, and skins keep every strip's joint palette (`StripBatch.Joints`). - **Skeletons** (verified in the PAL executable, `SetJointAnimations`, `TransformJoints`, `DrawOgi`): the game builds an OGI's skeleton in joint order, every joint under its parent's, and moves every joint without a parent as its root; it works out the joints' matrices walking the skeleton from the root down, a joint's children in the order of their indexes and each with everything under it, and draws the joint of an index (skin, inverse binds, rigid parts) with the matrix of that place in the walk. So a skeleton has one root, joint 0, its joints numbered 0 to n-1 in that walk's order, like every model of both discs (every joint after its parent isn't enough: a bone added under a hand took another joint's matrix), a joint has 12 children at most (`GetJointAnimationFromParentJoint` has none for a 13th, whose children then read from nothing) and a skin is drawn with 63 joints at most (their count goes into 6 bits of a VIF UNPACK). Rotations become the game's Euler angles through `GlmExtensions.ToEulerAngles`, because GlmSharp's `quat.EulerAngles` gives NaN at gimbal lock.
  - A joint with independent scaling still moves with its parent's whole transform (its offset gets the parent's scale), only its own axes leave out the parent's scale, like Blender's "None" scale inheritance the add-on sets (`animator.apply_to_all_armatures` on every frame change and scene update, only on armatures of Twin Tech models, `animator.is_model_armature`: it set every bone of every rig in the scene to Full). OGI 393's first animation scales the joint above everything to 0.3 and each part to 0.32 and ends on the bind pose at that size. The viewer's `TwinBone` keeps each bone's world rotation apart from its matrix, because animations hide joints by scaling them to nothing and joints under them that don't inherit scale still turn with them.
- **Cameras** (`CameraData`, TwinTech `Common/CameraSubtypes`, verified in the PAL executable, `Ghidra Stuff/Engine_RE`): a camera trigger runs up to two subtypes, each giving the camera's position for the player's. Points (`CameraPoint`, `CameraPoint2`: `Mode` 0 the `Distance`'s share of the way from the target to the point, 1 that many units from the target towards it, 2 the same no further than the point), lines (`CameraLine` sliding to the player's nearest point plus the base `Offset`, `CameraLine2` sliding by the player's flat distance between `NearDistance` and `FarDistance`; between them the game adds `NearDistance` to the share, a retail bug every camera of the kind avoids with 0), paths (`CameraPath`: the AI paths' B-spline with the same `ArcLengths`/`InverseSteps`), sampled splines (`CameraSpline`: samples a `StepLength` apart with unit `Tangents`, `ArcLengths`/`InverseSteps` like a path's; a sample's W is a word, the decomp's `SampleWord`: bit 24 passes over the sample, else bits 8-23 are an offset along the curve, n × 50/32768 − 50 units, which `SplineFlags` bit 0 replaces with the `Offset`, and bits 0-7 a share of the way toward the target, n × 5/128 − 5, both taken between the samples that have them; every retail spline's ends have them, and `CameraGeometry` gives new samples (W 0 reads −50 and −5) the passing word and ends without values the neutral 0x7FFF80; the inspector edits a sample as its place, Key, Offset and Share (`SplineSampleWord`, `SplineSampleFieldViewModel`, the samples' list's `DocumentCollectionViewModel.ElementEditor`), each part a step of its own, a passing sample without values made a key gets the neutral values and a key of the lowest offset and share keeps bit 25, which nothing reads, so its W isn't a new sample's 0), zones (`CameraZone`, `CameraZone::At`: where the player is within the flat `TargetBox`, across and along it, is where the camera goes within `CameraBox`; a box is the plane it lies in (its normal, across × along, and a leftover W; never read), its across and along axes, its corner and its sizes, X across and Y along (`BoxFractionsOf`/`BoxPointAtFractions`). `CameraBoxTransform`/`TargetBoxTransform` are them as matrices: across × size X, a thin thickness and along × size Y; TwinTech took the plane for an axis before and drew retail zones standing up) and the boss camera (`BossCamera`: the player in arena space through `WorldToArena`, the camera `Orbit.Y` from the axis in the player's direction at the player's height plus `Orbit.Z` while under `Orbit.X`, back through `ArenaToWorld`). Every subtype's `Follow` (`CameraSubBase.FollowMode`, one choice in its low two bits: `OwnWay` their own way, `AtRate` at `FollowRate`, 0 and 3 straight there) tells the camera rig's point followers how to move to its points. Only lines, paths, splines (with `ITwinCamera.SplineCameraFlags.TakesOffset`, the only bit of `SplineFlags` the game reads) and 1C09 read the `Offset`, zones don't even have the follow values in their files: the inspector leaves those out (`ForeignPropertyAttributes` keyed on the subclass, `Of` starts at the property's `ReflectedType`). `CameraPoint2.Mode` is a `PointMode` choice. The main camera's `Flags` (`ITwinCamera.CameraFlags`) tell the camera controller what to take from it (`FUN_00274e08`): `SetsPitch`, `SetsYaw`, `SetsFov` and `SetsDistance` hand its three angle blenders and distance the `PitchStart`/`PitchEnd`, `YawStart`/`YawEnd`, `FovStart`/`FovEnd` (65536ths of a turn, the blenders are named by the levels' values: 20°, half a turn, 32°) and `DistanceStart`/`DistanceEnd` (5, 10, 4.5 units), as the two targets of a blend over `BlendTime` seconds or, with `ValuesAlongGeometry`, the values at the start and end of the camera's line, path or spline; `BlendsInFrom*` replace the yaw's, pitch's and distance's ranges with `BlendInYaw`/`BlendInPitch`/`BlendInDistance` whenever the yaw is at least as near `BlendInYaw` as `YawStart` (`MainCamera::NearerBlendIn`, every frame the camera is taken: a camera entered from that side keeps looking that way), `NoBlendIn` cuts, `CutsFromSameKind` cuts between two cameras with it, `SetsTargetFollowRate`/`SetsPositionFollowRate` make the rig's point followers move the point the camera looks at and its place at `TargetFollowRate`/`PositionFollowRate` (shares of the way a second), `SetsYawSpeed` turns the yaw blender at `YawSpeed`, `NeedsRunningCamera` takes it only after another camera the frame before, and without `IgnoresPlayerState` a new camera is only taken on foot while the character is on the ground (`FUN_001434a0`). The rest are the follow camera's (the decomp's `FollowCameraPositioner`/`FollowCameraTarget`): `Steers` keeps its probes on, `GivesTargetBox` makes `TargetBoxMin`/`TargetBoxMax` the box the point it looks at sits in (the box's middle from the followed object, turned with it unless `TargetBoxUnturned`), `FramesInstances` moves that point toward the trigger's instances by `FramingShare` up to `FramingDistance`, `HoldsStill`, `KeepsHeight`, `OnlyLooksAtTarget`, `Tilts`, `NoProbes`, `BlendsWhenNear`, `BlendsAlongLine`, `SkipsViewCheck`, `AlwaysTakesValues`, `AddsExtraYaw`; bit 14 is never read and bit 1 only by a switch back nothing starts. `Switches` (`CameraSwitches`, 0 on nearly all) has `SecondSlot` (a camera for the character's death: taken only once the character died, shown while it's dead), `KeepsProbesWhileIgnoring` and `ResetsController`, `Group` keeps cameras of different nonzero groups from replacing each other. Without their flags the target box and the framing values are the tools' memory. The camera's trigger has bits 18 and 20 set in the levels, never read. `CameraGeometry` derives what the game stores next to the geometry (a path's and spline's parameters, a spline's tangents and step, the boss camera's other matrix) when it changes, keeping the game's values otherwise. The game reads both boss matrices (`FUN_00279990` computes neither) and uses each as the other's inverse (`BossCameraAt` takes the target into the arena through `WorldToArena` and the camera back out through `ArenaToWorld`, `FUN_0027cfb8` keeps the previous position in arena space), the game's pairs agree to 6e-6, so `WorldToArena` is read-only and follows `ArenaToWorld` in the inspector like a chunk link's `ObjectMatrix` (`InverseMatrixChange`, through `ForeignPropertyAttributes`). `CameraGeometry` also makes the viewport's handles: a draggable point for every point and sample (`Position` nodes may be `Vector4`s, their W stays), a box for each zone box (`Transform` through the box matrices) and the boss camera's arena cylinder (`CameraArenaVisual`), all in the camera paths layer.
- **Triggers** (`TwinTrigger`, verified in the PAL executable): the header's low byte is the tools' `Kind` (50 on most), 0 makes the trigger a box of its chunk's second reverb instead of a trigger node (`SoundBox`, 7 a chunk: the sounds take the chunk's box reverb, which scripts set with `SetSound`, while the listener is in one), and a camera's is its priority (`OfferCamera`: of the cameras the character is in the highest is taken, the one in use on a tie; captioned Priority in cameras, `EditorCaptionIn`). Bits 8-11 send the messages (`Enums.TriggerFlags`, the decomp's `MessageTriggerNode`): 11 the first to what enters until anything was inside at a check, 8 the second to what enters when the first isn't sent, 9 the third to what stays and to what enters when neither is, 10 the fourth to what leaves, the trigger's instances told along. Bit 12 is `NotPolled`. `ObjectActivatorMask` says what sets it off by object type: the playable characters check triggers of the character's bit alone (only the player then) or of none (any playable character) themselves every frame unless they tell what leaves, the rest are polled every `CheckInterval` seconds (0.3, stored in ticks by the node, `FUN_001f5428`) for instances of those types; cameras need the character's bit. The box reaches from -`Scale` to `Scale`, turned by the rotation's quaternion. `InstancesGrowth` is the tools' list growth (10; instances' lists of instances, positions and paths have one each). **Chunk links**: `Visibility` (`ChunkLinkVisibility`, the flags' low 7 bits: 0 hidden, 1 always drawn, 2 drawn through the load wall as a portal, `FUN_001ea3a8`), `KeepLoaded` and `IsLoadWallActive` (bits 7-13, either makes the linked chunk's own links load a level deeper, `LoadLinkedChunks`), `LoadsWithoutPlayer` (type bit 1: a link with hulls loads its chunk while there's no player yet). A zero `LoadingWall` is no wall (the build writes none), links without one are stored without one (`ShouldSerializeLoadingWall`, a link read back got a zero wall every save wrote). New links get a 10 unit square wall standing on where they're made, facing +Z (`ChunkLink.WallAt`: the constructor's at the origin, the viewport's menu's at the cursor), so it shows and can be dragged; a zero wall has no object in the viewport. Reading a link back puts the zero in first (`[OnDeserializing]`), so links stored without one (the game's 59 of 337, copies, prefabs) keep none. **AI positions**: the game's nearest point search (`FUN_0023c288`, what `SetFocusPositionToNearestPoint`, `LinkToNearestPoint` and `SetNearestPointFlags` use) goes by the coordinates alone, and the W of the position (`AiPositionData.Radius`) is only read by the `NearestPointEdgeDistanceSquared` condition (`FUN_00225be0`) and `GetShortRoute`'s distance limits (`value16`/`value17`: no route when the start or end is farther than them from the nearest positions' edges), which take it off the distance to the nearest point: the position's radius. The viewport draws it as a ring on the ground (a sphere while selected) and drags it by a handle on the ring's +X side (`AiPositionRadiusVisual`, `AiPositionRadiusHandle`). Their `Flags` (`Enums.AiPositionFlags`, bits 1, 2 and 4 in the levels) are read by the path finder (`Blocked` keeps routes out, the nearest point search with flags asks for some and rules some out) and the scripts' conditions on a route's step (`Airborne`, 2, 4-6); `SetFocusPositionToNearestPoint` never takes a position with flag 4 and takes one with flag 2 however far it is (others within 30 units), `SetNearestPointFlags` switches bits 0-2. An AI path's `Flags` (`Enums.AiPathFlags`) say which routes may take it (a route request's bits 17-24 rule out the paths with some) and what the conditions find on it (`NeedsJump`, `NeedsLongJump`, `NeedsHighJump`, `Flag5` flying, captioned NeedsFlying; bits 0 and 1, which the tools set together on a sixth of the paths, are never read), its `ChunkA`/`ChunkB` are the tools' chunk indexes the game replaces when it links the navigation. A chunk has one table of AI positions and paths that every layout with any makes anew, so they're all in one layout (6 in retail, see Layout indexes). An object's `SubType` (bits 12-19 of its header, 1 everywhere but the red wumpa's 17 and the projectiles' 18) only picks a pickup's node (16, 17) and drops its properties (16). The collision data's `Version` (3001) and the dynamic scenery's (0x10009) are read and never checked, a dynamic model's `LeftoverInt` (8) never read, its settings' `LeftoverByte` (22) never read and `ChannelCount` (7) turned into a mask nothing tests. A scenery's `UnusedByte` is never read. Its `FogColor` picks one of the executable's 8 tables of 256 colors (`SceneryFog`, 0x2f6ff8, `FUN_001aeab8`): every frame the game draws the screen over itself through the table (`FUN_001aee28`), the top byte of each pixel's depth picking a color whose alpha mixes it in, up to 30% far away and on the sky and nothing up close (table 6 has alpha 128 everywhere and changes nothing), switched to the player's chunk's when the player enters it (`FUN_0013be10`); retail uses 0 to 5. **Scenery trees** (`SceneryTree`, `Ghidra Stuff/Engine_RE`'s Scenery trees, checked on every tree of both discs): the root's `TreeDepth` is handed to the node search that ignores it, a tree node's `BoundsMin`/`BoundsMax` are its octree cell grown to hold everything placed under it, which the draw culls its subtree by and the search goes by, `BoundsCenter` (W the radius) and `BoundsHalfSize` the tools' values worked out of them, and only the root's light bits are read. TT Lab keeps a scenery's meshes and LODs as a list (`SceneryData.Placements`: the model, its matrix, its box and the tree node it's in as its octants from the root, `Node`) with the root's cell (`BoundsMin`/`BoundsMax`) and the depth (2 to 5 in retail, 5 for new sceneries, the inspector's Tree Depth), and the build makes the tree (`SceneryTree.Build`): an octree of the root's cell, a child the octant of its slot (bit 0 X, 1 Y, 2 Z, a set bit the lower half, in the game's float math of `FUN_001ebe00`), nodes at the depth leaves and the others nodes, every node on the way to something placed and no other, each followed by its children in slot order, a node's meshes then its LODs in list order. A node's box is its cell grown by the world boxes of what's under it (the root's never grows, 4 retail meshes of each version stick out of it), the W of its corners and half size the radius of the parent's cell, its center's W its own radius, its light bits the root's. A placement stays in its node while the node's cell grown twice around its middle holds its box (every retail one does), the others and new ones go down the octants their middle is in while that holds (where the tools put 91%, the rest depends on the order they put them in). The tools rounded otherwise (x87 or another order of operations, no float or double formula reproduces them), so importing keeps the game's values of the nodes the build doesn't work out to the bit (`SceneryData.TreeNodes`, `SceneryTree.Flatten`: 22616 of the 25977 nodes, their own light bits only for the 196 whose differ from the root's), used while they're within 1e-5 of the node's size of what's worked out and written while the tree still has the node and needs them: every tree of both discs comes back byte-identical. The game keeps every instance in the deepest tree node whose cell holds its box (`FUN_001eb250`, `FUN_001fa4b0` with 5e-05 of play) and leaves one in none out of the level's collision checks, so the root's cell has to hold every place objects go: every retail root is a box around the origin well past its level (the beach's ±210 × ±136 × ±251). A new chunk's root was the cell of its flat ground and Crash crept along at a sixth of his speed, couldn't jump and stopped at the edge (the collision tree's own root box is never read: rays and box queries start at its children). The scenery's `Bounds` (`SceneryBounds`: the root cell's middle and half size over its corners, `SceneryData.BoundsMin`/`BoundsMax`) edit it in the inspector and in the viewport's Scenery bounds layer (the box with a handle on the middle of its top, `SceneryBoundsHandle`, `SceneryBoundsTop` as the position converter, the scale tool setting the half size; both are computed values, see the editor system). New chunks get ±200 × ±100 × ±200 (`SceneryBounds.DefaultHalfSize`), and reading a file whose root has no cell of its own (made in Blender) or no room gives it that, grown to 1.5 times the reach of the collision and what's placed (`SceneryData.WidenRoot`); building warns when collision is outside it. A texture's `Reserved1`/`Reserved2` are 0 and unread, `SizeWords`/`ReservedBlocks` the sizes in blocks below.
- Instances belong to one of a chunk's 8 layouts (`LayoutID`, part of their URI and folder). The game doesn't name them, `ChunkLayouts` names them after what it keeps in each (0 main, 1 and 4 cameras, 2 and 5 crates, 3 extra actors, 6 AI navigation). Layout 7 only holds the default chunk's collision surfaces.
- **Chunk overrides**: a chunk keeps its own values of the assets it shares with other chunks (`LevelChunk.Overrides`, `AssetOverride`) instead of copies of them. Values are kept by their JSON path in the asset (`AssetOverrides`): its metadata without what makes it an asset of the project, and its data under `AssetData` when the data is kept as JSON the default way. Other data (models, pictures, sounds, code) can't have a chunk's own values, only the asset's metadata can.
  - Creating a project first makes a variant for each chunk after the first whose item has the same ID but other content (`Variation` is its chunk path, `GetUriByTwinId` finds the requester chunk's variants first). `VariantMerger` then turns every variant that only differs in values into an override of the first chunk's asset (a level's own version of a startup object into one of the global asset) for every chunk using the variant, and redirects what referred to the variant, including models' material URIs. A variant is often used by more chunks than the one it's named after, a later chunk with the same content found it by its hash; chunks use what they list in their resources and item versions and what those refer to down to other chunks. Variants no chunk uses (a chunk's model found the asset by its ID) go without values. Of the PAL version's 850 or so chunk variants only 5 textures of other pictures and 3 behaviour graphs of other code stay, the rest are 379 overrides of 111 chunks and every chunk builds byte-identical to before. A texture variant that stays is the chunk's own picture of an ID (the game reuses texture IDs, a hub's 16x16 `3B69A5CF` is a 32x32 one elsewhere) while the shared materials link to the base by URI, so the merger gives the chunk an override on every material linking the base with the link pointing at the variant (`LinkMaterialsToTextureVariants`), or the chunk built with the other picture, like hubd's whack-a-worm HUD did. Sounds were all the same, textures only differed in their header's leftovers, objects in their name, behaviour pack, template values and whether they list their resources.
  - Building a chunk exports its overridden assets as views (`ChunkOverrides`, `AssetOverrides.CreateView`): copies with the values, with the asset's URI and data file, made once per chunk because the chunk's resolution tells assets apart by their object. Views never save themselves.
  - A chunk's document edits the assets it shares through its views (`ChunkOverrideSession`, the property graph's `Overrides`), saving turns what they differ in into the chunk's overrides. The chunk's own assets (its resources, instances and what's in its folder) are edited as they are, and data without values of its own is the asset's, edited for every chunk. The inspector shows the chunk's own values with blue names, right clicking one puts the shared value back or shares the chunk's (`OverrideMenu`). A chunk reaches most of what it shares through links (an instance's object), their `->` opens the chunk's view in its inspector (`UriLinkViewModel.OpenDocument`, a step back is a click away, see the Inspector panel) and an instance shows its object's view in the viewport. Links to a view the chunk has values of its own in are blue as well (`DocumentNodeViewModel.GetLinkedView`). Data marked `[NoChunkOverrides]` (objects' names, the game only goes by IDs) is left out of views and overrides. A view's own values are the ones the chunk has or changed that still differ from the asset (`ChunkOverrideSession.GetOwnValues`), the asset can change in its own editor while the chunk's document keeps its view. Deleting an asset fixes the values of chunks' overrides that link to it the way the asset's own would be (`LevelChunk.FixOverrideValues`).
  - Each chunk still lists the objects and sounds it has (`LevelChunk.ItemVersions`), the build treats a startup object a level has as the level's own (it lists its resources). Building resolves those through `ITwinItemFactory.ChunkVersions` (`SerializableAsset.ChunkVersionOf`), which only swaps in the variants that stayed. Behaviours are one asset per name: the PAL version's chunks only differ in leftover memory in unused parameters (the NTSC version has the `0xCD` fill there).
- **What a chunk holds** (checked on every chunk of the game): the behaviours objects list, and the OGIs, animations and sounds they list or name in their slots. A graph's starter makes the game run the graph on its own and is only in chunks with objects listing it, so objects keep the graphs they list without their starter (`GameObjectData.GraphsWithoutStarter`) and put the starters in (`BehaviourGraphData.AddStarter`). High Seas' rats spawned with another chunk's starter running `COM_GENERIC_CREATURE_DESTROY` on them. The game's copies of the startup chunk's objects in levels list nothing (`ReferencesResources` off, not edited: chunks keep the disc's values as their own, and a startup object a level gets without having it on the disc is a copy, `GameObjectData.ListsResources`). Those, and startup objects a level has no version of its own of, bring no behaviours into it, only their slots' OGIs, animations and sounds and the objects they or their behaviours spawn (a crate's extra life). Instance templates (only the startup chunk's crates have behaviours in them) and instances' spawn scripts refer to starters, the ID before their graph's. The game reads templates into a table nothing looks up (`LoadInstanceTemplate`), so a template is its object, its `BehaviourStarters`, its `InstanceStateFlags` and properties; the tools' copies of the object's header bytes and list headers are written again from the object on build (`InstanceTemplateData.Export`).
- **Particles** (`TwinParticleSystem`, `TwinParticleEmitter`, `Rendering/Particles/ParticleSimulation`), worked out from the PAL executable (the Ghidra project's `GameParticle`/`ParticleInstance` structs and `GenParticle_*`/`GenerateParticles`/`BuildParticleRenderTable` functions, notes in `Ghidra Stuff/Particles_RE`): emitters (`ParticleSystemInstance`) play the system they name, their chunk's own or the default chunk's (`DefaultParticles`, one per version, `ParticleData.GetUsableSystems`/`FindSystem`, `ParticleSystemFieldViewModel`). Everything runs in frames of 1/60 s. An emitter on makes `GenRate` particles a frame (one every that many frames when negative, none at 0) for `EmitterOverTime` frames, waits `EmitterOffTime` (plus 1 to the random extras), the cycle shifted by the timing offsets against the frame counter, and only while the camera is between `CutOnRadius` and `CutOffRadius` (drawn within `DrawCutOff`). `MaxParticleCount` is what one lifetime makes times the ghosts (`TwinParticleSystem.ComputeMaxParticleCount`, the game recomputes it at load and TT Lab on write), the ring of slots that new particles write over, at most 1024. A particle is a start, a velocity and a spawn time: position = start + velocity·t + (0, `Gravity`, 0)·t² in the emitter's gravity space (the acceleration is twice `Gravity`; drips and splashes have negative gravity, fire and steam positive), the gravity rotation turning that space into the world. Rotations are 65536ths of a turn applied tilt (about Z, the up leans towards -X), yaw (about Y), roll (about X); the emit rotation turns the start and velocity within the gravity space. `GenSort` picks the generator (`GenSortType`: box, ranges, radial ring/cone with `RandomStart` = radius, yaw, tilt and `RandomEmit` = speed, yaw and tilt spreads, rotor, spheroid, plane bouncers with the emitter's `PlaneOffset`/`BounceFactor`/`BouncePlaneAngle`, area-even sphere, star), `GenCode` a fixed velocity-from-start rule (always 0 in the data). Ghosts are copies spawning `GhostSeparation` apart. Sizes and jibber amplitudes are ten thousandths of a unit, jibber frequencies cycles per life, colors bytes with 128 leaving the texture as it is, curves keys of a life fraction and a value sampled at 64 steps (the first pair of keys enclosing the step, 0 outside), texture rectangles pixels plus 2^19 (2^18 in a few systems; the game adds 2^19 and keeps the low 10 bits, `ParticleEmitter.TexturePixel`), `TexturePage` one of the default chunk's three pages. **Blend modes** (`ParticleBlendModes`, picked by name with `ChoiceFieldViewModel`): loading a page (`FUN_0019d9d8`) makes its four shaders in bucket 22, all dropping alpha under 5/128 and testing depth: 0 Additive (preset 1, 629 retail systems), 1 Subtractive (preset 2, the skid marks and the warp splash), 2 the page material's own first shader with those bits forced (normal blending in retail: smoke, dirt, feathers) and 3 Cutout (no blending, writes depth, unused); 0-2 don't write depth, 4-6 read the next page's IDs as the shader. 7 Distortion (unused) draws hexagons in bucket 23 through shader type 0x18, which copies the frame first (`FUN_001d6aa8`): the VU1 program (0x2e0960, `Ghidra Stuff/Particles_RE`) makes six triangles inside the particle's quad pointing along its height, the middle showing the copy where it is with the particle's alpha, the rim alpha 0 showing it moved by the corner's offset times (`Distortion.X` / 16384, -`Distortion.Y` / 4096), fading out with the depth to nothing at 40 units. `DrawFlag` is the draw list: the game draws list 0 (the modes in the order 3, 2, 1, 0) and list 2 (only mode 7, every mode 7 system is put there at load), never list 1. The `Unused*` fields and the tools' size/rotation ranges are never read by the game, `TextureFrame*` are recomputed and then never read (probably a texture animation), the switches and groups of emitters aren't read either. The retail data only uses GenSorts 0, 6, 7, 8, 9 and 11, version 0x1E, and no gravity rotation, roll, offset or plane on any emitter. Chunk viewports run the emitters' systems and draw them in their own pass with the default chunk's texture pages: the emitters queue their particles and `ParticlePass` draws them at its end in the game's order of the modes, each with its blending (`ParticleEmitter.DrawQueued`, `Particle.vert`/`.frag`; the page material's preset for mode 2, `ParticleData.GetPageBlends`), the hexagons over a copy of the frame (`ParticleDistortion.vert`/`.frag`), and leaves out what the game never draws (`ParticleBlendModes.IsDrawn`). The simulation reads the systems and emitters every frame and lines its cycle up again when the timing changes (`ParticleSimulation.Rephase`), so every edit shows right away; the default chunk's viewport plays every default system on a grid ignoring the camera (`DefaultParticleData.GetViewportObjects`). The curves are edited on a graph (`CurveGraph`) and the color on a gradient bar with a color picker (`GradientBar`), both through `ParticleCurveKeys`, which keeps the keys in order and the curve's end at 1; a key put in or taken out with the keys it moves is one step, so is a drag. A system's picture (`TexturePage`, `TextureStart`, `TextureEnd`, the corners hidden with `[EditorHidden]`) is edited as a rectangle of pixels on the page (`ParticleTextureRect`: `FromGame`/`ToGame` keep a corner's offset and fraction while its pixel stays, a start after the end mirrors) with `ParticleTextureViewModel` and `Controls/ParticleTexturePage`: the default chunk's three pages to pick from, the page with the game's pictures outlined (`ParticleTextureBank` clusters the usable systems' rectangles within 3 pixels) to click, the rectangle and its corners to drag (one step each), typed pixels and mirroring. Every particle item of both discs round-trips byte-identically. Systems', emitters' and decal variants' names are read up to their NUL (`ParticleNames`), what the tools left in the 16 (8) character buffer after it (the default chunk's systems, some level emitters) is kept in `NameLeftover` and written back, an emitter's name has to match its system's. A system's name is its own in its version of the game (`ParticleSystemNames`: the loaded particle assets as they are, the others by the names in their files, read in the background when a name is first checked and again when a file changed): the name field refuses a name another system has and says whose (`ParticleSystemNameFieldViewModel`, `TextFieldViewModel.CanCommit`), a system put into a list gets a free one (`NEW_SYSTEM`, `NEW_SYSTEM_2`, numbered within the 16 characters), and renaming one takes its emitters along (`ParticleSystemLinks`, one per document): the emitters of the same particles that played it as part of the rename's step, and once a renamed system of the default chunk is saved, the emitters of every other chunk of the version that play it (not those whose chunk has a system of that name, which they play instead), in the background, through the document of a chunk that's open, logged when done. The retail data names 47 systems more than once (four `XXX` in the default chunk, default systems that levels have copies of), their fields show it.
  - The default chunk's particle data also holds the **decal** system (footfalls, ripples): `UnusedDecalInt`, the `DecalUvPacket` (a VU1 packet of UV rectangles the game writes its GIF tag over), 16 `DecalTypeMarkers` (the tools' pointers, nonzero means a type follows) and the `DecalTypes` (`TwinDecalType`, 0x890 bytes: DMA tag, 15 variants of 4 color keys with alpha in W and 4 size keys with the time in W and the lifetime in the first's, the count, the variants' names). The game DMAs a type into VU0 memory and runs a microprogram per decal, so what the variants' vectors do beyond the lifetime is read off their values. The retail data has one type, "Ripple" and "FootFall".
- **PSMs** (`PSMData`, a list of PTCs: a texture and a material each) are the game's tile pictures: the legal, loading, game over and credits screens and the gallery are 8 tiles of 128x256 laid 4 across from the top left (512x512), the level titles one 128x128 tile, and `Startup/Icons.psm` is 40 icons (64x64, 32x64, 32x32) the game reads into the HUD's slots by their order and draws one at a time. Every part is kept upside down, like a font's pages. `PsmEditorViewModel` (`PsmEditorDesc` on `PTCs`, `Controls/PsmPicture`) shows the parts the right way up as the picture (`PsmLayout`: tiles when they're all the same size and 1 or a multiple of 4 of them, never for the PSM named Icons, whose icons go on a sheet), replaces the whole picture (tiles only) or the picked part with an image (resized to the picture's or the part's size) and saves either as a PNG. Replacing puts the pixels into the parts' texture assets and saves them right away, which no history undoes.
- **Fonts** (`FontData`) are edited with `FontEditorViewModel` (`FontEditorDesc` on `CharacterData`): every page with its characters' boxes drawn over it (`Controls/FontPageEditor`: the game keeps its pages upside down, the editor draws them the right way up (`GetShownRect`, a box's top row shown at `height - Bottom`, dragging down lowers `Bottom`) while the page's texture and a replaced PNG stay the game's way; clicking picks the character, dragging moves the box, dragging its bottom right corner resizes it, one history step per drag), the character table (code, page, left, bottom, width, height, edited through the document's nodes), adding and removing characters at the end, and replacing the selected page's picture with a PNG (8 to 256 pixels, powers of two; it replaces the page's texture asset right away, which no history can undo).
- Text files (`TextFileData`, Latin-1, written back byte for byte) are edited with the game's fonts (`TextFileEditorViewModel`): `Controls/PsfGlyphs` cuts every character's glyph out of a font's pages and `Views/Editors/Global/PsfGlyphGenerator` draws the text with them, a toolbar inserts the characters the fonts draw as controller buttons (`PsfGlyphs.ButtonCharacters`, the same ones in both versions), then every other symbol the font draws (`PsfGlyphs.Characters`, what a keyboard has no key for) and `~`, which the game starts a new line on. Undo is the document's history like the code editor's (the editor's own stack is off, `TextFileEditorViewModel.OnCurrentValueChanged` hands the text back to the view, typing at one place is one step until the caret moves). A font's table starts at the space, a character's box goes up from its bottom left corner (the page has it upside down), and page 0 and 1 are the first page, 2 the second and so on (the PS2's fonts number from 1 and give characters without a glyph 0, the Xbox's use 0 for the first page as well).
- Sounds are one asset per language and content, a sound item's hash doesn't cover its samples. A PS2 sound plays at its `Pitch` (`ITwinSound.PitchOf`: the sample rate times 4096 over 48000, truncated, handed to the driver by `FUN_001dfa38`), kept on the `SoundEffect` asset and set from the wav's rate when one is replaced; the Xbox item keeps the rate and derives it. `Param1` (32) goes to the driver with every play, `Param2`-`4` (16, 8192, 8192) and the `Header` (3, bit 0 clear = stereo) are read and dropped. Objects keep one sound per slot and chunks get every language's version of it. The startup chunk's sounds no object references (the game plays them itself) are its chunk resources. Without a playback device (the audio service throws when it opens none) sounds are still edited and replaced, only playing them is off (`SoundEffectViewModel.CanPlay`). **Loops**: a PS2 sound loops through its ADPCM blocks' flags (`TwinTech/Libraries/ADPCM`: blocks of 28 samples, bit 0 the last block played, bit 1 go back to the loop's start after it instead of stopping, bit 2 the loop's first block). Of the NTSC version's 812 sounds 717 play once (`00.. 01 07`: the last block flagged 1, then a silent block looping on itself; 166 have `00` there) and 95 loop from their second block to their last (`00 06 02.. 03`, nothing after); the Xbox's PCM sounds keep no loop. `ADPCM.Decode` includes the block ending the sound (the old decoder dropped it, 28 samples of every sound), `FindLoop` reads the loop and `Encode` writes both layouts, the loop's points rounded down to blocks and the samples after the loop left out; every retail sound comes back with its blocks' flags (the harness's `soundtrip` mode). The loop is the `SoundEffect` asset's `LoopStart`/`LoopEnd` (samples, the end exclusive, -1 without one), set on import from `ITwinSound.LoopStart`/`LoopEnd` and handed to `SetDataFromPCM` on build. The sound's editor draws the waveform (`Controls/SoundWaveform`) with the loop's handles to drag, playback following a click or a drag anywhere else on it, and buttons for the loop's start or end at playback, the whole sound or no loop (`SoundEffectViewModel`, whose node is the data's `[custom_editor]` one: the loop's nodes are the asset's), all in blocks of 28 samples through the document so undo covers them, and the preview plays the loop (SoundFlow's loop points); replacing the wav takes its sampler chunk's loop (`Riff.LoadRiff` reads chunks by their headers now) or loops the whole new sound when the old one looped.
- **List limits** (verified in the PAL executable): lists the game keeps in fixed places or counts in small fields have `[EditorParam(DocumentCollectionViewModel.MaxCount, n)]`; the inspector's add button stops there and says so (`CanAddItem`, `AddItemHint`), so do Ctrl+D and placing prefabs (`PropertyNode.MaxElements`/`IsFull`), undo and redo still put back what they took out, and a build refuses longer lists (`AbstractAssetData.CheckCount`, lists made before or by hand). A material has 4 shader slots with their count after them (`ReadMaterialShader` 0x1bbea0: a 5th pointer overwrote the count and the reader went on into the next material, retail materials have 1 or 2), a font 3 pages (`ReadFont`), the default chunk 16 decal types, the game's particle tables 300 systems and 768 emitters of every loaded chunk together (`ReadMainParticleSection`: systems past it are read and dropped, emitters not read; building a chunk warns when its systems and the default chunk's 255 go past 300), an object 255 of each slot, trigger message and instance property (its header counts them in bytes, like templates' and instances' property headers). An instance links 16 instances (`LinkToAgent` leaves out the rest) and counts its positions and paths in a byte, a trigger's or camera's node keeps 35 instances (`TriggerData.MaxInstances`, `TriggerNode::AddInstance` doesn't check), the game's table holds 128 collision surfaces and a path needs 4 points (`PathData.MinPoints`: a segment per point past the third, the viewport's Delete keeps them too). A link hull's corners are moved, not added (its faces are made of them). TwinTech refuses collision triangles the packing can't hold (18 bit vertex indexes, 10 bit surface index) and hulls past its byte indexes and offsets. Paths' points and chunk links are allocated to their size.
- Link fields (`UriLinkViewModel`) browse the assets of their `BrowseType` in their `BrowseScope`: the project, the document's assets, or `Scope.Chunk`, the chunk the edited asset belongs to (an instance's or trigger's instances, positions and paths). A link without a type browses everything. `GetBrowseCandidates` is what the browser gets.
- Toggling a bit of a `[Flags]` value in the inspector sets the whole value as its enum (the bit's node `SetsParent`, so a click is one step, it was two). A node whose value gets replaced raises `Changed` on every node under it, so editors of its parts (the bits' check boxes, a vector's components) show what undo put back.
- **Captions of what the game does**: names that say something else than what the game does with a value stay until a version of TT Lab renames them (2.0.0) and the inspector captions them instead: `[Editable(Caption = ...)]` on TT Lab's properties, `EnumCaptions` (`ViewModels/Editors/PropertyGraph`) for enum members (flags' bits, `FlagsFieldViewModel`, and enum dropdowns, `EnumFieldView` through `EnumCaptions.Converter`; bits the game never reads, `EnumCaptions.IsNeverRead`, get no check box and keep what they have: the camera's bits 1 and 14, surfaces' 12 to 19, AI paths' 0 and 1, the contact kinds nothing sends; a bit's check box gets its member's `[Description]` as its tooltip, `EnumCaptions.HintOf`), `EditorCaptionIn(editor, caption, hint)` for a property that means something else in another editor (a camera's trigger kind is its Priority, matched like `EditorHiddenIn`), and `ForeignPropertyAttributes` for TwinTech's properties, lists included.
- **Linked fields** (`[EditorLinkedField]`, `IFieldChange`: a trigger's `Kind`, `NotPolled` and argument bits and its `Header`, a chunk link's `ObjectMatrix` following its `ChunkMatrix`, a boss camera's `WorldToArena` its `ArenaToWorld`) run `DataChanged` when the value they follow changes; what they write is a consequence (`PropertyChange.IsConsequence`) recorded in the edit's step (one undo of a header edit took back only the last field), and while undo and redo apply the graph `IsReplaying`, so only `Linked` runs and the values come back as they were (made again, a link's object matrix got other floats: it's its chunk matrix's inverse only up to rounding). Values compare by their bits (`PropertyNode.IsSameValue`), undo couldn't put a NaN of other bits back. They get linked whenever nodes go into the graph (`PropertyGraph.Index`, so placed and relinked resources have them too, and a value of another type's children once they're all under it: `RebuildChildren` linked each before, among siblings looked for outside the graph) and only `Linked` runs then, which sets up what editors show (read-only fields): values written while linking changed assets just by opening them (every camera opened and saved lost its trigger's kind, links' matrices drifted). The fields shown of a trigger's header aren't stored, `TriggerData.DeriveFromHeader` works them out in every constructor and on deserialization (`[OnDeserialized]`, a camera keeps its trigger in its own file). New triggers are kind 50 checked every 0.3 s (kind 0 is the sound code's plain box), new cameras' triggers `0x140000` with no interval, like most of the game's.
- **Combo box editors** (enums, sample rates, layouts, render buckets, a slot's animation) ignore what the combo box hands back while they show a value (`_isShowing`) and give it a new list only when the choices change: a combo box whose list changed handed its old pick back, which the OGI animation field and the value then passed back and forth until the stack ran out, and a list changed in place made it pick items it no longer had.
- Assets are addressed by `LabURI` (`res://...`), not by game ID. `AssetManager.Get()` is the global registry (`GetAsset<T>(uri)`, `GetUriByTwinId<T>(requester, id, layoutId)`). Mark data classes that hold `LabURI`s with `[ReferencesAssets]`.

### UI and MVVM
- `AvaloniaScheduler` (the main thread scheduler) runs work right away when it's already on the UI thread, so `ObserveOn` doesn't keep the order of changes raised on several threads (tabs load on the task pool). Use such changes to look at the current state again after `ObserveOn` instead of passing their values on (`ChunkResourcesViewModel.FollowActiveEditor`).
- Avalonia 11 + ReactiveUI, with compiled bindings on by default, so every `.axaml` needs `x:DataType`. Docking uses `Dock.Avalonia`, and the code editor uses AvaloniaEdit with TextMate. The AgentLab grammar is `AgentLab/agentlab.tmLanguage.json` (embedded resource), served through `AgentLab/AgentLabRegistryOptions.cs`. Scripts are checked live with `AgentLabCompiler.Check` against the commands of the asset's version of the game (`Project.GetActionDefinitionsFile`), and AgentLab errors are `AgentLabSyntaxException`s carrying the line and column. Objects' command packs can only be a list of commands, no commands included (`AgentLabCompiler.CheckCommands`/`CompileCommands`, the `AgentLabCommandsOnly` editor param). Completion suggestions and parameter hints come from `AgentLabCompletion` in TwinTech, which scans the text before the caret instead of parsing, because scripts being typed are rarely valid. `AgentLab/AgentLabCodeCompletion.cs` shows them in the editor: the parameter hint follows the caret into a call, fields are suggested inside a packed argument's braces and `Prop`/`Raw`/`Float`/`Int`/`Angle` inside calls, and the rows are cached per item. `AgentLabCompletion.Warm` parses the definitions off the UI thread when an editor activates, the first completion parsed them on the first keystroke before. `AgentLabHoverHints` shows `AgentLabCompletion.GetHover` (an action's or condition's signature, a field's type, a keyword's or attribute's meaning) as a tooltip while the pointer rests on a word. A state names the behaviour it runs (`state S(COM_X)`, the `"res://..."` strings of older scripts still compile), resolved by `BehaviourReferences` within the asset's package and the packages it depends on (`AssetManager.FindByName`/`GetAssetsInScopeOf`: the global packages depend on nothing so their scripts only name their own, the PS2 and Xbox versions never see each other's, a level's own graph of a global name wins and the global one is then written by its URI). Importing writes the name when it finds the graph from there (`BehaviourReferences.ReferenceTo`). Inside the parentheses completion lists the behaviours in scope (`CodeEditorViewModel.GetBehaviourSuggestions`), the live check reports names out of it (`AgentLabCompiler.Check`'s `behaviourExists`), hovering one shows its URI and Ctrl+click or F12 opens it (`AgentLabNavigation`).
- DI is set up in `App.axaml.cs` and `DependencyInjection.cs` (MS DI bridged to Splat). Every non-abstract class ending in `ViewModel` is auto-registered as transient, except `ShellViewModel` (singleton `ILabManager`) and the types in `DependencyInjection.SingletonViewModels`. Views are matched to view models via `RegisterViewsForViewModels` (registered as `IViewFor<T>` only), and `Util/ViewLocator` looks up the view model's class and then its base classes itself (the Scenes and Resources panels, editors' roots, lists and particle system names show through a base class's view): ReactiveUI's locator only looks at the class and warned "Failed to resolve view for view model type 'System.Object'" about each of those, at start-up and for every editor opened (`ViewLocatorTests`). Service-locator access (`Locator.Current.GetService<ProjectManager>()`) is common.
- **Docking** (Dock.Avalonia, ReactiveUI model), with layouts built in code rather than XAML:
  - `ViewModels/DockFactory` owns the shell layout. Its panels are singleton view models that derive from Dock's `Document`: Project Tree, Log, the Scenes/Resources `EditorsViewerViewModel`s, Chunk Resources, Inspector and History (`ChunkResourcesViewModel`, `ChunkInspectorViewModel`, `HistoryViewModel`, tabs next to the Project Tree by default), and Prefabs (next to the Log).
  - Scene tabs only have their viewport. The Chunk Resources and Inspector panels show the document and inspector of the scene tab last worked on (`EditorsViewerViewModel.ActiveEditor`), inspecting something brings the Inspector's tab to the front (`DockFactory.RevealPanel`) and the resources panel keeps each chunk's view while its tab is open. Following a link in the inspector (`UriLinkViewModel.OpenDocument`: to the chunk's view of a shared asset, or to one of the chunk's own resources, inspected where the chunk's list has it so the scene and the resources panel follow, `DocumentViewModel.FindChunkResource`; anything else opens its own tab) is a step along the document's `InspectorTrail` (`FollowInInspector`). The Inspector panel's header goes back and forth along it (`InspectBack`/`InspectForward`, Alt+Left/Right, the mouse's side buttons, its steps as crumbs, `InspectCrumb`) and opens the shared asset a chunk's view is of in its own tab (`OpenSharedAsset`); what gets picked anywhere else (the scene, the resources panel) starts it over (`OpenInspector`), and steps whose nodes left the graph are passed over.
  - The chunk's `ChunkResources` are shown like the project tree (`ChunkResourcesTreeViewModel`, `Views/Editors/ChunkResourcesTreeView`): a folder for each kind of asset (level chunks always have the instance kinds, empty or not), the layouts of the kinds that have them, the resources in the chunk's order. Picking one inspects it (the viewport selects it), what gets inspected elsewhere gets its row picked and brought into view, a double click or Enter frames it in the scene, F2 renames it (its `Alias` through the document), Delete takes an instance of a layout out. A right click on a folder makes only its kind (`ViewportViewModel.CreateResource` of `CreatableTypes`, in the folder's layout or `DefaultLayoutFor`, the layout the chunk keeps most of the kind in; object instances of `DefaultObjectFor`, paths with four points, AI paths between the two selected AI positions), the links and particles folders add a link or an emitter. New resources go to the scene's cursor, in front of the camera without one (`NewResourcePosition`).
  - Layouts are serialized with Dock's Newtonsoft serializer, which resolves the panels through DI. `ValidateLayout` restricts which `$type`s are allowed.
  - The last layout is saved to `layout.json` next to the executable when the window closes, and restored on startup.
  - Each editor panel has its own `EditorTabsFactory`/layout, and its tabs are `TabbedEditorViewModel` documents (`SceneEditorTabViewModel`/`ResourceEditorTabViewModel`). Never share a factory between the shell and editor docks: Dock allows dragging between every `DockControl` that shares a factory.
  - Both factories derive from `DockFactoryBase`, whose `InitDockable` (which Dock runs on everything it lays out, adds or moves) gives every dockable empty `DockCapabilityOverrides` and every dock an empty `DockCapabilityPolicy`: Dock's tabs bind through both, and every tab logged binding errors while they were null (null values inherit, so empty ones change nothing). The shell window gets its view model before its XAML loads (`ShellView(ILabManager)`), because the `DockControl`'s theme binds to its `Layout` as soon as it's styled. `DockLayoutTests` shows the shell's layout and fails on any binding warning.
  - Ctrl+S/Ctrl+W/Ctrl+Z/Ctrl+Y (and Ctrl+Shift+Z) are `KeyBinding`s on the tab views, which are `Focusable` so a click anywhere in an editor moves the focus into it. `EditorsViewerView` binds them as well for when the focus is on the tab strip, and the chunk's panels and History bind the undo keys for the active editor. Closing goes through `TabbedEditorViewModel.RequestClose`, the same path as the tab's close button, and moves the focus into the editor shown next (`EditorsViewerView.OnEditorClosed`), the next Ctrl+W had nowhere to go otherwise. Avalonia drops the focus altogether when the element that has it leaves the visual tree (the X of a list's element takes its row away with it), and Ctrl+Z went nowhere until a click inside the editor; the tab views and the chunk's panels take the focus back once a click or key inside them leaves nothing focused (`Controls/FocusKeeper`: the input's route was made before anything got removed, so it still reaches them). They fire before AvaloniaEdit sees the key, and the code editor has no undo of its own (its `UndoStack.SizeLimit` is 0, it would undo the same typing again or the loading of the text): the document's history sets the code back, `CodeEditorViewModel.OnCurrentValueChanged` hands it to the view and `CodeEditorView.ApplyCode` replaces only what differs, with the caret at the change. Moving the caret somewhere else ends the step typing keeps changing (`UndoHistory.CloseStep`), so typing at one place is one step.
  - Saving a document saves every asset its edits touched (linked assets are edited in place) and clears `IsDirty`.
  - Closing TT Lab (`ShellView.OnClosing`, the close cancelled until it's answered), the project or every editor (`EditorsViewModel.CloseAllEditors`, opening another project) asks once about every editor with unsaved changes (`SaveOrDiscardUnsavedChanges`, their names in the `UnsavedChangesDialogue` closing an editor shows): Save saves them all, Discard goes on without them (closing every editor reverts them, `CloseTab(discardChanges)`), Cancel or a save failing keeps everything open. Closing the window didn't ask at all, closing every editor asked each in turn. On Linux `Program.Main` disposes Avalonia's D-Bus connection once the lifetime is over (`Util/DBusShutdown`, Avalonia's internal `DBusHelper` reached by reflection, recheck it after updating Avalonia): left to the process's end it went down on its own thread, its observers' synchronous Send to the stopped dispatcher threw, and every quit logged a `TaskCanceledException` as a crash; disposing it emits nothing, and not sooner: the lifetime's `Exit` comes while a window is torn down, whose D-Bus menu then found it disposed.
  - Every document keeps an undo tree (`DocumentViewModel.History`, `UndoHistory`) of the property graph's changes (`PropertyChange`: values, and elements put into or taken out of lists by their index). Changes of one value in a row (typing, dragging) are one step, `BeginGroup` makes one step of several (a gizmo drag, placing an instance and moving it to the cursor). Changing something after undoing starts a branch next to the undone one, `GoTo` goes to any entry, a change after a redo is a step of its own. Replacing a whole asset's data (textures, sounds) can't be undone and starts the history over. A value of another type (a camera's subtype picked or taken away) is a step like any other: its node makes its children again for the type it has (`PropertyNode.RebuildChildren`, `ChildrenVersion`) and composites showing them build theirs again, the old ones showed the old subtype's values. `IsDirty` is off again at the entry the document got saved at. When the inspected node leaves the graph (its resource deleted or its placing undone, its link pointed elsewhere) the inspector goes to what took its place or closes (`DocumentViewModel.FollowInspected`): editing it changed nothing the document had, and its steps' paths pointed at whatever came to its index. The viewport follows instances taken away or put back while undoing (`History.IsApplying`), placing and deleting them updates it directly. The History panel shows the tree of the editor last used (`EditorsViewerViewModel.Used`) and goes to the entry picked. It hears every change, typing included, so it only swaps the rows that differ while the tree stays the same.
  - Only `[DataMember]` properties of dockables are serialized, so view model state on panels stays out of layout files.
  - Dock keeps closed dockables alive through each `DockControl`'s control recycling cache and its private activation history. `EditorTabsFactory.ForgetDockControlReferences` evicts closed editors from both; the activation history is reached by reflection, so recheck it after updating Dock.
- **Tooltips** of the inspector (`DocumentCompositeView`/`DocumentModelView`, the `Hint`) sit on the property's name and a composite's header, not on the row: a row's tooltip showed while the pointer was anywhere in the rows under it and stayed until it left them all. They show after half a second, and popups are drawn in the window (`OverlayPopups` in `Program.cs`): every tooltip was a window of its own, and hovering across rows opened and closed one after another, which stalled the whole UI. Don't set `ToolTip.BetweenShowDelay` to 0: a tooltip closing and the next opening in the same tick made the next one instant.
- With popups drawn in the window, a combo box's dropdown is in the window's visual tree: its items asking to be brought into view (the selected one gets the focus as it opens, `ComboBox.ItemFocused`, and the dropdown's scroll viewer passes it on) bubbled out to every scroll viewer around the combo box, which scrolled the inspector up at every click on one. `Controls/ComboBoxDropDowns` stops those at their combo box, registered by `App` and the tests' `TestApplication`.
- **Property graph paths**: a node's `Path` is its parent's plus its own `Segment` (`.Name`, `[index]`, `[data]`), worked out when asked and cached until the graph's `StructureVersion` changes (every insert, removal or attach), and `PropertyGraph.Find` walks the tree a segment at a time (`FindChild`, elements by index). There is no path dictionary: keeping one meant renaming and indexing everything under a big list on every change, and undoing fifty deleted instances of a chunk took seconds (`PropertyGraphListTests`). Code reacting to changes compares nodes and walks parents (`ViewportViewModel.IsWithin`) rather than paths.
- **Angles in degrees**: values the game keeps in 65536ths of a turn (cameras' pitch, yaw, fov and blend-in angles, emitters' gravity and emit tilt, yaw and roll, the bounce plane angle) are edited with `AngleEditorDesc`/`AngleFieldViewModel` in degrees, converted back to the property's integer type: 32 bit words are the signed number the game reads (`static_cast<s32>`; l03stock's pitch of -361 showed as 23 million degrees, and a blend between -2° and 358° isn't the same), 16 bit unsigned ones wrap around the turn, `Int16` goes the shorter way.
- **What the game doesn't read**: values it never reads are left out of the inspector (`[EditorHidden]`, `ForeignPropertyAttributes`: shaders' leftovers, particle systems' unused floats, texture frames and the tools' size and rotation ranges, emitters' switches and group, AI paths' chunk indexes, triggers' list growth, sounds' Param2-4, the default chunk's decal markers, camera subtypes' unread offsets), values it only reads with some setting are grayed out while it doesn't (`Attributes/ReadWhen<TOwner>`: an `IFieldChange` asking the node's target, linked to every field the setting is made of): the camera's angle, distance, rate, box and framing values without their `Sets`/`BlendsInFrom`/`Gives` flags (`CameraData.ReadWith*`, a blend-in yaw needs any blend-in under its `Sets` flag, yaw start the yaw or a blend-in), a spline's offset without Takes Offset, a subtype's follow rate without At Rate, the boss camera's curves without Uses Distance Curves, particle systems' ranges, box and radial values, ramp time, star, distortion, draw list, ghost separation and collision radius by their generator, blend mode and counts, shaders' cloth parameters, custom blend formula, fixed alpha, destination alpha mode, scroll, animation color, shader color and depth test by their type and switches, surfaces' contact message without a message bit and the downhill pull's slope without a pull, a link's loading without the player without hulls (its load wall is used whenever it has one: the old gate on `IsLoadWallActive`, a keep bit, was wrong), a sound box's (a trigger of kind 0, which only takes its box: `LayoutInstances::RegisterTrigger`) activators, instances, interval, polling and messages, not a camera's, whose kind is its priority (`TriggerData.NotASoundBox`: `ReadWhen.IsRead(owner, node)` looks at what the owner is in), a trigger's messages without their bit, and an emitter's bounce values by the generator of the system it plays (`ParticleSystemInstance.FollowPlayedSystem`; a system's `GenSort` refreshes the emitters of its own particles, a default system changed elsewhere shows once the chunk's document is opened again). A shader's `LodParamK` is shown as `LodK`, the signed sixteenths the GS gets, and its scroll vector is the U and V phases then their speeds in turns a second. A sound's `Pitch` is picked as a sample rate (`SampleRateEditorDesc`, the known rates plus the current pitch when it's none of them).
- **Current editor system** (the one to use for new work) is document/property-graph based. Asset data properties carry attributes from `Attributes/` (`[Editable]`, `[EditorParam]`, `[EditorLinkedField]`, `[EditorHiddenIn]`, `[EditorReadOnly]`, `[ViewportEditable]`, ...). `PropertyGraphBuilder` reflects an `IDocumentModel` into `PropertyNode`s (TwinTech's types, which can't carry these attributes, are registered in `DocumentMetadataCache.RegisterForeignTypes` with every property shown, and `ForeignPropertyAttributes` gives single properties of them attributes: hints, links, read-only), and `EditorDescRegistry` maps property types to `EditorDesc`s, which create `Document*ViewModel` / `*FieldViewModel`s. Views derive from `DocumentBaseView<TViewModel>`. These view models use ReactiveUI source generators (`[Reactive] private bool _field;` on `partial` classes), `ReactiveCommand` and DynamicData.
  - Documents easily have thousands of editors, so editor view models stay cheap to create: `DocumentBaseViewModel` computes derived properties instead of observing them with `WhenAnyValue(...).ToProperty(...)`, creates its validation context on first use, and sub-editors (vector components, matrix columns) are made when shown. Only lists (`DocumentCompositeView` of a `DocumentCollectionViewModel`) of plain fields virtualize their items, lists of structs and models (`DocumentModelView`) never, whatever their length: a virtualizing panel takes the items it hasn't made for the average size of the ones it has, which is way off when items differ in size (a struct expanded among collapsed ones): lists jumped and dropped editors in sight, and with an expanded item near the end of a long list (the default chunk's 255 particle systems) the extent flipped as the panel made and dropped it, the scroll viewer clamped its offset each time and the layout cycled until the UI froze (`ListVirtualizationTests`). A collapsed model row costs 3 to 6 ms (mostly the Expander's template), so the Inspector panel keeps each document's inspector view and scroll position while its tab is open (`ChunkInspectorView`, like the resources panel) instead of building them again on every switch. Composites build their children once per expansion and keep them by the editors themselves: kept by their paths, which move when elements go in or out before them, a list's element put back by undo replaced the editor of the one that had moved to its path. List elements with a `Name` show it next to their index and follow it. A list's elements get the editor desc its `DocumentCollectionViewModel.ElementEditor` param names (`EditorDescRegistry.GetDesc`, a foreign list's through an `EditorParamAttribute` in `ForeignPropertyAttributes`), the list keeps the collection's. Captions are at most 200 pixels wide and wrap, long ones squeezed the value next to them to nothing. An asset's data has no editor of its own, its properties are laid out after the asset's (`DocumentCompositeViewModel.EditorInline` on `AssetData`), and data with nothing to edit shows nothing. Its nodes are still under `AssetData` in the property graph.
  - A document has one scroll viewer (`Controls/DocumentScrollViewer`, in `DocumentView` and the Inspector panel, vertical only): composites and models have none of their own and every editor expands downwards, only custom editors that lay out on their own (font pages, animation lists, particle graphs) scroll inside it. Tests hosting `document.Inspector` wrap it in one like the panel does. `FitToScrollViewport` stays for editors inside a scroll viewer that scrolls sideways.
  - Code and text editors (`EditorDesc.ShowsInSidePane`: `CodeEditorDesc`, `TextFileEditorDesc`) of the document's own asset (not what it links to, nothing under a `[data]` node) go in the document's side pane (`DocumentViewModel.SideEditors`, the right column of `DocumentView` with a splitter, each with all its height, `DocumentNodeViewModel.IsInSidePane`) and are left out of the composites (`ShowsInSidePane`); in the inspector they stay inline with a fixed height.
  - Scrolling a long list recycles its rows' views: `Controls/RecyclingItemsControl` keeps a recycled row's content (ItemsControl clears it, which dropped the row's whole subtree, about 80 controls for a point, and made it again for the next item: 70 ms per wheel notch on a 3000 point path, 19 now), and the `ViewLocator` is an `IRecyclingDataTemplate` that hands an existing view of the type its next view model (`IRecyclableView`: `DocumentBaseView.Recycle`; ReactiveUI's bindings follow the view's `ViewModel`, only views whose activation decides something from it or whose controls reset while it changes, combo boxes, `RebindsOnRecycle` and get their bindings made again; custom editors with state of their own set `CanBeRecycled` false). `ListRecyclingTests` checks it.
  - `DocumentViewModel.OpenInspector(node, focus)` expands the inspector down to `focus`, highlights and expands it and scrolls it into view (without a focus it just expands `node`). Each composite hands its view a one-shot `NodeScrollRequest` that the view takes, since views of recycled items get created again and a lasting request made them scroll back. `DocumentBaseView.BringNodeIntoView` retries after each layout pass until the document's scroll viewer shows the target, virtualized lists realize it on the way.
  - A material's render bucket is picked from a dropdown of the game's 28 (`RenderBuckets`, `RenderBucketEditorDesc`), named after what the game's materials and code use them for. ### Rendering (`Rendering/`)
- A custom Silk.NET OpenGL renderer draws to an offscreen framebuffer, which is shown in Avalonia via `Controls/Viewport.cs`. It uses render passes (`Passes/`), batches, a scene graph (`Scene/`) and gizmos. GLSL shaders live in `TT Lab/Media/Shaders`. Math uses GlmSharp (`vec3`, `mat4`), and `Extensions/GlmExtensions.cs` converts to and from Twinsanity vectors.
- GL work must be queued onto the render thread (`RenderContext.QueueRenderAction`), and UI work onto `Dispatcher.UIThread`. Scene graph structure (adding and removing children) changes on the render thread. Transforms, colors and visibility get set from the UI thread. What the render thread reads the UI thread may be changing: the selection it draws is an array replaced whole (`EditingContext`), a resource's objects are made again for the asset its node had when the rebuild got queued, not for whatever a later undo put at the node's index (that made another resource's objects twice), only while the node is still in the graph, and a rebuild reading the graph while the UI thread changes it (undoing many steps in a row) is tried again (`RebuildAttempts`); removals of gone resources are worked out when they run, and `Renderable.RemoveChild` only removes the child itself, never another one of its name.
- Each `ViewportViewModel` owns a `Controls/ViewportHost` for as long as its editor is open: the GL context, the render thread and the frames. The `Viewport` control only shows the host's frames and passes it the input while it's attached, so switching tabs or floating them never rebuilds the scene. The context's window is a hidden 1x1 SDL window only there to make the context current, frames go to a framebuffer of the host's (`RenderContext.OutputBuffer`).
  - The host renders at 60 FPS while it's shown and reads frames back through pixel buffers a frame late. A viewport that isn't drawn for half a second (a hidden tab) only processes its render queue until it's drawn again, and keeps invalidating its control meanwhile: Dock keeps the content of tabs that aren't shown, only hiding it, and a control shown again doesn't draw until something invalidates it.
  - SDL's GL driver stays loaded for the whole run: SDL unloaded it with its last GL window, which crashed the driver while Avalonia and other viewports still used it. A hidden window's context stays current on a thread of its own for the whole run too (`ViewportHost.PinGlLibrary`, the "GL Anchor Thread"): with NVIDIA's EGL on Wayland, a TT Lab that had created a project got no new context once no thread had one any more (the prefab pictures' viewports come and go right after creating), every viewport opened after them failing with "eglMakeCurrent failed, reporting an error of EGL_SUCCESS" until TT Lab restarted; a context left not current didn't help. Exceptions on a render thread and GL errors get logged instead of ending the application.
  - Viewports don't use ImGui, its one global context got corrupted by render threads using it at once. Overlays are Avalonia controls over the `Viewport` (`ViewportView`).
  - Until the scene renders the viewport says what it's loading in the game's font (`ViewportViewModel.Loading.cs`, `Controls/GameText`: the package's font with the most glyphs, `PsfGlyphs.OfDefaultFont`, cut out once per font's data; the game's texts spell words in lower case, which its font draws as small capitals, and its capital C, E and Î are controller buttons, so those get the small capital): reading assets (every asset the document's property graph reads, `PropertyGraphTracker.AssetRead`, with a running count), starting the renderer, building the scene (each chunk resource named like the Chunk Resources panel's folders, `ViewportContext.Progress`, with a progress bar). Reports come from any thread, the UI shows the newest (`ReportLoading`).
- Every draw is instanced. Before the passes, each `IInstancedRenderable` (`RenderBatch`, `BillboardSet`) writes its instances' model matrix, color and light set (lit materials, see Scenery lights; a second storage buffer) into `RenderContext.Instances`, a storage buffer the shaders index with `gl_BaseInstance + gl_InstanceID`. A `RenderBatch` draws all meshes of a model with one draw per pass. Meshes that need their own uniforms (`RequiresIndividualDraw`: skins, blend skins, material overrides) get one draw each.
- Go through `RenderContext.State` (`GlStateCache`) for blend, depth, culling, polygon mode and programs, and never read GL state back in the render path, because it stalls the driver. Uniforms set every frame or draw are `KnownUniform`s whose locations get resolved when the program links.
- `PrimitiveRenderer` draws editor visuals immediately each frame: thick anti-aliased lines, boxes, spheres, cones, cylinders, quads and discs, and grids (one quad each, with the lines worked out per pixel), in the `World`, `WorldXRay` (faint where hidden) or `Overlay` (always on top) layer. Submit from `IPrimitiveRenderable.DrawPrimitives` (picked up when registered for rendering) or `Renderer.DrawPrimitives`, both on the render thread.
- Collision has nothing to light it by (its material is unlit, its colors the surfaces'), so its buffers draw with the editor's flat shading (`ModelBuffer.EditorShading`, `TwinMaterialDesc.EditorShading`, `twin_material.editor_shading`): `MainPass.frag` takes the triangle's normal from the position's derivatives (before the alpha test can discard any fragment) and lights it from above and from the eye, whichever way it faces.
- A dynamic scenery model's `BoundingBox` is in its own space (the game's are a few units around the origin while the animation moves the model far away), so the chunk viewport draws each box through its model's current transform (`Rendering/Objects/DynamicSceneryBounds`, `DynamicSceneryMesh.ModelTransform`, the "Dynamic scenery bounds" layer).
- Materials have a viewport (`[SupportsViewport]`, `MaterialData.GetViewportObjects`): a sphere standing on the floor drawn with the material (`Rendering/Objects/MaterialPreview`, `MeshFactory.CreateMaterialPreview`; lit shader types count the vertex colors double and are lit by the default lights, so their sphere's colors are 128 like the game's models), updated in place on the render thread when the material's data changes (`ModelBuffer.ReplaceMaterial` makes its looks again and moves the batch to the passes they draw in), a new sphere only when it turns lit or unlit.
- Triggers' and cameras' boxes are volumes (`LabURI.Volume`), drawn after the scene's transparent surfaces without writing depth, their insides and then their outsides (`VolumePass`, culling front faces and then back faces), so each pixel blends in the same faces whatever order the triangles are in. Their faces are wound counter-clockwise seen from outside, like `PrimitiveMeshes`, which GL renders as front faces (only `FrameCamera` mirrors).
- **Skydomes** (verified in the PAL executable, `Ghidra Stuff/Engine_RE`): a chunk with a sky draws it first instead of clearing the frame (`FUN_001ba350`): the parts of its meshes in their order, at the camera's position (the model matrix is only that translation), into a buffer of half the screen's size (`FUN_001ba488`), then copied over the whole screen two pixels for one with the depth reset (`FUN_001ba6c0`), so the level always draws over it. Every retail sky material is shader type 10 in bucket 0 testing no depth, some blended. The type 10 program (VU1 code 0x2e3ec0) takes its matrices from the 9 quad words 78 past the buffer's base (`3(vi00)`) that only the sky's drawer uploads (`FUN_001c1f90`), never the model's own block (`2(vi00)`, which the level's drawers write): a type 10 material on anything else draws with the last sky's matrix, around the camera at half size in the middle of the screen, and a sky part of another type with whatever object block was left. TT Lab draws every type 10 shader around the camera in one `SkydomePass` (`FollowsCamera` in `MainPass.vert`, `ModelBuffer.PassOf`), in the order of the sky's meshes and parts (`ModelBuffer.DrawOrder`), into a half size buffer blitted over the frame (`Renderer.RenderSkydome`). The frame's alpha isn't shown (`ScreenHorizontalFlip.frag`): GL blends it along with the color, and the alt earth sky's subtracting sun left pixels the window showed through.

### Misc
- **Project tree** (`ProjectManager.BuildProjectTree`/`ExploreFolder`): folders before assets, each in name order (`ResourceTreeElementViewModel.BuildChildren`, `AddNewChild` inserts new rows the same way), the project's `build`, `prefabs` and `profiles` folders hidden (`_hiddenRootDirectories`). `ProjectTreeWatcher` watches the project folder (asset JSON files, directories and the disc's music and video files, not `build`; the data files written under `assets` it hands to hot reloading, one watcher for both: starting one on a whole project takes a fifth of a second and a watch per folder) and, once changes stop for half a second, `SyncProjectTree` on the UI thread adds what appeared (assets loaded from their JSON, folders explored like at opening) and removes what's gone (assets taken out of the `AssetManager` too). Folders are never written as files (`Folder.Serialize` does nothing: a folder's JSON in its own directory made the tree a cycle). A new asset is listed in the folder of the directory its file goes in (`AssetFactory.GetContainingFolder`: a chunk gets a folder of its own, a layout's instance the `<Type>/Layout_<n>` folders under its chunk's, made on disk right away), a layout's instance is only written when its chunk gets saved and is `SerializableAsset.IsUnsaved` until then, and the sync keeps unsaved assets and only takes an asset out of the project when its own file is gone (one listed in another folder than its file's just leaves that folder, `HasFile`). Instances placed in a chunk used to be listed in the chunk's folder, the first sync after saving (or before, when other files changed) took them out of the project, and closing the chunk's tab crashed looking them up (`PrefabLibraryTests.PlacedInstancesStayInTheProjectThroughSavingAndClosing`); `LevelChunk.Dispose` skips a resource the project doesn't have with a warning. The `disc` folders (`FolderMark.Disc`) list `DiscFile` rows, never assets of the project (registered, of no package: their paths go through their folder in the project, `DiscFile.LoadPath`; through the package they threw, and the hot reload, which looks at every asset's data path, failed in every project with a disc folder; `ExternalChangeTests`' project has a music archive): an MH/MB music archive as one node (`Music.mh/mb`) and each PSS video, double clicked or opened from the context menu with its twinstudio tool (`Tools/ExternalTools.Launch`: `tools/twinmusic`, `tools/twinpss` next to the executable, the Tools menu starts them, opens the folder and the releases page). Chunks are only offered and made in the `levels` folder at the root of a package, any package, and the folders under it (`Folder.GetPathInLevels`), where the build finds them (`Project.GetLevelsFolders`: the levels folders of every enabled package of the version the project's package depends on), and a chunk's path is its own in its version of the game (another package's chunk at it is refused, the build writes the first). Packages are only made in the project's own `assets` folder, which offers nothing else (`FolderElementViewModel.ListAssetsToCreate`, `AssetDataFactory.CreatePackageData`): a folder of their own (`AssetFactory.GetContainingFolder`), named as typed, depending on the PS2 package (the Xbox one when only it is enabled) and added to the project package's dependencies; a package's own `assets` folder is a folder like any other. A package's settings tab (right click the package) closes without reading its file back from the wrong path (`Package.LoadPath`).
- **Hot reload** (`EditorsViewModel.ReloadChangedFiles`): data files another program writes under `assets` (`.data`, `.tlm`, `.lab`, `.png`, `.wav`, `.txt`, written, made or renamed over, once the writes stop for half a second) make the editors showing them again. TT Lab's own reads and writes are told apart by the file's length and write time (`AssetFileStamps`, recorded by `AbstractAssetData.Load` after what loading writes itself, and by `Save`), and a file written within 2 seconds of being recorded by its content as well: file systems keep write times to their clock's tick, and on Windows another program writing as many bytes right after TT Lab saved got the same length and time and went unseen. A changed asset counts while it's loaded or a tab shows it: its document reaches it (`GetReferencedAssets`) or its scene drew it (`RenderContext.ReadAssets`: the textures, materials and meshes the render services and `MeshFactory` read, which a chunk's document doesn't reach, `TabbedEditorViewModel.Shows`). Its file is read first in an `AssetDataScope` of its own (`ReadAgain`: the scope reads the asset's data from the file even while an editor has it loaded), and one that doesn't read (a failed write, another kind of model exported over the asset) is warned about and left alone. The tabs showing a changed asset are made again over the data still in memory, only the changed assets let go of with their internal assets (`TabbedEditorViewModel.Unload`/`LoadAgain`): the new document takes over the unsaved changes, the assets they're in, a chunk's override session (`ChunkOverrideSession.Forget` drops the views of what's read again), the particle systems renamed and the history (`DocumentViewModel.Carry`/`TakeOver`, `UndoHistory.Adopt`, steps are kept by path; started over, still dirty when it was, when a step is in what's read again), and the tab keeps a chunk's camera (`ViewportViewModel.KeepView`) and the inspected node, which the viewport selects once its scene has its objects. A tab whose unsaved changes are in a changed asset asks, once for all of them (`ExternalChangeDialogue`): Reload discards them like closing without saving, Keep leaves them and every tab showing what they share as they are, looked at again without asking once an editor is saved or closed. Loading tabs, scenes being built and builds are waited for (`WaitForEditorsToSettle`). `ExternalChangeTests` covers scripts and game objects; a chunk's scenery exported over by Blender (its moved instance, undo, camera and selection kept) and a texture only its scene draws were checked in the app.
- Log with `Log.WriteLine(text, Log.LogType.X)`. Every line is appended and flushed to a session log file straight away, together with unhandled exceptions. The Log panel gets the lines in batches, at most every 100 ms at background priority, the last 500 of them as one edit (`Log.FlushPendingLines`): a dispatcher job and an edit of the panel per line ran ahead of input and rendering, and 2000 lines a second froze the UI for 22 s (`LogPanelTests`). The files live in `%LOCALAPPDATA%\TT Lab\Logs` on Windows and `$XDG_STATE_HOME/tt-lab/logs` (default `~/.local/state`) on Linux, and the last 5 sessions are kept. `Debug`/`Trace` lines only go to the file. An exception escaping the UI thread's work (an event handler, an `async void` method) or a ReactiveUI command nothing watches is logged as an error and TT Lab carries on (`App.LogUnexpected` through `Dispatcher.UIThread.UnhandledException` and `RxApp.DefaultExceptionHandler`, the stack trace in the file): they ended TT Lab and every unsaved edit with it. The tests' application has neither. Avalonia's own log goes to the console (`Program.cs`), from its Debug level in Debug builds and from Warning in Release: Information is two lines for every layout pass, which a Linux desktop puts into the journal (they cost 5-9 µs a pass, about 0.5% of layout time).
- User settings live in the static `Preferences` class, stored in `settings.json` next to the executable. The Project menu's Open Recent lists the last 10 projects opened (`Preferences.RecentProjects`, `ProjectManager.WithRecentlyOpened`), saved as soon as they change. Opening one closes the open project's editors first, like opening one from the dialog.

## Code style

Match the surrounding file. The codebase spans several eras, so consistency within a file matters more than uniformity across files. For new code:

- **Comments**: avoid verbose comments. Only add comments that describe hacks, workarounds, or code whose intent isn't obvious (bit layouts, format quirks, ordering requirements). Don't narrate what the code does and don't add XML doc comments to new members, except in TwinTech public interfaces or files that already document every member.
- **Namespaces**: use file-scoped `namespace X;` in new files. Don't convert existing block-scoped files unless you're rewriting them.
- **Braces/layout**: Allman braces, 4-space indent, braces even for single-statement `if`s. Prefer early-return guard clauses. Put a blank line after a closing block before the next statement.
- **Naming**: PascalCase for types, methods, properties and public/protected members. `_camelCase` for private instance fields. PascalCase for `private static readonly` fields. `UPPER_SNAKE_CASE` for game IDs in `Constants`. Interfaces for game items are `ITwinX`, PS2 implementations are `PS2AnyX`/`PS2X`, and asset data classes are `XData`.
- **Types**: `.editorconfig` doesn't force C# keywords. For binary-format fields and game data (TwinTech items, asset data mirroring game structs) use explicit BCL names (`UInt32`, `Int32`, `UInt16`, `Single`, `Byte`) so widths are obvious. Elsewhere, new code uses keywords (`string`, `bool`, `int`).
- `var` for locals, target-typed `new()`, and collection expressions (`[]`) in TT Lab. Not collection expressions in TwinTech (C# 11).
- Use hex literals for IDs, masks and bit shifts (`_header >> 0xB & 0x1`), and `{id:X}` when formatting IDs.
- `nameof(...)` for property-change notifications and attribute references.
- `Debug.Assert` for internal invariants. Throw exceptions for bad input or game data.
- `using var` for streams, readers and writers.
