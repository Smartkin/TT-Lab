# CLAUDE.md

TT Lab is a modding toolkit/editor for **Crash Twinsanity** (PS2 and Xbox). It unpacks the game's disc files into an editable project of JSON assets, lets you edit them in an Avalonia UI with a 3D OpenGL viewport, and repacks them into game archives/ISO.

## Build & run

```bash
dotnet build "TT Lab.sln"
dotnet run --project "TT Lab/TT Lab.csproj"
```

- Targets .NET 8 (`global.json` rolls forward to newer SDKs).
- The build has around 3.4k pre-existing warnings, so only errors and new warnings in code you touched matter.
- Tests: `dotnet test "TT Lab.Tests/TT Lab.Tests.csproj"` (xUnit) and `python -m unittest discover -s tests` in `TT Lab/BlenderTools`. They never use game data. Build made-up data in the test instead (see `Support/TestAnimations.cs`).
  - `Support/TestProject` opens an empty project with the base packages in a temporary directory. `BuildProjectTree` creates the package folders the way opening a project does. Tests using it must be in `[Collection(ProjectCollection.Name)]`, because the opened project is global (service locator plus CWD); so must tests changing `Preferences` (`PreferencesWindowTests`, `DiscordPresenceTests`, `RecentProjectsTests`: the settings are the process's, and the two setting Rich Presence ran side by side).
  - `TT Lab` exposes its internals to the test project.
  - UI tests use `[AvaloniaFact]` and run in the headless `Support/TestApplication`, which renders with Skia (so bitmaps encode, textures need that) and has the app's `ViewLocator`, Dock theme and view registrations, so real editor panels and tabs can be shown and driven with key and mouse input. Tests creating ReactiveUI objects have to be `[AvaloniaFact]` too, so they run after the application set ReactiveUI's schedulers. The main thread scheduler is `Support/TestMainThreadScheduler`, not `AvaloniaScheduler`: the session resets `Dispatcher.UIThread` between tests, a thread pool thread asking then gets a dispatcher claiming every thread, so a code editor's live check finishing after its test ran on the pool thread, made Avalonia's `MediaContext` on that dispatcher and no later test's window laid out after `Show()` (the Windows CI runner's failures, `taskset -c 0` reproduces them). Wait for views and closed tabs by polling, not with fixed delays. Clicks, `InputHitTest` and `CaptureRenderedFrame` go by what the compositor got last, and a commit waits until the render timer (a dispatcher timer in the headless session) has taken the one before it: a test showing windows right after another test hit nothing in them, so tests that click run `Dispatcher.UIThread.RunJobs()`, `AvaloniaHeadlessPlatform.ForceRenderTimerTick()` and `RunJobs()` again first (`PrefabDragAndSearchTests.Render`), and tests checking a captured frame's pixels poll a few such ticks for it (`FontEditorTests.PagesAreShownTheRightWayUp`: the Windows runner captured the page's background where its picture was).
  - Rendering code that needs a GL context isn't tested, but its math is (`Rendering/`: camera projection, gizmo picking and dragging, splines).
  - Add-on tests import its modules without Blender through the fakes in `tests/fakes.py`.
- CI (`.github/workflows/build.yml`) only runs when started by hand (`workflow_dispatch`, the Actions budget is small). It runs both test suites on Windows and Linux, the C# tests built in Release: what only Debug builds pass on to the tests is missing there (the Simple theme came only with `Avalonia.Diagnostics`, which Release builds keep to TT Lab, and `ToolTipTests` didn't compile until TT Lab referenced it itself), so build the tests with `-c Release` too after using another package's types. A test running 20 minutes is taken for a hang (`dotnet test ... -c Release --blame-hang-timeout 20m --blame-hang-dump-type mini`): its test host is dumped and stopped, its name and the dump go into the uploaded `TestResults` (a run that hung went on until the job's six hours were out without naming a test). It then publishes a framework-dependent build for `win-x64`/`linux-x64` as an artifact. Publishing for a runtime makes a single file (`PublishSingleFile` in `TT Lab.csproj`, symbols embedded in Release, no documentation files): only the native libraries stay next to the executable (bundled ones get extracted elsewhere, where Veldrid's SDL loader doesn't look), with `BlenderTools/dist` and `tools/`. Assemblies have no `Location` there (`EnableSingleFileAnalyzer` warns about it). Nothing is read from next to the executable but `settings.json`, `layout.json`, `tools/` and the add-on: `Media` (shaders, icons, pictures, not its unused fonts) and `Images/SadTransparent.gif` are embedded, read by their paths through `Util/ManifestResourceLoader` (which resolves shaders' relative includes, `ShaderSourceTests`), and TwinTech embeds its `.lab` definitions and three JSON files (`Libraries/EmbeddedFiles`, by file name). `_WINDOWS`/`_LINUX` come from the OS doing the build, so each platform has to be built on its own OS. `scripts/package_addon.py` zips the Blender add-on without the uv environment. `scripts/fetch_tools.py --os Windows|Linux --out publish/tools` downloads the twinstudio tools (twinmusic, twinpss: https://github.com/Smartkin/twinstudio/releases, zips named `<tool>-windows-latest.zip`/`<tool>-ubuntu-latest.zip`, each a bare executable with a `resources/` folder) into `tools/<tool>/` next to the published build, which is where `Tools/ExternalTools` looks for them (`AppContext.BaseDirectory/tools`; a local `TT Lab/tools/twinmusic` and `twinpss` are git-ignored and copied to the output, only those: the repository ignores case, and ignoring `TT Lab/tools/` hid the sources in `TT Lab/Tools/`, which were never committed). Tools > Install the tools does the same from inside TT Lab (`ExternalTools.InstallAsync`: the latest release's zip for this system, unpacked into the tool's folder in place of what's there, the executable bit set). The tools take no file on their command line, so opening a disc file starts the tool with the path as an argument anyway and on the clipboard.
- Platform-specific code is gated by `_WINDOWS` / `_LINUX` defines set in `TT Lab.csproj`. Native libraries (`PS2ImageMaker`) in `TT Lab/Libraries/Native/{Windows,Linux}` are copied into `runtimes/*/native` by the `CopyNativeLibs` target (an absolute `-o` folder included, they used to go into a folder of that name inside the project). When publishing for a runtime, the `PublishNativeLibs` target copies them next to the executable instead. `PS2ImageMaker`'s libraries are its tt-lab-2.0.0 branch's (264a41e; the Linux one a Release build needing GLIBC_2.33 and GLIBCXX_3.4.22 at most, the Windows one a static MinGW build of 4eb6edc needing only KERNEL32 and the UCRT, until its CI's MSVC build replaces it): the builds before ran away when an image's sector count was a multiple of 16, writing zero sectors past its end until the memory ran out (see Build).
- The app requires OpenGL 4.6 (see `Program.cs`).

## TwinTech (game formats)

- Names and descriptions follow what the decompilation (`twinsanity-reversed`, `include/game/*.h`) found a value does; values it shows are never read keep `Unused`/`Leftover` names.
- `TwinsanityInterchange/Interfaces`: every game item is an `ITwinItem : ITwinSerializable`, implementing `Read(BinaryReader, int length)`, `Write(BinaryWriter)`, `GetLength()` and `Compile()`. `GetLength()` must exactly match what `Write` emits. Containers implement `ITwinSection`.
- `Interfaces/Items/**` defines platform-agnostic `ITwin*` interfaces (for example `ITwinTrigger`). `Implementations/PS2/**` (`PS2Any*`) and `Implementations/Xbox/**` implement them. `Implementations/Base/BaseTwinItem` and `BaseTwinSection` hold the shared logic. A section maps child item IDs to concrete types via `idToClassDictionary`, and anything unmapped falls back to a raw `BaseTwinItem`.
- `Common/` holds shared structs (`TwinTrigger`, `Vector3/4`, and so on) that implement `ITwinSerializable`.
- `Enumerations/Constants.cs` holds section and item IDs (`LEVEL_CODE_SECTION`, `LAYOUT_TRIGGERS_SECTION`, ...). `Enums.cs` holds game enums.
- `PS2Hardware/` contains the VIF/GIF/DMA packet code for PS2 model data. `TwinVIFCompiler` and `TwinSkinPacketDecoder` pack and read models, skins and blend skins exactly the way the game does, which `VifCodecTests` checks. A packet goes out with one DMA tag whose size field holds 65535 quad words: `TwinVifPacket.Writer.Finish` refuses more (the overflow once sent a fifth of a 35k vertex skin and the game hung waiting for the rest), so `PS2ItemFactory` spreads a part's batches over several sub skins or sub models of the same material when they'd go past `TwinVIFCompiler.MaxPacketBytes` (`SkinBatchBytes`/`RigidBatchBytes` are what the compiler writes per batch). The game draws every model of a blend skin's sub blend with the first model's shape factors (`FUN_001c1ac0`, the scale of the shapes' byte offsets), which every retail sub blend's models share, so `PS2ItemFactory.GetFittingBlendShape` fits one scale over all of a part's batches. `Libraries/` contains ADPCM, swizzling, hashing, quantization and the Xbox's DXT5 codec (`Dxt5`). Names and paths in the game's files are a byte per character (`Libraries/GameText`, what every item's names, chunk links' and archive records' paths go through, characters past Latin-1 written as '?'): they were read and written in the reader's and writer's encoding, the build's UTF-8, and a name with a character past ASCII (a particle system named in Cyrillic) was longer than its item said. A picture of more than 256 colors made into a palette texture (`PS2AnyTexture.FromBitmap`) gets its palette from `ImageQuantizer`: a median cut of every mip level's colors (the GS draws every level with the one palette) that splits the group with the most error where it drops most, refined by k-means, colors told apart with the eye's weights (green most, blue least, alpha like green); the pixels get Floyd-Steinberg diffusion of their color at 0.8 (never of alpha, cut-outs keep their edges, see-through pixels pass none on) and its mips average the picture (taking every other index aliased). Pictures of 256 colors or fewer keep their exact palette and their mips every other index, so the game's textures still come back byte-identical (`TextureTests`).
- **Xbox** (`Implementations/Xbox/**`): every file of the Xbox disc TwinTech knows reads and writes back byte-identical (`XboxFormatTests` covers each quirk with made-up data).
  - Most Xbox items subclass the PS2 ones. The Xbox's behaviour classes only swap the command table (`XboxBehaviourGraph.GetAgentLabDefs`, some commands take more arguments), the PS2 classes have the virtual hooks (`Defs`, `GetSize`, `Create*`) for it.
  - Models, skins and blend skins are plain vertexes drawn as triangle strips, one strip per group (`XboxSubModel`, `XboxSkinnedGeometry`). Normals are packed 11:11:10 signed fractions. A skinned vertex refers to up to 3 joints of its strip's palette by vertex shader register (16 + 4 per palette slot). Unused slots hold leftovers of the tools' memory (registers past the palette, weights near 0) which are kept for writing but read as joint 0 with no weight, like the PS2 version's. `ITwinStripGroups` marks Xbox geometry.
  - The Xbox's tools joined strips without keeping their triangles facing one way, the game draws them without culling.
  - Textures are DXT5 with only the largest mip (level textures) or plain BGRA (menus, fonts). The first header word is the length of the PS2 texture they were made from, and textures embedded in PTC files work out their length from it.
  - Fonts store every character's box as fractions of its page. Sounds are 16 bit PCM. Unknown header bits (dynamic scenery, trigger behaviours, the order of a scenery's lights) are kept as read, several of them only the Xbox version sets.
- A PS2 chunk's sound section (`PS2AnySoundsSection`, the front end's `PS2Frontend` too) is read by each header's stored offset, where the game reads the samples, and the stereo sounds' right halves after all samples in the order of their offsets, the way `PreprocessWrite` lays them out: TT Lab's builds lay the samples out before the code section sorts the records by ID, and reading them in the records' order garbled a project made of a TT Lab build. Offsets that don't fit the samples are taken one after the other in the records' order; every retail section stores the offsets that order gives (`SoundSectionTests`).
- PS2 textures (`PS2AnyTexture.FromBitmap`) get the game's layouts. The header has the texture's size twice, in blocks of 64 of the 32 bit pixels it uploads, which is what the game reserves GS memory by; 32 bit textures upload their whole image and textures without mips have their palette where the game's have it (`UnmippedClutPointers`). A wrong size made textures overwrite each other or go missing in game. The rest of the header is what the tools had in memory (`TwinTextureLeftovers`: the signature's low half, a slot number unique in each chunk, reserved words and 32 bytes after the header), worked out from every texture of the game. It's written back as read (`ITwinTexture.Leftovers`, kept in `Texture.Leftovers`). The PSM files' icons have zeros where chunk textures have an address of the tools' memory, textures made in TT Lab get the chunks' values.
- Behaviour starters get their script ID and their first assigner the ID one past their graph's (`Compile(graph)`, `Compile()` is `Compile(ID + 1)`), like every starter of the game. A starter's ID is the one before its graph's but for AltEarth's 0xBFE of COM_GENERIC_FURNITURE_WAKE_CONTACT_RESPONSE (0xBED) and labext's 0xF6C of COM_DOOR_CORTEX_LAB_DEFAULT (0xF65), which their chunks' objects name: the graph keeps it in `BehaviourGraph.StarterId` (JSON, set only for those two, dropped by a copy of another ID) and everything writing a starter's ID (slots, trigger messages, objects' lists, spawn scripts, templates) writes `BehaviourGraph.StarterIdOf` (the game's while the graph is built with its own ID, else the one before it); every starter was built at its graph's ID less one. A build's compile of a graph gives its starter its ID and graph before the chunks share it (`BehaviourGraphData.Compile`) and `AddStarter` only puts it into a chunk without its ID: set by every chunk putting it in, a chunk written meanwhile could catch 0xBFE's assigner running 0xC00. With a starter the `[Priority]` attribute is the starter's, `[GraphPriority(n)]` holds the graph's own priority (0, 1 or 3).
- `Implementations/PS2/PS2SaveIcon` is the PS2 memory card icon the game's saves get (`Startup\Crash.ico`, Uka Uka's mask; the Xbox disc has none), in ps2iconsys' layout, which accounts for every byte of the game's: a header (shape count, texture type), triangles of 3 corners each with a position per shape and a normal (X, Y, Z in 4096ths with Y going down, and a word the tools wrote 0 into), a UV in 4096ths and an RGBA color, the animation (a header, then every shape's keys of a time and a weight) and a 128x128 texture of 16 bit texels (5 bits of red, green, blue from the lowest, the alpha bit), run length encoded when the texture type's bit 3 is set (a count below 0xFF00 repeats the next texel, a larger one is 65536 minus it texels as they are; the encoding read is written back while it still decodes to the texels). It reads and writes back byte for byte (`SaveIconFormatTests`).
- Animations (both versions) count channels in their flags: every joint its amount (9, or a facial joint's shapes) and how many are animated (`animated << 4 | static`), the header the amount per joint. `Write` works them out, so animations made in Blender get them right.
- `AgentLab/` is the compiler/decompiler for the behaviour scripting language (AI graphs, starters, command sequences). The pipeline is `AgentLabLexer` → `AgentLabParser` (AST in `AbstractSyntaxTree/`) → `AgentLabSymbolTableBuilder` → `Analyzers/` → `AgentLabCompilerNodeVisitor`, which emits `ITwinAgentLab` objects. A word takes the token type it names (that makes the keywords) but the end of the script's: `eof` is an identifier (the parser stopped at it and left out what followed), which `IsReservedKeyword` still takes for reserved, so names spelled like it stay quoted. A number that doesn't read (`99999999999`, `1.2.3`, `5-3`: a `-` goes into a number after its digits) is an `Undefined` token of its text (`AgentLabToken.IsInvalidNumber`), which the parser reports as "Invalid number ..." wherever it stops at it; it was dropped for what came after it. Values nest 256 deep at most (`AgentLabParser.MostNesting`: parentheses, signs, tagged literals, array indexes and the levels of a chain of operations), an error at the token past it: the symbol pass and the compiler walk them recursively, and 100000 parentheses ran the live check's thread out of stack and ended TT Lab. `Analyzers/ConstDeclarationOrderAnalyzer` orders a behaviour's consts so each comes after the consts its value names (Kahn's, the first written first), and the ones going back to themselves (Tarjan's, no recursion) are an error at the first of them ("Const X's value depends on itself"): it never ended for up to three consts, which hung the editor's live check and the build. Operations group from the left (`10 - 3 - 2` was 8) and compile to their values wherever a value goes (`AgentLabValues.Apply`: integers stay 32 bits, past them and a division of integers by zero are errors at the operator, a float on either side makes a float, strings add up): they had no value in the compiler, and a packet's data of one got its byte without its float (a packet's data that isn't a number is an error now). A condition written without its parameter compiles as 0, a parameter that isn't an integer of 0 to 32767 is an error at it. The check doesn't work values out, so these are the compile's errors (`AgentLabCompileTests`). A control packet's data are `ControlPacketData`'s names (`TumbleData`, `SpinData`, `TwistData`, which the decompiler writes; the symbol table had Tumble, Spin and Twist, which failed the compile), anything else in a data block is the check's error, the old three naming the data they were; completion offers only those names there. Visitors register handlers with `Visitors.Add(typeof(Node), VisitX)`. Reference resolution is abstracted behind `Resolvers/Interfaces`, which TT Lab implements in `TT Lab/Assets/Code/Resolvers`.
  - `ActionDefinitions{Ps2,Xbox}.lab` are **generated** by `LabActionGenerator.py` (run it in `TwinTech/`, it writes both) from `AgentLabDefs{PS2,Xbox}.json`. Edit the JSON and regenerate instead of hand-editing them. A command's `Arguments` are its dword types (`single`, `int32`, `hex`, or the tagged `tfloat`/`tint`/`tangle`), `ArgumentNames` its parameter names, `ArgumentFields` (by argument index) the fields of the dwords the game packs (flags, bytes, halfwords: `Name`, `Bit`, `Width`, `Type` `bool`/`int`/`sint`, together covering all 32 bits) and `Aliases` the names the command went by before, which old scripts still compile under (`AUnknown_N`, and the earlier name of a renamed command). `ConditionDefinitions.lab` is hand-maintained, one line per condition index, with the old names as aliases. Every command and every condition of the PAL executable has a name now; the ones found by reverse engineering (`Ghidra Stuff/AgentLab_RE`, `data/decisions.json` holds each with its confidence and what the code does) are mostly educated guesses, the ones the user had are kept.
  - Packed parameters are declared as `name { int slotCount : 4, bool blendTimeGiven, sint slotA : 16, ... }` (fields from bit 0 up, widths adding up to 32) and written in scripts as `{slotCount = 1, blendTimeGiven = true}` (any order, the fields left out are 0, `{}` for none; a plain int or hex literal is still taken for the whole dword). The decompiler prints the fields that aren't 0 in declaration order, `unused*` ones in hex, so scripts stay byte exact. The symbol pass checks the names, types and the range of literal values, the compiler packs them (`PackFields`), `PackedArgument.Format` unpacks them and completion suggests the fields inside the braces (`AgentLabCompletionKind.Field`).
  - A state's child behaviour is a name (`state S(COM_X)`, `BehaviourReferenceNode`) or a string for what only the resolver understands (`IStateGraphResolver`: a URI in TT Lab, an index in the default one). The decompiler writes bare what lexes as an identifier and isn't a keyword or a token type's name (`AgentLabLexer.IsReservedKeyword`), the rest quoted. `AgentLabCompletion.GetBehaviourReference` finds the reference at an offset, name or string. A state can run one of the object's behaviour slots instead (`[UseObjectSlot(...)]`, `ITwinBehaviourState.ObjectBehaviourSlots`, see Behaviour slots): slots 9 and 10 are `Slot_9` and `OnGettingThrownAttacked`, their old names `OnPhysicsCollision` and `OnUnknownCollision` still compile (`ObjectSlotNames`, completion offers the new ones), and hovering a slot's name says what starts it.
  - What the game does with the bytecode (verified in the PAL executable): a body passes when its condition's result is above the threshold (`if X(p) > t`, `<` inverts), and among the passing bodies the largest `(result - threshold) * weight` runs, `weight` being 1/threshold unless written. `window` (the condition's first float) is a time window in seconds only the event conditions read, never a check interval. `else` is the fallback body (condition 2) and `completion` the first body of a state with bit 10, run when its control packet or child behaviour finishes (condition 0, never evaluated). `restart = true;` (body bit 8) makes a jump to the same state re-enter it. `[Interrupting]` (state bit 11) keeps the state's conditions evaluated while its child behaviour runs. State bits 5-9 (small leftover numbers, dropped: old scripts' `[Unknown(n)]` is accepted and ignored) and 13, and assigner locality/status/preference, are never read. An assigner's `RefListIndex` is the instance's RefListIndex a `GLOBAL_AGENT` receiver is, not an object. Tagged arguments (`TaggedValue`) are a literal of the parameter's type or `Prop(n)`, an instance property index; `Raw(0x...)` keeps bits as they are and hex literals always do. Many commands take a "designator" byte: a starter receiver index below 0xDE, or 0xFB the focus object, 0xF8/0xF7 AgentRef1/2, 0xF2 the player, 0xF4 the originator, 0xF6/0xFC the focus position, 0xFD/0xFE the next/current key, 0xFF none. The old spellings (`NonBlocking`, `interval`, `unknown`, `>=`, `GlobalObjectId = "uri"`) still compile, projects store behaviours as script text. Floats print so they lex as floats and reproduce their bits (`-0.0`, `2.0`), and bits no literal reproduces (NaN, infinities, denormal leftovers, `int.MinValue`) print in hex or `Raw(0x...)`; control packet data is written in float slot order. Every script of the PAL archive round-trips byte-identically but for those bits (`Ghidra Stuff/AgentLab_RE/scripts/harness`, modes `roundtrip`, `context`, `sample` and `locate`).

## TT Lab (editor)

### Project lifecycle (`Project/Project.cs`, `ProjectManager.cs`)
- **Create**: copy the disc contents (`CopyDiscContents`: into the project's `disc/ps2` and `disc/xbox` by their place on the disc; the PS2 disc's folders went to the file system's root when its folder was given without a separator at its end), then `CreateBasePackages()` (Base, Global PS2/Xbox, PS2/Xbox packages), then `UnpackAssetsPS2()` and `UnpackAssetsXbox()`. Both go through `UnpackAssets`, which parses the chunks and runs `AssetResolvers/*` over each of them through `ResolverManager.PerformResolve`. The resolvers turn `ITwinItem`s into `IAsset`s, OGIs, textures, sounds, skydomes, behaviour command sequences, instance templates and OGIs' animations named after twinsanity-editor's names of their IDs (TwinTech's `Enumerations/DefaultHashes`, the tables of its `DefaultHashes.cs` for those kinds as it has them, folders like `Crates/` included; `RetailNames` leaves the folders out of the asset's name, which is its file's, but where two names of a kind would be the same; models, skins and blend skins are parts of OGIs, and the textures whose IDs the game reuses are keyed by a hash the editor never computes), the rest and IDs without a name the way they were (objects, behaviours and collision surfaces keep the game's own names, which the editor's are copies of, but for 5 IDs the game reuses for other scripts). What an item names by IDs is resolved in every chunk whatever an earlier chunk had the same of (`AssetResolver.ResolveParts`: objects their OGIs, OGIs their skins and rigid models, those and meshes their models and materials, materials their textures, LODs their meshes; `Resolved` tells a resolver which asset an item of the chunk is, and a part a chunk names without having it is skipped with a warning naming the chunk, its kind and ID, what names it linking another chunk's of the ID): a chunk whose object, OGI or material was the same as an earlier chunk's never had its textures read, and 61 PAL chunk files (58 Xbox) built with another chunk's picture of a reused texture ID. The game reuses three graph IDs for other scripts in other chunks (0xBED, 0xEF3, 0xF65, the later chunks' script a variant), so `AssetResolvers/UnpackedScripts` reads every chunk's starters with their graphs' names in the parallel read and keeps each chunk's `ChunkScripts` as it's resolved: a graph gets its chunk's starter, else another chunk's of the same graph (ID and name), what a chunk's objects name by a graph's or a starter's ID (`GameObjectData.GraphOf`, `GraphsWithoutStarter` by `ChunkScripts.StarterIdOf`) and what its graphs run as a state's child (`ChunkScripts.GraphNamed`, by name when that finds it, else by URI) are the chunk's own, and instances' spawn scripts and templates' starters name their own chunk's graph of the ID after the starter (its variant first) while the unpack found the starter with it, else the graph whose starter the unpack found with the ID (`BehaviourGraph.GraphOfStarter`); objects linked the first chunk's graph of an ID, every graph of an ID got the first chunk's starter and the starters of other IDs were lost (12 PS2 and 17 Xbox chunks ran another level's script or none), and docamok3's bear ran l03stock's platform in a project made of a disc TT Lab built. The PS2 version's files come from its `.BD/.BH` archive (`DiscPath.Find`: PAL's Crash6/Crash.BD, NTSC's CRASH6/CRASH.BD, any case; a `ProjectException` names a folder without them, Linux found neither NTSC's nor lowercase names), the Xbox's are loose on the disc (`GetXboxDiscFiles` takes the Startup, Levels, Extras and Language folders whatever their case, in that order, a folder's files by their paths with '/', like the PS2 archive has them: the chunk an item is first found in has its asset and the default chunk shares items with levels; the paths name the folders the game's way, STARTUP\x is Startup\x, and Linux skipped a folder of another case without a word). `oldFileOrder` (`GetXboxDiscFiles`, `IProject.UnpackAssetsXbox`) is 1.1.0's order, every folder's files sorted together (the levels first, the default chunk's shared graphs and objects in the XBOX package), which repairing a project 1.1.0 made needs (`DiscFoldersTests`). Creating writes the project's repair marker, neither version needs the repair (see Repairing projects 1.1.0 created). Unpacking the Xbox disc enables its packages, a project made without the PS2 disc has its PS2 packages off (`UnpackAssetsPS2`, and `UnpackRetailAssets` for a version not given): they were on, empty, and new packages were made on them. The project's `UUID` is made once, with the project (it had no setter, so it was never read back and every write of the project file made a new one).
- **Open** (`Project.Deserialize`): every package folder's asset JSON files are read in parallel (`AssetDeserializerFactory.GetAssets`). A second file of an asset's URI (a file manager's copy) is left out with a warning, the first by path kept, and a file that doesn't read fails the opening with its path (`ProjectException`); a copy used to hang the opening for good, the lock every file waited for held by the one that threw. Failures are reported in Debug builds as well, they went nowhere and the opening looked stuck. A project opened from another folder than the one it was made in (copied, moved, cloned under another name) is where it's opened (`Project.ReadProjectFile`: `Location`, the project file only has the folder it was made in, and disc folders that were in that folder are rebased, whichever system made it: the paths are split on both separators and a Windows path's folders compared without case, Linux took a Windows path for the name of one file and a project made on Windows lost its disc folders there, `RetailAssetsTests`); it used to read and write everything where it was made.
- **Folders named in another case** (`Util/DirectoryCase`): assets find their files by their URIs, and the global packages' URIs name the startup folder `Startup` (the startup folder's files, the disc's case) and `startup` (the default chunk and its assets, the chunk's lower case path). Windows had one folder of both, named after whichever got written first, and on Linux the files of the other weren't found. An asset's path (`SerializableAsset.LoadPath`, so `FullPath` and `FullDataPath`) takes the name of the directory there named alike where its own isn't there, exact names first (projects made on Linux before have one of each), each directory asked of the file system once (a check per path asked took 276 ms over 120k assets) and forgotten when the open project changes. The directories assets are written to are looked up and made under one lock (`DirectoryCase.Create`): written in parallel there was a folder of each name, and an asset's data could go into one and its metadata into the other. ### Assets (`Assets/`, `AssetData/`)
- `IAsset` / `SerializableAsset` is an asset's metadata (ID, URI, package, references, variation). It is serialized to `<Name>.json` with Newtonsoft (`MemberSerialization.OptIn`, `[JsonProperty(Required = ...)]`).
- `AbstractAssetData` subclasses hold the payload, stored in `<Name>.data` (JSON). Data is lazy: `asset.GetData<T>()` loads it, and `Serialize(SaveData)` saves and then **disposes** it unless `PreserveData` is passed.
- Files are written from content made before they're opened (`TlmFile.Save`, `AbstractAssetData.SaveInternal`, the metadata JSON of assets, packages, chunks and the project): opening them first emptied them when making the content threw, and saving a scenery with a NaN typed into its bounds left its model file empty, unreadable from then on. A model file's JSON can't hold NaN or infinities, `TlmFile` names the value's JSON path when it gets one.
- A new asset type usually needs:
  - an `Assets/<Category>/X.cs` class with `Section`, `IconPath` and `GetData()`, which recreates the data when `!IsLoaded || Disposed`;
  - an `AssetData/<Category>/XData.cs` class with a `[JsonConstructor] internal XData() : base(null)` ctor, an `Import(...)` that reads from `GetTwinItem<ITwinX>()`, and an `Export(ITwinItemFactory)`;
  - a resolver in `AssetResolvers/` and a factory method in `ITwinItemFactory`/`PS2ItemFactory`/`XboxItemFactory`.
- **Data lifetime**:
  - Open editors own the data they use: a document's property graph loads every linked asset's data, and `Save()` keeps it loaded (`PreserveData`).
  - When an editor closes, `EditorsViewModel.ReleaseUnusedAssetData` calls `UnloadData()` on every asset no open editor references (`TabbedEditorViewModel.GetReferencedAssets`). `UnloadData()` detaches without disposing, because renderers may still hold the data.
  - Closing a tab with nothing to save leaves its asset's data alone, and discarding changes disposes it only when no other open editor uses the asset, else just detaches it (`TabbedEditorViewModel.DiscardData`; a discarded chunk's resources always go back): a chunk's view of a behaviour, model, picture or sound shares the asset's data object, and the behaviour's own tab closing disposed it, which emptied the script the chunk's inspector showed (`BehaviourGraphData.Dispose` clears `Graph`).
  - Internal assets (`IsInternal`) are never serialized. Loading an owner's data recreates them, so any code creating one must set `InternalOwner` to the asset whose data creates it; `AssetManager.RemoveOrphanedInternalAssets` drops them once their owner isn't loaded.
  - Project creation removes all internal assets once a disc's assets are written.
  - Assets never saved (`IsUnsaved`: a layout's instances until their chunk gets saved) keep their data, there's no file to load it back from. When a scene's tab closes, the instances made for its chunk that it no longer lists (their placing undone, the chunk closed without saving) leave the project (`AssetDeletion.ForgetUnsaved`): they stayed in the project tree and couldn't be opened. Saving a chunk deletes the files of the layout instances of the chunk it no longer lists (`LevelChunk.HasTakenOut`: deleted in the scene or the Chunk Resources panel, or by an earlier TT Lab, whose saves left them and the project opened again had them back, holding their IDs) and keeps them unsaved with their data (`SerializableAsset.DeleteFilesKeepingData`), so undoing the deletion puts them back for the next save and closing the tab forgets them; the document doesn't save one it edited before (`DocumentViewModel.Save`, `ChunkTakeOutUiTests`). Every layout instance of a project made of the discs is listed by its chunk (checked on the user's PS2 project, 23,429 of them, 2026-10-28). A tab whose data fails to load logs why and closes, it stayed loading for good.
- **Deletion** (`Assets/AssetDeletion.cs`): every asset referencing a deleted one is fixed by `DeletedReferenceFixer`, which walks the data by reflection and follows each `LabURI` member's `[OnReferenceDeleted]` policy: replace with a placeholder from `PlaceholderAssets` (the default), clear, or remove from the list. Annotate new `LabURI` members whose placeholder wouldn't make sense. A command sequence's pack aliases (the URIs objects' slots name its packs by) are deleted with it (`AssetDeletion.PackAliasesOf`, `AssetManager.RemoveUri`): what links to them is fixed like a link to the sequence, the slots emptied; they stayed registered and the objects failed to build. The placeholder texture is boat guy (`MiscUtils.BoatGuyPath`, `Media/boat_guy.png`, 128x128), the picture the viewport draws for parts without a material, in the layout textures TT Lab makes get (`Texture.UseGameLayout`: a palette and mips for the sizes the game's tools laid out, every color otherwise).
- **Textures** are PNGs that go through Skia unpremultiplied (`TextureData.FromPng`, `GetPngBytes`); Avalonia's bitmaps premultiply what they load and save and lose the color of transparent pixels, so `TextureData` keeps the exact pixels and only shows them through its `Bitmap`. `Texture.ReservesMemory` keeps the header's second size at 0 for Crash's textures every chunk has. The texture's editor (`TextureViewModel`) shows what building makes of the picture level by level: the item `TextureData.Build` makes with the asset's settings, decoded (`ITwinTexture.DecodeLevels`, `TextureViewModel.Levels`, off the UI thread and made again when the picture, the texture function or the mipmaps switch change), with a line saying how (more than 256 colors quantized into the palette, every color kept, the Xbox's DXT5), its mips (the PS2 version draws them in the distance) picked on a slider and drawn as big as the picture a pixel a block, and a check box for the picture as it's stored. A palette texture of a size the game's tools never laid out is built as a 32 bit texture without mips (`PS2AnyTexture.FromBitmap`, `HasPaletteLayout`), it threw. Replace (and a sound's) sets the data through the data's `[custom_editor]` node, which sets its parent's value (`SetsParent`): it set the asset's `AssetData` property on the data itself and threw "Object does not match target type" for every picture (`TextureEditorTests`).
- Shader vectors (`LeftoverVector`, `ShaderColor`, `UvScrollSpeed`) often hold leftover bytes that are NaN as floats (every UI shader has them), and Newtonsoft would write them all as the same NaN, so `LabShader` stores their bits (`BitsVector4Converter`). What the PAL executable does with a shader's other values (`Ghidra Stuff/Engine_RE`): `LeftoverVector` is bits of the tools' strings, only compared when equal shaders get merged; only `ShaderColor.X`'s integer part reaches the VU1 program (0, the UI's materials 1); `UnusedValue` (the byte after the depth test, 4 or the UI's 6) and `UnusedFlag` are never read; `AlphaCorrectionValue` is the settings' "no FBA" bit (56, `SettingNoFba`, the GS gets FBA = bit ^ 1): on, the pixels keep their alpha, off sets its top bit, which keeps the characters' shadows off them (see Character shadows); `AntiAliasing` is the GS's PRMODE AA1; `AnimationDrivesColor` makes the animation's color track set `ShaderColor` every frame. A material's `DmaChainIndex` is which of the game's 28 render buckets its draws go into, drawn in bucket order: 0 skydomes, 2 opaque scenery and objects, 3 opaque global objects, 6-19 alpha-blended, 20 decals and layered materials, 22 particles, 24 the UI, 26 fonts. A bucket has no GS state of its own: every material sends its shaders' PRMODE, FBA, ZBUF (with the depth mask), ALPHA, TEST (the depth test always on), TEX1 and CLAMP with every draw (`SetShaderSettings`). What's fixed is what the game's code puts in (`RenderBuckets`): the frame's setup and clear at the head of 0 (`FUN_0019f958`), the debug drawing in 4 (off in retail), the characters' shadows in 21 (`FUN_001f1a10`, see Character shadows), the particle pages' shaders in 22 (the particle code makes them, whatever the page material says), the Distortion particles in 23 and the movies in 27. The material's first 8 bytes (`ActivatedShaders`, a bit per shader type) are the key of the VU1 programs its bucket has loaded (`RenderMaterial`): the same key as the last material drawn in the bucket skips loading the shaders' programs and 1 never loads them, so `MaterialData.Export` writes `DeriveActivatedShaders` (the bits of the shaders' types, what all 10487 Xbox and every PS2 material have). The inspector shows the types the material's shaders have, following them (`ActivatedShadersFieldViewModel`), not the stored bits: only building writes those, and `AppliedShaders.UnlitBillboard` is `StandardUnlit`'s bit, a flags editor ticked both. TwinTech reads every shader type the game's reader does (the decomp's shaderclasses.cpp): 0x18 `ScreenCopy` (one float, the Distortion particles' shader) and 0x1C `WaveDeformation` (a speed and an amplitude, the decomp's WaveShader) had no members and were read without their values, the rest of the shader from the wrong place; no retail material has them, and their applied shaders bits are ones no other type has (0x20000, 0x100000), the game only compares the keys (`ShaderTypeTests`). The material reader's factory makes neither (the decomp's `MakeShader`, `ReadMaterialShaders` then reads through nothing), so a material with one crashes the game: the particle code makes its own screen copies. Every shader type's `[Description]` says what it draws (the type dropdown's choices' and the activated shaders' rows' tooltips, `ShaderTypeItem.Hint`); the PS2 materials of the game only use types 1, 2, 4, 10-13, 15, 16, 18, 19, 21-23, 26 and 27. The alpha presets (`TwinShader.AlphaBlendPresets`, `G_AlphaRegPresets` filled by `FUN_001daa68`) are 0 Mix (Cs - Cd)·As + Cd, 1 Add Cs·As + Cd, 2 Sub Cd - Cs·As, 3 Brighten Cd·As + Cd, 4 Darken Cd - Cd·As, 5 Scale Cd·As, and zeros past them on PS2 (Replace: the source as it is); the blended retail materials only use 0-2. `Rendering/GsBlending` turns them into GL's blend state for materials and particles. Shader animations (`TwinShaderAnimation`: six tracks U, V, R, G, B, A in 1/4096ths, static or per frame, looping at the header's frames per second, `AnimateShader` 0x297260) still run in retail: the `FromAnimation` scroll modes take the U and V tracks as the UV offset and `AnimationDrivesColor` the color. TT Lab edits them on a timeline in the material's inspector (`ShaderAnimationEditorViewModel`, `Controls/ShaderAnimationTimeline`: a lane per track with its keys, the selected track's curve whose keys drag up and down (a static track's line as a whole), a row per track to make it animated or static and type its value at the playhead, frames put in as copies and taken out, the frames per second (no playback of its own, the material's preview plays it) and switches for what the shader takes from it: `MovesU`/`MovesV` set its X/Y scroll settings to `FromAnimation`, `DrivesColor` its 'animation drives color', one step each; the tracks it doesn't take are gray and read-only until their switch is on: their rows disabled with a tooltip naming the switch, their lanes and curve gray and their keys not dragged, `TimelineTrack.Used`). Every edit replaces the shader's animation with an edited copy made through the game's bytes (`ShaderAnimationTracks`: values where the game reads them, from the first settings' indexes, and the frame count the game times by following the frames while it was theirs), so leftovers stay and a drag is one step; the TwinTech classes have no nodes of their own. An animated track's values are each frame's `AnimatedTransformation.Transforms`, which has a setter for TT Lab's JSON: asset data is read replacing the lists it has, a list it can't set was passed over and a material read back had its animated tracks without values (`ShaderAnimationTracksTests`). The viewport plays their U and V tracks (`ShaderAnimationSampler` samples them at the render context's `Time`, `TwinMaterial` adds them to the scrolls' `uv_offset`, `ShaderScroll`). The color track goes into the shader's color, which no VU1 program but the shadows' volumes' reads (the shader record's second quadword), so the viewport doesn't tint by it (it did); no retail material has an animation. **Cloth deformation** (types 0x17 `UnlitClothDeformation`: `IntParam` mode, `FloatParam` speed and one amplitude; 0x1A `UnlitClothDeformation2`: mode, speed, an amplitude per axis, `ReadPrecompShaderType_0x17`/`_0x1A`): the game keeps 16 rows of 3 phases, each starting at a random angle in [0, π), and every frame (`FUN_001d1cf0`) moves them all by speed × time × 2π (mode 2: × time, wrapped past 10π), hands VU1 sin of each (modes 1 and 2 cos, mode 2 times cos of a second random set sped up 2, 2.3 and 2 times) as 16 quad words next to the amplitudes (`FUN_001d1948`). The VU1 programs (0x21 and 0x1E, disassembled in `Ghidra Stuff/Engine_RE/VU1`, `vudis.py` is the disassembler) move every vertex by the amplitudes times a wave per axis whose row is the low 4 bits of the float bits of the coordinate × 0.000373 (`MTIR` of the scaled position): a hash of the position, so vertexes at the same spot move together and nothing tears. `MainPass.vert` (`ClothOffset`) does the same with `floatBitsToInt` and fixed pseudo-random phases (`twin_material.deform_mode/deform_speed/deform_amplitude`). The **environment maps** (types 0x16 and 0x0C, VU1 programs 0x1D and 0x14) are no sphere maps: per vertex H = normalize(eye − P) + N, d = normalize(C(H)) with C the object's clip matrix's 3×3 (model × view × projection: the view's axes scaled by cot(fov/2)/aspect, cot(fov/2) and about 1; the follow camera's lens is `g_DefaultFov`, 45°, which most of the game's cameras keep, on the PAL screen's 4:3), and the picture is read at (0.5 + 0.5 d.x, 0.5 − 0.5 d.y) clamped, plus the material's scroll, the mesh's UVs unused: a "matcap" that turns with the view. The object block `SetRigidModelRenderDMA` (0x19bd38) writes is a header (13 basic quad words), the screen matrix (1-4), the lights transposed (5-7), their colors (9-11) and the ambient (12), then from the header's basic size the object's clip matrix (written for every shader that needs the eye), the guard band, the eye and the "up" point: what 0x1D reads at the header's offset is the clip matrix, not the lights (a VU1 emulation, `Ghidra Stuff/Engine_RE/VU1/research_2026-10-08`, matched the clip matrix to 1e-7 and missed with the lights by 0.5). The vectors are normalized with the 0x5F400000 fast inverse square root without a Newton step (1.0 to 1.089 long). 0x0C is StandardLit's color with 0x1D's lookup (97 retail materials, always a second shader added over a lit or unlit one). **Lit Metallic** (0x0F, program 0x17) is LitSkinnedModel's lighting reading the skin buffer, its picture at (0.5 + 0.5 r.x, 0.5 + 0.5 r.y) of r = C(2(V·N)N − V) not normalized (V the way to the eye): only ordinary skins give it its eye and matrices. **Lit Reflection Surface** (0x10, program 0x18) is StandardLit's color drawing the frame, which the EE copies into a 256×256 buffer before the draw (`WriteScreenCopy`, `MakeScreenCopySettings`: clamped, no blending), at the pixel's place moved by `FloatParam[0]` × C(N), never its own texture. **Unlit Glossy** (0x15) draws exactly like StandardUnlit (the gloss of its 65 retail materials is the 0x16 pass after it), **Color Only** (0x0B) is the shadows' volumes (bucket 21: positions and a constant color of its record, two records drawing either winding), the **UI** shader (0x0D) makes sprites of a font page's glyphs, and **Unlit Billboard** (0x1B) is StandardUnlit's program with the EE turning the model about its up axis to face the camera (the decomp's `Billboard` in `SetPlacedModelRenderDMA`): only placed models (scenery meshes, LOD levels, dynamic scenery), the whole model when any shader of its parts' materials is a billboard's, never an object's parts, toward the camera's place in the model's space (taken there with the rigid inverse of its matrix), the turn's rows its side and back of up and the way from the camera, applied before the placement's matrix: a reflection, which keeps the model's local +X on the right of the game's screen. TT Lab turns them so (`Rendering/BillboardTurn` and `MainPass.vert`'s `BillboardTurn`, an instance's turn mode `InstanceBuffer.BillboardTurn` for a mesh that `Mesh.IsPlaced` with such a shader, set where scenery placements, LOD levels and dynamic scenery make their meshes): it turned every billboard part, objects' too, to the view's axes, a rotation, and drew the cards mirrored and parallel to the screen (sch_hub's skyline from the game's camera came 3 times closer to PCSX2's picture). The editor's icons (`BillboardSet`) face the view (`InstanceBuffer.FacesView`). The game turns only the matrices a placed model is drawn with, its eye and, while it's wholly in view, its clip matrix stay the model's: the shaders reading them look up on a turned billboard as if it hadn't turned (`MainPass.vert`'s `lookupMatrix`). TT Lab draws the environment maps and the metallic shader so (`MainPass.vert`'s `EnvironmentUv`, `twin_material.env_map` 1 for the environment maps and 2 for the metallic one, the picture read there instead of at the UVs and scrolled like them): the view's axes as the game's camera has them, GL's view x turned around (TT Lab's frame is shown mirrored), scaled by the game's lens (`Rendering/EnvironmentMapping`: `ClipScale`, handed to the shaders as `GameClipScale`, and the lookups in C# for `EnvironmentMappingTests`), so a sphere looks the same from every side; it used the chunk's three strongest directional lights before (`EnvLights`, gone). Unlit Glossy draws as Standard Unlit and Lit Metallic by its lookup, both had a made-up specular (`metalic_specular`, gone). The reflection surface draws a 256 by 256 copy of the frame drawn so far (`Passes/ScreenCopy`, taken once per material as its first draw comes in the scene's order, like the game's `WriteScreenCopy`: it was taken after the opaque passes, before any blended bucket below the material) at the pixel's place moved by `FloatParam[0]` × C(N) (`ReflectOffset`, on the game's screen axes), times its lit colors with 128 as 1: it read a screen texture nothing drew into and came out black. The Blender add-on's materials do the same lookups (its `x` turned around too: Blender shows imported models mirrored from the console like TT Lab's frame before it's flipped).
- **Character shadows** (verified in the PAL executable, `Ghidra Stuff/Engine_RE`): an instance's shadow node (`FUN_001caba0`) casts while the instance has its shadow (`InstanceState.ShadowActive`, every Crash instance has it), is visible and is in a scenery cell drawn this frame (instance flags 0x1000, 0x400, 0x200), its shapes, capsules between two joints, spheres and a plain one (`FUN_001c9130`/`FUN_001c9328`), cast from a point along a fixed direction above it into its chunk's list of up to 100 (`FUN_001cc460`). A chunk draws its list (`FUN_001f1a10`, `FUN_001ed468`: it and its linked chunks) only while its flag 0x800000 is set, which the scenery's draw sets when the cells in view hold instances or dynamic scenery (`FUN_001ed2e8`, every SM2 file has 0x20000 or 0x30000, the scenery reader takes its first word as the chunk's flags). Bucket 21's pass (`StartShadows`/`ApplyShadows` in the decomp's `shadows.cpp`) copies the screen's alpha top bit and its depth into a half size buffer, draws the shapes' volumes into it where that bit is clear (DATE) and in front of the depth, and takes a quarter of it away from the screen. So shadows fall on what a material without FBA drew: every retail scenery material, most objects and creatures; the characters casting shadows keep FBA so theirs don't darken them. A material with any blended shader draws through the colour-only frame (`ReadMaterialShader`'s `MaterialBlends`, FRAME's alpha masked) and never writes the alpha, FBA or not: its pixels keep the bit of what was behind them, so Mecha-Bandicoot's metal (an opaque pass and an additive one) is darkened by his own shadow in front of scenery, which looks see-through where the volumes cross him (his instance has the shadow on; checked in PCSX2's hardware and software renderers). New shaders get no FBA (`LabShader.AlphaCorrectionValue` on, shown as Receives Shadows), skins made in Blender keep it (`TlmMaterials`); the new chunk's ground had FBA and Crash cast no shadow on it, projects made before keep that `Ground` material until it's ticked.
- **Scenery lights** (`TwinTech/Common/Lights`, verified in the PAL executable): the header's low byte is the type the game lights by (`LightType`, written from the class), bit 8 `Enabled` is never read. The game lights an object once per instance at its position (`GatherStrongestLights` 0x1c7f50 from `FUN_001fe290`) with the lights whose bit the scenery root's `LightsEnabler` has, in the scenery's order of lights (`LightOrder`, else kind by kind): ambient lights add `Color` × `Intensity`, the others give a direction and an intensity there (directional: `Direction` and `Intensity` as they are; point: the way to the light times the falloff 25 / (d² + 25), no unit vector, and the intensity times the falloff `AttenuationPower` times; spot: that, nothing while the dot product of that way with -`Direction` is below `OuterConeCosine`, fading in up to `InnerConeCosine`, times that dot product to the power of `SpotExponent`'s low byte) and the 3 of the highest intensity are kept, a light only taking the place of a weaker one. Their colors become `Color` × intensity × 0.5 and the ambient is halved (`FUN_001c7d50`); the lit VU1 programs (shader types 2, 4, 12, 15, 16, `MaterialFactory.IsLit`; 0x2dbeb0, 0x2e3b40) give a vertex min(255, its color's bytes × (ambient + Σ color × max(0, direction · normal))), neither vector normalized, which the GS takes as twice the texture at most. Scenery materials are never lit. Without lighting (no lights, or a root without their bits) lit objects are black, which new chunks were: every retail scenery has lights and its root the bits of all of them and no others, so the lighting follows the lights (`SceneryData.HasLighting` is whether there are any, written as the file's flag) and the build gives the root those bits (`SceneryData.RootLights`). Retail colors add up to 1 with the brightness in the intensity (every scenery has one ambient light of a third grey at 3 to 6). A spot light (`SpotLight`, the tools' negative light) shines along `Direction` within `ConeAngle` (65536ths of a turn) fading out over `FalloffAngle`, but the game lights with `InnerConeCosine`/`OuterConeCosine`, which TT Lab makes again from the angles when a file's angles changed (`SpotLight.ConeCosines`). A directional light's `Direction` is a unit vector pointing at where the light comes from. `BoundsMin`/`BoundsMax` are the tools' boxes the game works out again at load (`ComputeBounds`) and never reads. In TLM files a light's node points its Z axis along its direction (the add-on's arrow), the stored `Direction` is kept while the node still points along it, a stored direction of no length (the add-on writes lights made in Blender with one) while the node isn't turned. TT Lab draws lit materials the same way (`Rendering/Lighting`: `SceneLights.At` gathers a `LightSet`, `InstanceBuffer.LightSetOf` writes one per object and frame for the instances to index, gathered where the nearest `ILightAnchor` (`OGI`) or the topmost parent is; `MainPass.vert`'s `LitColor`, skinned normals included; the clamped color multiplies the texture's PNG like an unlit vertex's does, the GS taking 128 as the texture as stored, half its PNG: TT Lab multiplied by 255/128 more and drew lit objects twice as bright as the game, see the game's look under Rendering): a chunk's viewport with its scenery's lights (`RenderContext.Lights`, made again whenever a light changes), single models and the material preview with `SceneLights.Default`. That's what new chunks get (`DefaultLights`: a third grey ambient light at 4.5 and a third grey directional light at 3 from above, also every new light's values; new chunks also get Crash, a 20 unit checkered ground with its collision and scenery bounds of the game's size, `AssetDataFactory.CreateChunkData`). The chunk's inspector edits the scenery's lighting: the light classes are foreign types (`ForeignPropertyAttributes`: hints, `Enabled`, the bounds and leftovers hidden, a spot light's angles in degrees with the cosines following, `SpotConeCosineChange`, a light's color picked as a color, `LightColorFieldViewModel`: the hue at full brightness, a picked color stored adding up to what the light's did, the brightness left to the intensity), new elements start as `DefaultLights` (`DocumentMetadata.RegisterFactory`). The viewport shows them in the Lights layer (`SceneryLightVisual`: a sun icon, a directional light's arrow the way its light goes, a point light's reach where its falloff halves the intensity, a spot light's cones) for the gizmo to move and turn (`LightDirectionRotation`, a viewport object's `IRotationConverter`: the direction keeps its length), and its menu places lights at the cursor (`CreateLight`).
- **Collision tree** (`AssetData/Instance/Collision/BvhBuilder.cs`, `BvhStats`; the game's `CheckCollisionRayCast` 0x27fb58, `FUN_0027f310`): the nodes (`TwinCollisionNode`, the tools' collision triggers) are the boxes of a binary tree, an inner node's `FirstChild`/`SecondChild` are its children's indexes, a leaf's are both `~group`, a group (`TwinCollisionGroup`: `Count`, `FirstTriangle`) a run of the (reordered) triangles of `Triangles` over `Vertexes`. A query tests the segment against both children of every box it enters and every triangle of every leaf it reaches, a box query gathers at most 256 leaves. The retail files are balanced trees halved by triangle count until 30 or fewer (leaves of 13-31, all at the same depth, ~7-10% sibling overlap), which `Strategy.MedianBestAxis` with 30 makes again within a few boxes and the same cost per ray; `Sah` (binned) is there for comparison. The Command Interface's `bvhstats <chunk.rm2>` measures a retail tree against every strategy under the game's ray walk.
- **Collision surfaces** (`Enums.SurfaceCollisionFlags`, `ITwinSurface`, `CollisionSurfaceData`): the game plays a surface's sounds and particles by contact kind (0 impact, 1 and 2 steps, 3 land, 4 hard impact, 5 scrape: `Impact*`, `Step*`, `Land*`, `HardImpact*`, `Scrape*`), objects landing on it play 0 (4 when hard) and 5 while scraping, scripts play any kind with `DoSound`'s bits 19-22 (`unused3`, 0xF plays the slots), and the player's own footsteps come from the character's sound table by surface ID. Of the 10 floats (`PhysicsParameters`, `SurfacePhysics` indexes them) five are the kinds' volume scales (-1 leaves the volume) and the rest are read too: index 5 (`Unread5`, `UnreadValue5` captioned Ground acceleration) how fast a character's velocity gets to what it's steered at, in units/s² (1000000 on most, 5 or 2 on slippy ground, 120 on liquids), `Friction` (6: rigid bodies' grip, with their own friction, 1 on most, 0.05 on ice; the characters steer in the air by 10 + 40 times it), `Restitution` (7: what rigid bodies' bounce is multiplied by, 0.5 on soft grounds, 0.1 on liquids), 8 and 9 (Downhill pull and Downhill pull slope) how hard ground steeper than the slope (the ground normal's Y below 9) pulls a character downhill, and the `UnusedVector` (Flow) is a velocity along X and Z the surface carries the characters along at ((0, 0, 0, 1) in retail). The flags are one bit per ray cast (`SolidToPlayerProbes` 4, `BlocksCamera` 5, `SolidToObjects` 6, `BlocksLineOfSight` 7), `SendsContactMessageToObjects` (8: a rigid body touching it hands its agent the surface's contact message, `DynamicBody::SurfaceContact`) and `SendsContactMessageToPlayer` (9), both on the deadly surfaces, `Sticky` (10: packs snow on the Rollerbrawl's ball), `LeavesFootprints` (11, captioned Soft: Nina clings to walls of it and skid trails are laid on it, footprints go by surface ID) and `SolidToPlayer` (20); bits 0-3 are the tools' tags and bits 12-19 are set on every surface, none of them read. The game copies the default chunk's surfaces into one table of 128 (`SurfaceTable`, no room check) that every chunk's collision finds them in by ID, see Layout indexes. The volumes live in the `PhysicsParameters` array. The `ContactMessage` (`TwinContactMessage`, the game's ContactMessage, which the scripts' damage commands send too) is a point, the `Kinds` of hit the contact is (`Enums.ContactKinds`, named after what sends each in retail: the surfaces (FallingThrough 0x4, Electric 0x80, GenericHit 0x400 the instant death, Burning and Sinking 0x800008 lava, Water and Sinking 0x2800000 drowning, Water 0x2000000), the engine (a crush, hitting back, particles with collision spheres burning a character) and the scripts' CreateDamage; nothing but the scripts' conditions tests them, besides the drowned staying still and lava melting the Rollerbrawl's snow, each check box's tooltip names its condition (the members' `[Description]`, `EnumCaptions.HintOf`), bits nothing sends or tests get none; rigid bodies touching the level's collision are told of a surface with any kind whatever its flags) and the `Damage` (100 on the deadly surfaces, 0 never reaches the agent's script), then 11 bytes of the tools' memory. The particle IDs (`ImpactParticleSystemId` kind 0, `StepParticleSystemId` 1 and 2, `HardImpactParticleSystemId` 4; land and scrape have none, `GetSurfaceParticle` 0x282160) are indexes into the default chunk's particle systems: the game plays entry index + 1 of its table of systems (`FUN_00223ad0`), which the default chunk's fill first, 0xFFFF none (new surfaces). The inspector names them and picks them from the default chunk's list (`DefaultParticleSystemFieldViewModel`, `->` shows the system in the default chunk), an index past the list shows as broken.
- **Instance state flags** (`Enums.InstanceState`): the engine reads bits 0-18. `PlayableCharacterCanMoveAlong` (4, the decomp's `carriesRiders`, captioned CarriesRiders) sets the instance's flag 14: characters standing on its collision hulls move with it while its matrix isn't scaled (the characters' solver) and rigid bodies landing on it ride its movement node (with `TracksMovement`), dynamic scenery always has it; it was taken for a bit nothing reads, captioned SoftFlag4. `TracksMovement` (5) gives the instance a node keeping its previous transform, `SyncCrossChunkState` (6) a persistent flag slot of its chunk (scripts' `CheckPersistentFlagCondition`), `PersistentFlagInChunkStore` (7) keeps that flag in the chunk meta's own store, `SnapToGround` (18) places the instance on the ground below when created. Scripts test any bit of their instance's state with `SoftFlagSet(n)` (condition 67, retail's `CheckInstanceFlagSet`), so bits 19-31 (`Unknown4` to `Unknown16`), which no engine code reads, are the scripts' own, captioned SoftFlag19 to SoftFlag31: the retail creatures', drones', bats' and penguins' scripts read 19-31 as options of their instances (each set on 9 to 681 of the PAL version's instances), no retail script tests 4.
- **Instance properties** (the game's `PropertyList`): instances, templates and objects keep three lists the class of the object's type copies into its property holder (the rest go to extras): tagged values (`TaggedProperties`: an int, an angle or a float, or another property's index, `Common/AgentLab/TaggedValue`; the tools left a few raw words of no valid type), floats and ints. An object keeps its lists with the state the instances its scripts spawn start in, in a template block (header bits 28 and 29) written while it has a state or values (`ITwinObject.HasInstanceProperties`): the state of an object without values reached no file. TT Lab keeps a tagged value's word (`TaggedProperty`) and edits it as text the way scripts write tagged arguments (`TaggedPropertyFieldViewModel`: an int as it is, `Float(x)`, `Angle(x)` in degrees, `Prop(n)`, `Raw(0x...)`; a plain number keeps the value's type). The class of the object's type keeps a fixed share of each list and puts at most 7 more values of all three together aside (see Object types). An instance's rotation is three signed words of 65536ths of a turn (`GetRotationXYZ` takes the whole word), edited in degrees, and its `SpawnScript` is the starter of the graph its agent runs whenever it starts (without one its object's first behaviour slot).
- **Object types** (`AssetData/Code/Object/ObjectTypes`, verified in the decomp: `instancefactory.cpp`'s MakeTypeNode, MakeAgentObjectNode and GameFactoryStandIn, `properties.cpp`'s CopyFrom and PropertyExtras): the game makes every instance's holder, part, agent and nodes by its object's type. Its class keeps a share of the instance's property lists (`TypeRules`: characters 9 tagged values, 56 floats and 3 ints, crates 0, 3 and 2, creatures 1, 6 and 3, grabbables 1, 4 and 2, pay gates 0, 1 and 3, graples 0, 18 and 2, the others 0, 1 and 2), never cleared (what an instance lacks is whatever the heap had), and puts what's past it aside in 7 words with no check, counting each kind's difference in a byte: a kind past its share while another is short wraps round to hundreds of values copied over its memory (`ObjectTypes.PropertyProblem`). Every instance's second integer is its near distance (0 thinned while unseen, 255 never), read from its own list with no check; float 0 is the mass of scripts' bodies, int 0 the actor subtype scripts test (a character's playable character, a grabbable's kind, a custom pickup's or projectile's slot). Only characters, creatures, generic objects and grabbables get waypoints (`HasWaypoints`), the game appends any other instance's positions and paths to nothing. Every instance reads its object's first model slot (one of none is fine) and every agent its object's resource references with no check. A character is a playable character: its instance's first integer (0 Crash, 1 Cortex, 2 Crash without probes, 3 Nina, 4 none, which no controls drive, 5 the Mecha-Bandicoot) goes into the progress's table of characters with no check, a second instance of a kind stands in for the first, and the character code reads exit points 0-10 (the Mecha-Bandicoot's up to 16), joint IDs up to 28 (`CharacterNeeds`; every retail character has 11 and 29, the Mecha-Bandicoot 18 and 33) and its model's animator, none checked. A graple's rope moves joints 0 and 1 (2 joint IDs). Only pickups read the sub type: 16 and 17 make a custom pickup a pickup code model drives through the slot in int 0 (`PickupObjectNode`; 16 without its instance's properties), any other object with them gets its collision pinned and a pickup's timer written into its node (a projectile's state); the tools wrote the code model's kind (`CodeModel::KindPickup` 0x11 on the red wumpa, `KindProjectile` 0x12 on the projectiles) and 1 on the rest, nothing reads those. Changing an object's `Type` gives it what the new type needs in the type's step (`GameObjectData.TypeChange`, a linked field on the type itself that only acts when the type changed): the new type's sub type when the old was the old type's or can't be had, a model slot when it has none, the template lists filled up to the class's share (`ObjectTypes.Fit`: its own values where they are, the type's most common retail ones for the rest, Crash's for a character; what's past them dropped when the game couldn't put it aside) and the type's state when it had none, a character the playable character none with 11 exit points and 29 joint IDs, a graple 2 joint IDs. The `SubType` is picked from the type's choices (`ObjectSubTypeEditorDesc`: a `ChoiceFieldViewModel` whose choices follow another node), the type's dropdown shows what each type is for (`ObjectType`'s `[Description]`, `EnumCaptions.HintConverter`). An instance linked to another object is fitted for it (`ObjectInstanceData.ObjectChange`: filled up with the object's template values, all of them and its state for an instance without any, a character's first integer a playable character, no positions or paths for a type without waypoints), new instances of the viewport's menu start with their object's values (`TakeValuesOf`, what an instance scripts spawn gets; in both an object of state flags alone counts as having a template, and its instances took the type's state), every new object instance with no starter receiver's index (`RefListIndex` -1), and new objects are generic objects with a model slot and the type's values (`AssetDataFactory.CreateGameObjectData`). Building refuses what the game can't take (a sub type 16 or 17 on another type, template or instance lists that wrap or overflow, a graple of fewer than 2 joint IDs, positions or paths on a type without waypoints, a character that isn't a playable one or whose object lacks the exit points, joint IDs or an animated first model, `OGIData.GetsAnimator`), writes an object without model slots one of none and an instance without a second integer (made by TT Lab before instances took their object's values) its object's values with a warning. Every object and instance of the NTSC, PAL and Xbox discs passes and gets nothing written (checked 2026-10-07 applying `ObjectTypes` to every chunk).
- **Behaviour slots** (`AssetData/Code/Object/BehaviourSlotEvents`, verified in the PAL executable: the decomp's callers of `RunAgentEvent`, the agents' vtables, every object's slots on the NTSC disc): the game starts an object's behaviour slot by its number (none past the object's count). Slots 0 to 10 are every agent's events (`AgentBehaviourSlot`): 0 the instance started without a spawn script of its own (made, reset, spawned, `RestartDefaultBehaviour`), 1 another instance's `TriggerLinkedObjects` on the ones linked to it (generic objects also `Open`/`CloseAllLinkedFurniture`; pickups that don't fly to the player, any sub type but 16 and 17, while the player is within 1.5 units), 2 a contact message (surfaces and water touched as a physics body, `CreateDamage`, `DamageOriginator`, `HitInstancesInBoxes`; with damage only, but pickups and creatures take any, playable characters lose hit points instead and projectiles drop them) and the hard physics hits of crates (over 5, which break unless `SolidToSlide`), creatures and characters (over about 14), 3 to 8 and 10 the playable characters' attacks (walk into, from below, landing on, spin, body slam or the second tied character's touch, slide, a thrown character; while the instance has `ReceiveOnTriggerSignals` and not `CanAlwaysDamageCharacter`, scripts switch the kinds with `SetObjectFlags587`, the decomp's SetAttacksTaken; nothing attacks a graple) and some physics hits (crates' 3, 4 and 5 by the impulse's direction, creatures' and characters' 3, generic objects' 3 with their walk into bit, a falling crate onto another crate 5 or 7 by its `SolidToBodySlam`); nothing starts 9, which the tools filled with copies of hit handlers. Past 10 only the playable characters (11 to 110: `CharacterEvent`, the claw's, the gun's, the vehicles'; Crash's own scripts start 20, 21, 30, 44, 45, 79, 84, 85, 102 and 104), crates (11 falling, 12 landed, 13 `TriggerAllNitroCrates`, 15 checkpoint released) and the graple (11 to 17, told by Nina's claw) have events; every other slot only runs when scripts start it (`RunScriptSlot`, `RunSlotBehaviourOnLinked`, a state's `UseObjectSlot`), the object's scripts decide what it's for. The object's inspector captions each slot the game starts for its type with what starts it (`Behaviour Slot 3 · Touched`, when as its hint) through a linked field following the type and the list (`GameObjectData.SlotCaptions`, the elements' presentations), the others keep the list's caption, and the Replace links dialogue captions them the same (`LinkReplacement` takes an element's presentation's caption).
- **Layout indexes** (`Assets/Factory/LayoutIndexes`, the decomp's `instancesection.cpp`): the game numbers a layout's elements of a kind in the order it reads them and the build writes them by ID, so building a chunk gives each layout element its place among the chunk's elements of its kind and layout (`ExportTwinID` while the chunk's `LayoutIndexes.Current` is in use, the IDs outside a build) and references are those places: an element taken out (a gap in the IDs) made every reference past it point at the next one. Positions and paths are one list per chunk, the layouts' after each other: the chunk's own layouts (0-2 and 7) find positions from its start, the others past the positions of the last own layout before them that has any (`PositionReference`, `ChunkEntry::OtherLayoutPosition`), paths are found from the start (`PathReference`), and only those of layouts read before. New elements get the lowest ID free among their kind of their layout of their version's chunk (`TwinIdGeneratorServiceInstance`, by chunk path, package and layout): the PS2 and Xbox chunks of a path were numbered together, and one version's left the other gaps.
- **TT Lab model files** (`.tlm`, spec in `TT Lab/BlenderTools/TLM.md`): models, rigid models, meshes, skins, blend skins, OGIs, scenery, dynamic scenery, collision, skydomes and the save icon are stored as a JSON tree of nodes with their arrays in binary data next to it, written and read through `AssetData/Graphics/TlModel/` (`TlmFile`, `TlmNodes`, `TlmTreeNode`, `TlmMeshes`, `TlmAnimations`, `TlmMaterials`). The file is the asset's data file itself (`DataExt => ".tlm"`). Users edit them in Blender through the add-on's own importer and exporter, so:
  - A node has a `kind`, a `name`, its Twin Tech values in `data` (the same keys the add-on's panels edit) and a transform relative to its parent. Names are cosmetic, the hierarchy is only read where it means something: an OGI's bodies, exit points and collision hulls name the joint they follow, a scenery LOD's levels are the meshes under it, and a scenery's placed meshes and LODs are whatever has a mesh anywhere under its root but the collision and the dynamic scenery (`SceneryData.ReadPlacements`; a LOD's level moved out of its LOD is one too), each with the tree node it was in (`Node`) and its place among them (`Order`). TT Lab writes them under the root's `Meshes` (`scenery_meshes`) and `LODs` (`scenery_lods`), numbered in their group (`AddPlacementNodes`): they were one list under the root, which Blender showed as one long list. The add-on gives what's made in Blender under them their kind (`tlm_blender.role_of`, by the role of what it's in: a mesh in either group is a placed mesh, an empty in `LODs` a LOD, a mesh under a LOD its level). Skins and shapes have no transform, the add-on bakes where their object is under the root into the vertexes (a modder's mesh is usually rotated and scaled against the skeleton), and works a body's or exit point's transform out from where the object follows its bone (Child Of constraint or bone parent) with the armature at rest (`_attached_placement`). An exit point's game matrix is the node's `matrix`, carried by the add-on without showing it, like the bones' binds. A blend skin has as many shapes as its mesh has shape keys (`BlendsAmount` is derived), the add-on writes every key's weights into the facial animations.

- **OGI material slots** (`OGIData.MaterialSlots`, `OgiMaterialSlot`): the OGI's inspector lists every material its rigid models, skin and blend skin draw with, a slot each with the parts drawing with it (`Slot n · <material>`), like Blender's material slots. Another material picked for a slot goes into every one of its parts, the models' data the OGI's file is written from, a step of the history, and the viewer draws it at once (the slots are its viewport object's `RenderDependencies`, its `Refresh` drops the models' meshes from the `MeshService` and the meshes are made again). The slots aren't stored: they're made of the parts once something reads them and again when the file is read, so the reflection walks over data (`ExtractReferences`, which importing runs while a project is created, `DeletedReferenceFixer`, `PrefabLibrary.StripChunkLinks`) skip `[JsonIgnore]` properties, reading the slots reads the models' data (`OgiMaterialsTests`).
- **OGI animations**: animations aren't assets. Each OGI keeps the animations played on it (`OGIData.Animations`) in its file, under its armature (`TlmAnimations`). Game objects pair a model with an animation in `ModelSlots` (the OGI's URI and the ID of one of its animations), the game never has an animation without a model. Creating a project gives every OGI the animations game objects play on it, so animations shared by several OGIs get copied. Building puts each slot's animation into the chunk through `OGIData.ResolveAnimation`, where copies that are still the same go in once and edited copies of an ID get an ID of their own (see the IDs below). The OGI editor plays them (`OgiAnimationsViewModel`: `Advance()` plays on by the clock's time since the last frame, `Advance(elapsed)` by a time the tests give, the clock's took a frame or more on a loaded machine) the way the game does (`SetAnimationData`, `ConstructAnimationSettings`: an animation lasts its frames over its rate; looping, every frame 1/rate and the last blending into the first, which the frames' slider goes on to; once, the steps between its first and last frame over that time, ending on the last; it went from the last frame straight back to the first), between frames angle by angle like the game's `AnimateJoint` (`AnimationData.GetJointPose`: translations, scales and each Euler angle straight from a frame's to the next's, an angle taken round to the next's side when they're more than half a turn apart, `ReadJointAngle`, the rotation of the angles turned by the joint's additional rotation): it slerped the frames' rotations, and Twinhou's Reimu, whose run twitched a leg backwards in the game at every loop, ran smoothly in TT Lab and the slot's animation is picked from the OGI's (`OgiAnimationFieldViewModel`) in a dropdown with a search: the combo box shows the slot's animation and opening it (a click, F4, Alt+Up/Down, Enter or Space) shows a flyout below it in place of its own list, a search box over the animations with every word typed in their name or ID (hex, with 0x or without, `OgiAnimationChoice.Matches`), the first highlighted, the arrows moving the highlight, Enter or a click picking and Escape leaving the slot as it was (`OgiAnimationFieldView`: a flyout's popup has no visual parent, so nothing typed in it reaches the combo box, whose Space and Enter pick and close its own list, or the inspector around it). Its Skeleton check box (only in the OGI's own viewer, `CanShowSkeleton`: a chunk's scene would draw every instance's) draws the joints, the root bigger and orange, and the bones from their parents over the model in the pose it's shown in (`OGI.DrawSkeleton` of `TwinSkeleton.Pose`, the overlay layer, joints a fixed size on screen); the viewport keeps the switch (`ViewportViewModel.ShowsSkeletons`, handed to its `RenderContext`) while the panel and the model's objects get made again, and it's a preference (`Preferences.OgiViewerSkeleton`, in `settings.json` once TT Lab closes, like the snapping settings) every OGI viewer starts with and follows (`ViewportViewModel.Init`, `OnPreferenceChanged`), no other viewport. A model made again (another material for a slot) is at rest, the panel gives it the frame or the bind pose it was shown in once the viewport says so (`ViewportViewModel.ObjectsRebuilt`).
  - Every joint of the model reads the track settings of its index from the animation playing (`AnimateJoint`, no bounds check), and the facial weights are read at the main animation's frame (`SetAnimationData`). A few of the game's animations have fewer or more joints than their model (Crash has some of 62 joints and one of 2, of his 51), which stays while the model has no more bones than when the animation was imported (the action keeps that count, `model_joints`; retargeted copies the source model's); once bones get added the add-on gives every animation settings for each (`skeleton.animation_joint_count`). A facial animation always has the main animation's frames (`TlmAnimations.FacialFromKeys`, the add-on writes them so too). The add-on samples an action's curves on every frame of its frame range from its start (imported actions have a manual range from 0, Blender keys new ones from 1; dynamic scenery movements likewise), a bone's rotation from the curves of its rotation mode or the ones the action has (`_rotation_components`, quaternion, Euler or axis and angle, shared with retargeting), and warns about bones whose constraints or drivers the keys don't have (`_unbaked_bones`). Pose locations get the armature object's scale relative to the root in each bone's rest frame (`_location_stretches`, `blender_roundtrip.py --scaled` checks it): the bind poses have it, and an FBX rig's 0.01 left its animated translations a hundred times too long. An animation's frames a second are 5 bits of its header (`GameAnimation` bits 18-22, `ConstructAnimationSettings` plays it for frames over them, 0 divides by zero; every retail animation has 25): the add-on writes an action faster than 31 every few frames at a rate keeping its length (`MAX_ANIMATION_FPS`, 60 at 30), TT Lab clamps the rate it reads to 1-31 with a warning (`TlmAnimations.MaxFps`), TwinTech masked 60 to 28.
  - Every animation has the game's bytes (`exact`) next to every frame's local transform of every joint and its per-animation flags (independent scaling, additional rotation). The add-on turns the keys into poses of the bones and back and carries the game's bytes with the action. Reading keeps the game's values of every joint, frame and track whose keys still round to them, rotations closer than half of a raw unit, so an unedited animation is its bytes and editing one bone changes only that. Animations without an ID (made in Blender) and copies of one get a new one from 0x8000 up, and loading an OGI writes its file again when it had any. The add-on gives them their IDs itself when it exports, kept with the action (`skeleton.animation_ids`, `_give_animation_ids`): TT Lab numbered them in the file's order, the add-on writes actions made in Blender sorted by name and never learned the IDs, so adding or renaming an action changed which one a game object's slot played.
  - Those are the IDs the OGI and game objects' slots know an animation by, the game's are the build's (`Assets/Factory/AnimationIds`, verified in the decomp's `resourcetables.cpp`): the game keeps the animations of every chunk it has loaded in one table of 2500 at the ID's low 15 bits (`ResourceIndexMask`, no check that it's in the table) and skips an animation of an ID it has (`ResourceReaderFor`), and only finds them through objects' slots (cutscenes too). The build gave edited copies and animations made in Blender IDs from 0x8000 up, chunk by chunk, which took the place of the game's from 0: Twinhou's beach played the cutscene director's copy of Crash's idle (0x8000) for Reimu's retargeted one (0), her skin twisted, the sandbox (no director) was fine. Now one table per version gives the IDs (`ITwinItemFactory.AnimationIds`, shared by the chunks' factories, kept in `build/cache/animation_ids_ps2.json`/`_xbox.json`, Play's builds of a few chunks included): every animation's ID is worked out at once when the table is first asked (`AnimationIds.Plan`), from the project's OGIs' animations, each by its key (the SHA-256 of `AnimationData.GetItemSource`, `KeyOf`) and the ID the OGI has it by: an animation keeps each ID an OGI has it by (the disc's chunks have one spin by CrashSpin's 3 and CrashSpinWithCortex's 0xA8, and the crates' breaks 9/A/B, 10/17, 12/16, 108/10B and 109/10C, which the builds gave one ID each: 101 of the PAL version's 135 chunks had other IDs than the disc's; a copy by one ID goes into a chunk once, the same animation by several IDs by each), an ID OGIs have other animations by stays the first one's, the others get the ID their animation got first or one worked out for them in the fixed order (the highest no OGI's animation has), given once a chunk asks for it (`Plan.AddSlot`, only what chunks have takes the table's room); first is a fixed order (the version's OGIs before the other version's, the game's four packages before the project's, then the OGI's URI and the ID), so builds from nothing give the same IDs whichever chunk the memory gate starts first (keyed by the content alone the first chunk to ask decided: two builds of a project gave the spin 3 or 0xA8 in every chunk); past the room for every animation of the OGIs the plan is made again with the animations game objects play first (their model slots: loaded data, else the data file, and chunks' own values) and an animation left without room fails whenever a chunk asks for it. The IDs builds gave stay while valid (an ID an OGI has the animation by, or one no OGI's animation has, which is then what the animation gets by the IDs it can't keep), so a project's builds after keep theirs. What the OGIs' animations are comes from their files when the table loads, kept per file by its length and write time (the table's file is version 2): the game's bytes a file TT Lab wrote keeps (`TlmAnimations.ReadStored`, `OGIData.StoredAnimationsOf`), a file the add-on wrote (`exported_by`) read the way TT Lab reads it in a dry `AssetDataScope` that leaves its `AssetFileStamps` as they were (recorded, the project's watcher took the export for TT Lab's own and an open editor of the model kept its old data), a loaded OGI's data as it is. A chunk keeps its animations' IDs as `animation:` dependencies of their key and the ID their OGI has them by (`AnimationIds.DependencyOf`) in the build cache and is rebuilt once one of them changes; the IDs no chunk the cache knows has are let go of when a build starts (not while the cache was just reset, it then knows none of the build folder's chunks) and once every chunk got built (`KeepOnly`). The NTSC disc has 1074 animation IDs, up to 0x679, each of one content in every chunk; an unedited project keeps all of them (checked on Twinhou's beach, its links and the sandbox: 303 animations kept their IDs, Crash's idle and walk the director plays got 0x9C3 and 0x9C2, and Reimu idles in PCSX2). Rotations become the game's Euler angles through `GlmExtensions.ToEulerAngles`, because GlmSharp's `quat.EulerAngles` gives NaN at gimbal lock. Every rotation has two sets of angles ((x, y, z) and (x + half a turn, half a turn - y, z + half a turn)) and the game blends from one frame's to the next's angle by angle, so blending to the other set swings the joint around, and close to a middle angle of a quarter turn (gimbal lock) neither set blends along the turn: `TlmAnimationFrames.ChooseAngles` picks every frame's set over the whole track (a dynamic program, frames keeping the game's values fixed, the other first angles at gimbal lock among the choices) by how far the game's blend strays from the shortest turn halfway, from the last frame into the first too when the track comes back near where it started (its last frame no farther from its first than its frames from each other), a step of about half a turn counting the worse way rounding can turn it. Picked frame by frame, Reimu's thighs passed near gimbal lock mid-stride, ended on the other set and swung up to 79 degrees off at every loop. The add-on's export gives every joint whose additional rotation no animation keeping the game's values turns by (`exact` holding with its flag on, `animation_frames.holding`) the one the game blends its animations best with (`animation_frames.choose_frame`, `tlm_blender._choose_additional_rotations`: the same costs, only where gimbal lock is matters, an axis searched over a hemisphere and refined, kept while every blend follows its turn within a degree or no axis is clearly better) and sets `additional_rotation` in the animations made from keys; in the file only, the scene keeps its settings. Measured as how far the feet stray from the slerped path during the game's blends: Reimu's run 53% and 118% of the leg before, 23% and 22% with the angles picked over the track alone, 3% and 5% with the add-on's additional rotations (Crash's retail run 6% and 11%); +1.7 s exporting her 119 animations.
  - A joint with independent scaling still moves with its parent's whole transform (its offset gets the parent's scale), only its own axes leave out the parent's scale, like Blender's "None" scale inheritance the add-on sets (`animator.apply_to_all_armatures` on every frame change and scene update, only on armatures of Twin Tech models, `animator.is_model_armature`: it set every bone of every rig in the scene to Full). OGI 393's first animation scales the joint above everything to 0.3 and each part to 0.32 and ends on the bind pose at that size. The viewer's `TwinBone` keeps each bone's world rotation apart from its matrix, because animations hide joints by scaling them to nothing and joints under them that don't inherit scale still turn with them.
- **Cameras** (`CameraData`, TwinTech `Common/CameraSubtypes`, verified in the PAL executable, `Ghidra Stuff/Engine_RE`): a camera trigger runs up to two subtypes, each worked out from the player's position: the first (`MainCamera1`, captioned Camera Look At) gives the point the camera looks at (`FollowCameraTarget::TakeCamera`, none looks at the player), the second (`MainCamera2`, Camera Positioning) where it stands (`FollowCameraPositioner::TakeCamera`, none follows the player from behind). Most of the game's cameras with a subtype only have the second, and all six boss cameras are second ones; a boss camera made first turned the camera behind the player to look past them. Points (`CameraPoint`, `CameraPoint2`: `Mode` 0 the `Distance`'s share of the way from the target to the point, 1 that many units from the target towards it, 2 the same no further than the point), lines (`CameraLine` sliding to the player's nearest point plus the base `Offset`, `CameraLine2` sliding by the player's flat distance between `NearDistance` and `FarDistance`; between them the game adds `NearDistance` to the share, a retail bug every camera of the kind avoids with 0), paths (`CameraPath`: the AI paths' B-spline with the same `ArcLengths`/`InverseSteps`), sampled splines (`CameraSpline`: samples a `StepLength` apart with unit `Tangents`, `ArcLengths`/`InverseSteps` like a path's; a sample's W is a word, the decomp's `SampleWord`: bit 24 passes over the sample, else bits 8-23 are an offset along the curve, n × 50/32768 − 50 units, which `SplineFlags` bit 0 replaces with the `Offset`, and bits 0-7 a share of the way toward the target, n × 5/128 − 5, both taken between the samples that have them; every retail spline's ends have them, and `CameraGeometry` gives new samples (W 0 reads −50 and −5) the passing word and ends without values the neutral 0x7FFF80; the inspector edits a sample as its place, Key, Offset and Share (`SplineSampleWord`, `SplineSampleFieldViewModel`, the samples' list's `DocumentCollectionViewModel.ElementEditor`), each part a step of its own, a passing sample without values made a key gets the neutral values and a key of the lowest offset and share keeps bit 25, which nothing reads, so its W isn't a new sample's 0), zones (`CameraZone`, `CameraZone::At`: where the player is within the flat `TargetBox`, across and along it, is where the camera goes within `CameraBox`; a box is the plane it lies in (its normal, across × along, and a leftover W; never read), its across and along axes, its corner and its sizes, X across and Y along (`BoxFractionsOf`/`BoxPointAtFractions`). `CameraBoxTransform`/`TargetBoxTransform` are them as matrices: across × size X, a thin thickness and along × size Y; TwinTech took the plane for an axis before and drew retail zones standing up) and the boss camera (`BossCamera`: the player in arena space through `WorldToArena`, the camera `Orbit.Y` from the axis in the player's direction at the player's height plus `Orbit.Z` while under `Orbit.X`, back through `ArenaToWorld`). Every subtype's `Follow` (`CameraSubBase.FollowMode`, one choice in its low two bits: `OwnWay` their own way, `AtRate` at `FollowRate`, 0 and 3 straight there) tells the camera rig's point followers how to move to its points. Only lines, paths, splines (with `ITwinCamera.SplineCameraFlags.TakesOffset`, the only bit of `SplineFlags` the game reads) and 1C09 read the `Offset`, zones don't even have the follow values in their files: the inspector leaves those out (`ForeignPropertyAttributes` keyed on the subclass, `Of` starts at the property's `ReflectedType`). `CameraPoint2.Mode` is a `PointMode` choice. The main camera's `Flags` (`ITwinCamera.CameraFlags`) tell the camera controller what to take from it (`FUN_00274e08`): `SetsPitch`, `SetsYaw`, `SetsFov` and `SetsDistance` hand its three angle blenders and distance the `PitchStart`/`PitchEnd`, `YawStart`/`YawEnd`, `FovStart`/`FovEnd` (65536ths of a turn, the blenders are named by the levels' values: 20°, half a turn, 32°) and `DistanceStart`/`DistanceEnd` (5, 10, 4.5 units), as the two targets of a blend over `BlendTime` seconds or, with `ValuesAlongGeometry`, the values at the start and end of the camera's line, path or spline; `BlendsInFrom*` replace the yaw's, pitch's and distance's ranges with `BlendInYaw`/`BlendInPitch`/`BlendInDistance` whenever the yaw is at least as near `BlendInYaw` as `YawStart` (`MainCamera::NearerBlendIn`, every frame the camera is taken: a camera entered from that side keeps looking that way), `NoBlendIn` cuts, `CutsFromSameKind` cuts between two cameras with it, `SetsTargetFollowRate`/`SetsPositionFollowRate` make the rig's point followers move the point the camera looks at and its place at `TargetFollowRate`/`PositionFollowRate` (shares of the way a second), `SetsYawSpeed` turns the yaw blender at `YawSpeed`, `NeedsRunningCamera` takes it only after another camera the frame before, and without `IgnoresPlayerState` a new camera is only taken on foot while the character is on the ground (`FUN_001434a0`). The rest are the follow camera's (the decomp's `FollowCameraPositioner`/`FollowCameraTarget`): `Steers` keeps its probes on, `GivesTargetBox` makes `TargetBoxMin`/`TargetBoxMax` the box the point it looks at sits in (the box's middle from the followed object, turned with it unless `TargetBoxUnturned`), `FramesInstances` moves that point toward the trigger's instances by `FramingShare` up to `FramingDistance`, `HoldsStill`, `KeepsHeight`, `OnlyLooksAtTarget`, `Tilts`, `NoProbes`, `BlendsWhenNear`, `BlendsAlongLine`, `SkipsViewCheck`, `AlwaysTakesValues`, `AddsExtraYaw`; bit 14 is never read and bit 1 only by a switch back nothing starts. `Switches` (`CameraSwitches`, 0 on nearly all) has `SecondSlot` (a camera for the character's death: taken only once the character died, shown while it's dead), `KeepsProbesWhileIgnoring` and `ResetsController`, `Group` keeps cameras of different nonzero groups from replacing each other. Without their flags the target box and the framing values are the tools' memory. The camera's trigger has bits 18 and 20 set in the levels, never read. `CameraGeometry` derives what the game stores next to the geometry (a path's and spline's parameters, a spline's tangents and step, the boss camera's other matrix) when it changes, keeping the game's values otherwise. The game reads both boss matrices (`FUN_00279990` computes neither) and uses each as the other's inverse (`BossCameraAt` takes the target into the arena through `WorldToArena` and the camera back out through `ArenaToWorld`, `FUN_0027cfb8` keeps the previous position in arena space), the game's pairs agree to 6e-6, so `WorldToArena` is read-only and follows `ArenaToWorld` in the inspector like a chunk link's `ObjectMatrix` (`InverseMatrixChange`, through `ForeignPropertyAttributes`). `CameraGeometry` also makes the viewport's handles: a draggable point for every point and sample (`Position` nodes may be `Vector4`s, their W stays), a box for each zone box (`Transform` through the box matrices) and the boss camera's arena cylinder (`CameraArenaVisual`), all in the camera paths layer.
- **Triggers** (`TwinTrigger`, verified in the PAL executable): the header's low byte is the tools' `Kind` (50 on most), 0 makes the trigger a box of its chunk's second reverb instead of a trigger node (`SoundBox`, 7 a chunk: the sounds take the chunk's box reverb, which scripts set with `SetSound`, while the listener is in one), and a camera's is its priority (`OfferCamera`: of the cameras the character is in the highest is taken, the one in use on a tie; captioned Priority in cameras, `EditorCaptionIn`). Bits 8-11 send the messages (`Enums.TriggerFlags`, the decomp's `MessageTriggerNode`): 11 the first to what enters until anything was inside at a check, 8 the second to what enters when the first isn't sent, 9 the third to what stays and to what enters when neither is, 10 the fourth to what leaves, the trigger's instances told along. Bit 12 is `NotPolled`. `ObjectActivatorMask` says what sets it off by object type: the playable characters check triggers of the character's bit alone (only the player then) or of none (any playable character) themselves every frame unless they tell what leaves, the rest are polled every `CheckInterval` seconds (0.3, stored in ticks by the node, `FUN_001f5428`) for instances of those types; cameras need the character's bit. The box reaches from -`Scale` to `Scale` around `Position`, turned by the rotation's quaternion (x, y, z, then w: `MatrixFromRotation`'s rows are the columns of its usual matrix, glm's `quat(x, y, z, w)`). TT Lab keeps the rotation as degrees about X, then Y, then Z like an object instance's (the game's `GetRotationXYZ`, glm's `quat(vec3)`, `TriggerData.Rotation`, what the inspector, the gizmo and the viewport go by) and the game's quaternion (`GameRotation`), built while the angles are still the ones worked out of it: no float angles give its bits back. The import kept radians about Y, then X, then Z, each turned the other way, which the viewport drew as degrees and the build turned in yet another order (every turned box drawn wrong, 27 of every disc built turned by up to half a turn); checked against every trigger and camera of the PAL, NTSC and Xbox discs (2026-10-12), they're drawn within 1e-5 degrees of the game and built bit-exact. `GlmExtensions.ToEulerAngles`/`ToEulerDegrees` work the angles out of the matrix in doubles: the arc sine of the middle angle made a quarter turn 89.98, and at gimbal lock the turn goes into the first angle. `InstancesGrowth` is the tools' list growth (10; instances' lists of instances, positions and paths have one each). **Chunk links**: `Visibility` (`ChunkLinkVisibility`, the flags' low 7 bits: 0 hidden, 1 always drawn, 2 drawn through the load wall as a portal, `FUN_001ea3a8`), `KeepLoaded` and `IsLoadWallActive` (bits 7-13, either makes the linked chunk's own links load a level deeper, `LoadLinkedChunks`), `LoadsWithoutPlayer` (type bit 1: a link with hulls loads its chunk while there's no player yet). A zero `LoadingWall` is no wall (the build writes none), links without one are stored without one (`ShouldSerializeLoadingWall`, a link read back got a zero wall every save wrote). New links get a 10 unit square wall standing on where they're made, facing +Z (`ChunkLink.WallAt`: the constructor's at the origin, the viewport's menu's at the cursor), so it shows and can be dragged, and the chunk matrix's inverse as their object matrix (the menu's gave them their chunk matrix, and what crossed the link landed twice the link's offset away); a zero wall has no object in the viewport. The build writes a link's object matrix as its chunk matrix's inverse where it isn't one (`ChunkLink.WrittenObjectMatrix`, `InverseMatrices.Written`: the link's own while it's the inverse within a thousandth relative, which every retail link is), with a warning saying how to store it: the inspector's linked field (`InverseMatrixChange`) only follows changes of the chunk matrix. The viewport draws it as a ring on the ground (a sphere while selected) and drags it by a handle on the ring's +X side (`AiPositionRadiusVisual`, `AiPositionRadiusHandle`). Their `Flags` (`Enums.AiPositionFlags`, bits 1, 2 and 4 in the levels) are read by the path finder (`Blocked` keeps routes out, the nearest point search with flags asks for some and rules some out) and the scripts' conditions on a route's step (`Airborne`, 2, 4-6); `SetFocusPositionToNearestPoint` never takes a position with flag 4 and takes one with flag 2 however far it is (others within 30 units), `SetNearestPointFlags` switches bits 0-2. An AI path's `Flags` (`Enums.AiPathFlags`) say which routes may take it (a route request's bits 17-24 rule out the paths with some) and what the conditions find on it (`NeedsJump`, `NeedsLongJump`, `NeedsHighJump`, `Flag5` flying, captioned NeedsFlying; bits 0 and 1, which the tools set together on a sixth of the paths, are never read), its `ChunkA`/`ChunkB` are the tools' chunk indexes the game replaces when it links the navigation. - **Chunk overrides**: a chunk keeps its own values of the assets it shares with other chunks (`LevelChunk.Overrides`, `AssetOverride`) instead of copies of them. Values are kept by their JSON path in the asset (`AssetOverrides`): its metadata without what makes it an asset of the project, and its data under `AssetData` when the data is kept as JSON the default way. Other data (models, pictures, sounds, code) can't have a chunk's own values, only the asset's metadata can.
  - Creating a project first makes a variant for each chunk after the first whose item has the same ID but other content (`Variation` is its chunk path, `GetUriByTwinId` finds the requester chunk's variants first). `VariantMerger` then turns every variant that only differs in values into an override of the first chunk's asset (a level's own version of a startup object into one of the global asset) for every chunk using the variant, and redirects what referred to the variant, including models' material URIs and the chunks' own values (`RedirectOverrideValues`: a value then the asset's own is dropped, an override without values goes). Every variant's asset is decided first and each one's values worked out with every link to a merged variant leading to its asset, so the order they're merged in changes nothing (merged one at a time in the order of the project's assets, which parallel writes leave in the order of the slots they freed, an object's override kept a link to another object's variant merged after it, then deleted, and a PAL build failed in 10 levels, `VariantMergeTests`). The overrides are added by kind (what they refer to first), then URI, sorted by asset stably. A variant is often used by more chunks than the one it's named after, a later chunk with the same content found it by its hash; chunks use what they list in their resources and item versions and what those refer to down to other chunks. Variants no chunk uses (a chunk's model found the asset by its ID) go without values. Of the PAL version's 850 or so chunk variants only 5 textures of other pictures and 3 behaviour graphs of other code (the reused IDs 0xBED, 0xEF3 and 0xF65, whose chunks' objects name them) stayed, the rest were 379 overrides of 111 chunks and every chunk built byte-identical to before; that was before every chunk's parts were resolved (see Create), and 2.0.0's creation, which resolves them the same way, keeps 10 texture variants (of BAC3703A, 7AE4447B, 3B69A5CF, 935246FC, B7D46A15, CC4BA680 and 5844B4A0) and merges 5438 variants, this version's weren't counted again. A kept variant of the same base, picture and settings as an earlier one (URI order) whose texture only differs in the tools' leftovers is merged into it (the PAL version's 43 BAC3703A variants of one picture are one). Sounds were all the same, textures only differed in their header's leftovers, objects in their name, behaviour pack, template values and whether they list their resources.

The chunk's own assets (its resources, instances and what's in its folder) are edited as they are, and data without values of its own is the asset's, edited for every chunk. A chunk reaches most of what it shares through links (an instance's object), their `->` opens the chunk's view in its inspector (`UriLinkViewModel.OpenDocument`, a step back is a click away, see the Inspector panel) and an instance shows its object's view in the viewport. Links to a view the chunk has values of its own in are blue as well (`DocumentNodeViewModel.GetLinkedView`). Data marked `[NoChunkOverrides]` (objects' names, the game only goes by IDs) is left out of views and overrides. A view's own values are the ones the chunk has or changed that still differ from the asset (`ChunkOverrideSession.GetOwnValues`). What another editor changes in the asset (its own tab, another chunk sharing a value with it, its changes discarded) the open chunks' views take wherever the chunk has no value of its own, and what chunks can't have values of (`DocumentViewModel.TellChanged` to the open chunk documents, `ChunkOverrideSession.Follow`, the view's origin taking it too): set in place (`AssetOverrides.Take`), so the chunk's nodes keep showing the view's objects, the nodes of what changed made again (`PropertyGraph.Follow`) and its `Followed` event telling the viewport, no step of the chunk's history and nothing it saves. The chunks' scenes drew an object's old model until they were opened again. A value put back or shared follows the asset again (`ChunkOverrideSession.Share`). Deleting an asset fixes the values of chunks' overrides that link to it the way the asset's own would be (`LevelChunk.FixOverrideValues`).

Behaviours are one asset per name: the PAL version's chunks only differ in leftover memory in unused parameters (the NTSC version has the `0xCD` fill there).

- **Particles** (`TwinParticleSystem`, `TwinParticleEmitter`, `Rendering/Particles/ParticleSimulation`), worked out from the PAL executable (the Ghidra project's `GameParticle`/`ParticleInstance` structs and `GenParticle_*`/`GenerateParticles`/`BuildParticleRenderTable` functions, notes in `Ghidra Stuff/Particles_RE`): emitters (`ParticleSystemInstance`) play the system they name, their chunk's own or the default chunk's (`DefaultParticles`, one per version, `ParticleData.GetUsableSystems`/`FindSystem`, `ParticleSystemFieldViewModel`). Everything runs in frames of 1/60 s. An emitter on makes `GenRate` particles a frame (one every that many frames when negative, none at 0) for `EmitterOverTime` frames, waits `EmitterOffTime` (plus 1 to the random extras), the cycle shifted by the timing offsets against the frame counter, and only while the camera is between `CutOnRadius` and `CutOffRadius` (drawn within `DrawCutOff`). `MaxParticleCount` is what one lifetime makes times the ghosts (`TwinParticleSystem.ComputeMaxParticleCount`, the game recomputes it at load and TT Lab on write), the ring of slots that new particles write over, at most 1024. A particle is a start, a velocity and a spawn time: position = start + velocity·t + (0, `Gravity`, 0)·t² in the emitter's gravity space (the acceleration is twice `Gravity`; drips and splashes have negative gravity, fire and steam positive), the gravity rotation turning that space into the world. Rotations are 65536ths of a turn applied tilt (about Z, the up leans towards -X), yaw (about Y), roll (about X); the emit rotation turns the start and velocity within the gravity space. `GenSort` picks the generator (`GenSortType`: box, ranges, radial ring/cone with `RandomStart` = radius, yaw, tilt and `RandomEmit` = speed, yaw and tilt spreads, rotor, spheroid, plane bouncers with the emitter's `PlaneOffset`/`BounceFactor`/`BouncePlaneAngle`, area-even sphere, star), `GenCode` a fixed velocity-from-start rule (always 0 in the data). Ghosts are copies spawning `GhostSeparation` apart. Sizes and jibber amplitudes are ten thousandths of a unit, jibber frequencies cycles per life, colors bytes with 128 leaving the texture as it is, curves keys of a life fraction and a value sampled at 64 steps (the first pair of keys enclosing the step, 0 outside), texture rectangles pixels plus 2^19 (2^18 in a few systems; the game adds 2^19 and keeps the low 10 bits, `ParticleEmitter.TexturePixel`), `TexturePage` one of the default chunk's three pages. **Blend modes** (`ParticleBlendModes`, picked by name with `ChoiceFieldViewModel`): loading a page (`FUN_0019d9d8`) makes its four shaders in bucket 22, all dropping alpha under 5/128 and testing depth: 0 Additive (preset 1, 629 retail systems), 1 Subtractive (preset 2, the skid marks and the warp splash), 2 the page material's own first shader with those bits forced (normal blending in retail: smoke, dirt, feathers) and 3 Cutout (no blending, writes depth, unused); 0-2 don't write depth, 4-6 read the next page's IDs as the shader. 7 Distortion (unused) draws hexagons in bucket 23 through shader type 0x18, which copies the frame first (`FUN_001d6aa8`): the VU1 program (0x2e0960, `Ghidra Stuff/Particles_RE`) makes six triangles inside the particle's quad pointing along its height, the middle showing the copy where it is with the particle's alpha, the rim alpha 0 showing it moved by the corner's offset times (`Distortion.X` / 16384, -`Distortion.Y` / 4096), fading out with the depth to nothing at 40 units. `DrawFlag` is the draw list: the game draws list 0 (the modes in the order 3, 2, 1, 0) and list 2 (only mode 7, every mode 7 system is put there at load), never list 1. The `Unused*` fields and the tools' size/rotation ranges are never read by the game, `TextureFrame*` are recomputed and then never read (probably a texture animation), the switches and groups of emitters aren't read either. The retail data only uses GenSorts 0, 6, 7, 8, 9 and 11, version 0x1E, and no gravity rotation, roll, offset or plane on any emitter. Chunk viewports run the emitters' systems and draw them in their own pass with the default chunk's texture pages, in the game's bucket 22 between the scene's two passes (see Draw order): the emitters queue their particles and `ParticlePass` draws them at its end in the game's order of the modes, each with its blending (`ParticleEmitter.DrawQueued`, `Particle.vert`/`.frag`; the page material's preset for mode 2, `ParticleData.GetPageBlends`), the hexagons over a copy of the frame (`ParticleDistortion.vert`/`.frag`), and leaves out what the game never draws (`ParticleBlendModes.IsDrawn`). The simulation reads the systems and emitters every frame (their curves sampled at the 64 steps once a frame, `ParticleSimulation.PrepareSteps`) and lines its cycle up again when the timing changes (`ParticleSimulation.Rephase`), so every edit shows right away; the default chunk's viewport plays every default system on a grid ignoring the camera (`DefaultParticleData.GetViewportObjects`). The curves are edited on a graph (`CurveGraph`) and the color on a gradient bar with a color picker (`GradientBar`), both through `ParticleCurveKeys`, which keeps the keys in order and the curve's end at 1; a key put in or taken out with the keys it moves is one step, so is a drag. A system's picture (`TexturePage`, `TextureStart`, `TextureEnd`, the corners hidden with `[EditorHidden]`) is edited as a rectangle of pixels on the page (`ParticleTextureRect`: `FromGame`/`ToGame` keep a corner's offset and fraction while its pixel stays, a start after the end mirrors) with `ParticleTextureViewModel` and `Controls/ParticleTexturePage`: the default chunk's three pages to pick from, the page with the game's pictures outlined (`ParticleTextureBank` clusters the usable systems' rectangles within 3 pixels) to click, the rectangle and its corners to drag (one step each), typed pixels and mirroring. Every particle item of both discs round-trips byte-identically. Systems', emitters' and decal variants' names are read up to their NUL (`ParticleNames`), what the tools left in the 16 (8) character buffer after it (the default chunk's systems, some level emitters) is kept in `NameLeftover` and written back, an emitter's name has to match its system's. A system's name is its own in its chunk (`ParticleSystemNames`): emitters play their chunk's own system of a name before the default chunk's, so a level's system of a default system's name is the level's own version of it, played there in its place (a PS2 project's levels have 5). The name field refuses a name another system of the chunk has and says so (`ParticleSystemNameFieldViewModel`, `TextFieldViewModel.CanCommit`), a pasted system keeps its name unless another of the chunk's has it (a default system pasted into a level becomes the level's version of it), one put into a list otherwise gets a free one, for a level's none of the default chunk's either (`NEW_SYSTEM`, `NEW_SYSTEM_2`, numbered within the 16 characters, `MakeUnique`'s `avoidsDefaults`: it would take that one's place by accident; the default chunk's names read from its file in the background while nobody has it loaded), the emitters' picker offers the chunk's version and not the default system it takes the place of (`ParticleSystemChoice.Overrides`), and renaming one takes its emitters along (`ParticleSystemLinks`): the emitters of the same particles that played it as part of the rename's step, and once the default chunk's particles are saved with a system renamed, whichever editor saves them (`DefaultParticles.DataSaved`: the systems as the file had them, kept with the data from its first change of their names or list, against what's written; started once the saving document's save is done, `ParticleSystemLinks.FollowSaved`; a later system of a repeated name renamed takes nothing along), the emitters of every other chunk of the version that play it (not those whose chunk has a system of the old name, which they play instead; a chunk with its own system of the new name plays that with them, which the log warns about), in the background, through the document of a chunk that's open, logged when done (the unloaded chunks' file paths taken before it, so nothing in the background looks at the open project; a chunk file that doesn't read is logged with its path, the others are renamed). Closing the project, opening another or closing TT Lab waits for a save's follow (`ParticleSystemLinks.WhenFollowed`, which first starts the renames a save that failed after writing the particles left, from `EditorsViewModel.SaveOrDiscardUnsavedChanges`, before the unsaved editors are asked about and after the saves it makes, which then saves what the follow renamed in open editors; `ShellView.OnClosing` while `ParticleSystemLinks.IsFollowing`, which counts those renames too): only the renaming document's save followed a rename, the follow wasn't waited for, and the project closed under it. The build warns about emitters of a system neither their chunk nor the default chunk has (`ParticleData.Export`), which the game makes none of. Two systems of a name in one chunk are only the default chunk's four `XXX` and l10chasb's two `IIG_SMOKE` in retail, their fields show it.
  - The default chunk's particle data also holds the **decal** system (footfalls, ripples): `UnusedDecalInt`, the `DecalUvPacket` (a VU1 packet of UV rectangles the game writes its GIF tag over), 16 `DecalTypeMarkers` (the tools' pointers, nonzero means a type follows) and the `DecalTypes` (`TwinDecalType`, 0x890 bytes: DMA tag, 15 variants of 4 color keys with alpha in W and 4 size keys with the time in W and the lifetime in the first's, the count, the variants' names). - **PSMs** (`PSMData`, a list of PTCs: a texture and a material each) are the game's tile pictures: the legal, loading, game over and credits screens and the gallery are 8 tiles of 128x256 laid 4 across from the top left (512x512), the level titles one 128x128 tile, and `Startup/Icons.psm` is 40 icons (64x64, 32x64, 32x32) the game reads into the HUD's slots by their order and draws one at a time. Every part is kept upside down, like a font's pages. `PsmEditorViewModel` (`PsmEditorDesc` on `PTCs`, `Controls/PsmPicture`) shows the parts the right way up as the picture (`PsmLayout`: tiles when they're all the same size and 1 or a multiple of 4 of them, never for the PSM named Icons, whose icons go on a sheet), replaces the whole picture (tiles only) or the picked part with an image (resized to the picture's or the part's size) and saves either as a PNG. - **Fonts** (`FontData`) are edited with `FontEditorViewModel` (`FontEditorDesc` on `CharacterData`): every page with its characters' boxes drawn over it (`Controls/FontPageEditor`: the game keeps its pages upside down, the editor draws them the right way up (`GetShownRect`, a box's top row shown at `height - Bottom`, dragging down lowers `Bottom`) while the page's texture and a replaced PNG stay the game's way; clicking picks the character, dragging moves the box, dragging its bottom right corner resizes it, one history step per drag), the character table (code, page, left, bottom, width, height, edited through the document's nodes), adding and removing characters at the end, and replacing the selected page's picture with a PNG (8 to 256 pixels, powers of two; it replaces the page's texture asset right away, which no history can undo).

- Sounds are one asset per language and content, a sound item's hash doesn't cover its samples. A PS2 sound plays at its `Pitch` (`ITwinSound.PitchOf`: the sample rate times 4096 over 48000, truncated, handed to the driver by `FUN_001dfa38`), kept on the `SoundEffect` asset and set from the wav's rate when one is replaced or when a sound is made of a wav (`AssetDataFactory.CreateSoundEffectData(asset, wavePath)`, which the Create Asset dialogue's overload hands the file picked; it takes the wav's sampler chunk's loop in whole blocks like Replace; it kept 22050 Hz's pitch, and a 44.1 kHz wave played at half speed); the Xbox item keeps the rate and derives it. The loop is the `SoundEffect` asset's `LoopStart`/`LoopEnd` (samples, the end exclusive, -1 without one), set on import from `ITwinSound.LoopStart`/`LoopEnd` and handed to `SetDataFromPCM` on build. The sound's editor draws the waveform (`Controls/SoundWaveform`) with the loop's handles to drag, playback following a click or a drag anywhere else on it, and buttons for the loop's start or end at playback, the whole sound or no loop (`SoundEffectViewModel`, whose node is the data's `[custom_editor]` one: the loop's nodes are the asset's), all in blocks of 28 samples through the document so undo covers them, and the preview plays the loop (SoundFlow's loop points); replacing the wav takes its sampler chunk's loop (`Riff.LoadRiff` reads chunks by their headers now) or loops the whole new sound when the old one looped.

New triggers are kind 50 checked every 0.3 s (kind 0 is the sound code's plain box), new cameras' triggers `0x140000` with no interval, like most of the game's, and both are set off by the playable character (`ObjectActivatorMask` bit 0 alone, `TriggerData.NewActivators`: every camera and 643 of the 678 triggers of a PS2 disc's levels have it, none has none; a camera without it is never taken).
- **Combo box editors** (enums, sample rates, layouts, render buckets, a slot's animation) ignore what the combo box hands back while they show a value (`_isShowing`) and give it a new list only when the choices change: a combo box whose list changed handed its old pick back, which the OGI animation field and the value then passed back and forth until the stack ran out, and a list changed in place made it pick items it no longer had.

### Rendering (`Rendering/`)
- A custom Silk.NET OpenGL renderer draws to an offscreen framebuffer, which is shown in Avalonia via `Controls/Viewport.cs`. It uses render passes (`Passes/`), batches, a scene graph (`Scene/`) and gizmos. GLSL shaders live in `TT Lab/Media/Shaders`. Math uses GlmSharp (`vec3`, `mat4`), and `Extensions/GlmExtensions.cs` converts to and from Twinsanity vectors.
- GL work must be queued onto the render thread (`RenderContext.QueueRenderAction`), and UI work onto `Dispatcher.UIThread`. Scene graph structure (adding and removing children) changes on the render thread. Transforms, colors and visibility get set from the UI thread. What the render thread reads the UI thread may be changing: the selection it draws is an array replaced whole (`EditingContext`), a resource's objects are made again for the asset its node had when the rebuild got queued, not for whatever a later undo put at the node's index (that made another resource's objects twice), only while the node is still in the graph, and a rebuild reading the graph while the UI thread changes it (undoing many steps in a row) is tried again (`RebuildAttempts`); removals of gone resources are worked out when they run, and `Renderable.RemoveChild` only removes the child itself, never another one of its name.
- Each `ViewportViewModel` owns a `Controls/ViewportHost` for as long as its editor is open: the GL context, the render thread and the frames. The `Viewport` control only shows the host's frames and passes it the input while it's attached, so switching tabs or floating them never rebuilds the scene. The context's window is a hidden 1x1 SDL window only there to make the context current, frames go to a framebuffer of the host's (`RenderContext.OutputBuffer`).
  - The host renders at 60 FPS while it's shown and reads frames back through pixel buffers a frame late. A viewport that isn't drawn for half a second (a hidden tab) only processes its render queue until it's drawn again, and keeps invalidating its control meanwhile: Dock keeps the content of tabs that aren't shown, only hiding it, and a control shown again doesn't draw until something invalidates it.
  - SDL's GL driver stays loaded for the whole run: SDL unloaded it with its last GL window, which crashed the driver while Avalonia and other viewports still used it. A hidden window's context stays current on a thread of its own for the whole run too (`ViewportHost.PinGlLibrary`, the "GL Anchor Thread"): with NVIDIA's EGL on Wayland, a TT Lab that had created a project got no new context once no thread had one any more (the prefab pictures' viewports come and go right after creating), every viewport opened after them failing with "eglMakeCurrent failed, reporting an error of EGL_SUCCESS" until TT Lab restarted; a context left not current didn't help. TT Lab makes it as it starts (`ViewportHost.MakeGlAnchor` from `App`): made by the first viewport, it couldn't be made either after unpacking the game's assets for a project without them. Exceptions on a render thread and GL errors get logged instead of ending the application.
  - Viewports don't use ImGui, its one global context got corrupted by render threads using it at once. Overlays are Avalonia controls over the `Viewport` (`ViewportView`).
  - GL objects kept for as long as a viewport (the renderer's buffers, the vertex pool, the material table, the indirect draws' buffers, `ScreenCopy`'s copy, the particles' batch) are deleted on `RenderContext.Destroy`, raised on the render thread with the context current as the host closes, after it deleted its output framebuffer (`OutputBuffer` is 0 then, what's released binds that). The contexts share no objects, so what nothing deleted went with the context, owned by nobody until then.
  - Until the scene renders the viewport says what it's loading in the game's font (`ViewportViewModel.Loading.cs`, `Controls/GameText`: the package's font with the most glyphs, `PsfGlyphs.OfDefaultFont`, cut out once per font's data; the game's texts spell words in lower case, which its font draws as small capitals, and its capital C, E and Î are controller buttons, so those get the small capital): reading assets (every asset the document's property graph reads, `PropertyGraphTracker.AssetRead`, with a running count), starting the renderer, building the scene (each chunk resource named like the Chunk Resources panel's folders, `ViewportContext.Progress`, with a progress bar). Reports come from any thread, the UI shows the newest (`ReportLoading`).
- Every draw is instanced. Before the passes, each `IInstancedRenderable` (`RenderBatch`, `BillboardSet`) writes its instances' model matrix, color and light set (lit materials, see Scenery lights; a second storage buffer) into `RenderContext.Instances`, a storage buffer the shaders index with `gl_BaseInstance + gl_InstanceID`. A `RenderBatch` draws all meshes of a model with one draw per shader of its material. Meshes that need their own uniforms (`RequiresIndividualDraw`: skins, blend skins) get one draw each. Gathering every mesh of a scene every frame took longer than drawing it, so a batch of unlit meshes keeps its instances where it wrote them (`InstanceBuffer.Keep`, `RenderBatch.PrepareKeptInstances`) until one of its meshes changes what it draws (moved, shown or hidden, recolored, joined or left the batch: `Mesh.OnDrawnChanged` → `RenderBatch.MarkChanged`, queued on the context), and an emptied batch gives them back (`BatchStorage` keeps every batch); lit batches (their light sets are the frame's), batches with meshes drawn on their own and billboards write theirs every frame after the kept ones. An object keeps its light set while the scene's lights and its position stay (`Renderable.AnchorLight`). What the UI thread sets (transforms, a skin's bones, a blend skin's weights) reaches what the render thread draws through the context's queue (`Renderable.QueueRenderTransform`, taken after every frame and before prefab pictures, `RenderContext.FlushRenderTransforms`): every renderable of the scene took its transform every frame.
- **Meshes made again are let go of** (`Rendering/Services/RenderCache`, `MeshService`): a context's meshes by URI are handed out until they're forgotten (`Forget`: an OGI's material slots changed, data replaced whole) and released once no batch draws them (`MeshService.ReleaseUndrawn`, run by the `Renderer` once the render queue is done, `RenderContext.RenderQueueProcessed`, hidden tabs included, and only after a mesh left the scene or more got forgotten): their models' vertex pool ranges or own buffers (`ModelBuffer.Release`), a blend skin's offsets texture (`Mesh.ReleaseBuffers`), and their batches out of `BatchStorage`, the frame's batches and the passes (`BatchStorage.Drop`, `PassService.UnregisterBatches`). Meshes join their batches as they're added to the scene and a rebuild takes the old objects out and puts the new ones in in one render action, so nothing released is drawn again (`BatchStorage` asserts it). Data replaced whole (`ViewportViewModel.ForgetMeshesOf`: a model Blender wrote, that undone or redone, in its viewer and every scene drawing it) forgets the meshes of the asset's own URI; its parts' URIs are of their content (`SerializableAsset.SetData` appends the data's hash to an internal asset's name), so they keep their meshes while the new data's objects draw them and go once nothing does (`ForgetWhenUndrawn`). Every part used to be made again and nothing let go of the old copies: every Blender save, undo or redo of sch_hub's scenery (49 MB of vertexes) added one to the GPU and its empty batches to the passes, which the indirect draws went through every frame, until the tab closed. A kept part keeps the material looks it was made with, as a scene doesn't follow a material edited elsewhere. `RenderCacheTests`.
- **Data replaced while a scene is built** (`ViewportViewModel.RememberReplacedWhileBuilding`): replacements arriving while the scene is being built (a context but not `_renderInit`) aren't dropped. A picture's refresh is queued, which runs after the render action building the scene; a model another document replaced (found by `Draws`) or the scene's own document did (by its node) is remembered, its objects forgotten and made again once `FinalizeSceneInit` ran (`RebuildWhatWasReplacedWhileBuilding`, after what's inspected got selected). The finished scene drew what the building had read of the old data until the tab was opened again.
- **Draw order** (`Services/PassService`, `SceneOrder`, verified in the decomp's `buckets.cpp`/`materials.cpp`): the game draws its 28 buckets one after the other, every shader type mixed and blended or not, nothing sorted by depth. In a bucket the skins and blend skins come first as they're submitted (drawn straight into it), then every other material in the order of its first draw, all of its draws together: model after model by their first draws, each with every shader of the material in turn, all in the material's bucket. The game submits the sky, the camera chunk's scenery in its tree's order (a node's meshes, LODs and dynamic scenery, then its children), the linked chunks', then the instances, the order TT Lab makes their batches in (`RenderBatch.Sequence`), which stands for the game's: a chunk's scenery and links make their objects first whatever order it lists its resources in (`LevelChunk.GetViewportObjects`; an Xbox chunk lists its instances first, and every object's material was drawn before the scenery's). A model's instances go into a block that opens at its first draw (models.cpp's `WriteSubModels`), and the build makes one model of the placements of the same parts and materials, while each placement is a model of its own in TT Lab: a material's draws go by the game's model (`ModelBuffer.GameModel`, `MeshFactory.GiveGameModel`: a hash of its parts' vertexes and materials in their scenery or model), its parts one after the other (`PartIndex`), so roof05's two landscape billboard meshes of 8 placements each are drawn one after the other and not in their tree's order. Not like the game yet: a block holds 8 to 18 placements in view and the next one opens another (TT Lab draws a model's placements together), the game lists the materials it draws in a frame (TT Lab goes by every batch, the LOD levels not drawn and what the game culls included: replaying LOD levels on every PS2 scenery changed no retail frame), a dynamic model is drawn at its tree cell (TT Lab after the placements; the retail blended ones are additive, whose order doesn't show), and a scene doesn't follow a material edited in another editor (its passes, order and looks come when its batches are made, as before). TT Lab draws the sky's pass (type 10 shaders, `SkydomePass`), then the scene in that order in two passes (`ScenePass` for the buckets up to 22 and `LateScenePass` after it, the particles between them: the game draws the particle pages in bucket 22 after the level's own materials of it), then its own: volumes, previews, the icons (`CUSTOM_BILLBOARDS`). Every pass entry is a renderable drawing itself or one shader of a batch's material (`PassEntry`, `RenderBatch.RenderShader`, `ModelBuffer.Bind(shader)`). TT Lab's own see-through visuals (the markers of positions and the like, MeshFactory's built-ins) go in `RenderBuckets.EditorVisuals`, after the game's. It drew every opaque pass and then every blended one, a pass per shader type ordered by the bucket minus `ShaderColor.W` (a leftover the game never reads for ordering): in 106 of the PAL version's 135 chunks blended draws came in another order than the game's (487 pairs where the earlier one wrote depth over see-through texels), roof05's bucket-6 landscape billboards came after its bucket 8 and 10 mists (the mist now veils them, as in the game), the glass materials' two shaders came the other way round and a material with two shaders in one pass drew its first one twice.
- Go through `RenderContext.State` (`GlStateCache`) for blend, depth, culling, polygon mode, programs, textures (`TextureBuffer.Bind`), samplers and vertex arrays, and never read GL state back in the render path, because it stalls the driver. The bindings are forgotten at the start of every pass (`ForgetBindings`: what's outside the cache binds too), so a pass's first bind is always made. Materials set their state and leave it, the pass puts back blending, the depth mask and test and unit 0's sampler at its end when one was bound (`Renderer.PerformPass`, `GlStateCache.MaterialBinds`; `TwinMaterial.Unbind` put them back after every draw). Uniforms set every frame or draw are `KnownUniform`s whose locations get resolved when the program links. The Generic program reads a material's values from the context's `Materials/MaterialTable` (binding 6, `TwinMaterialEntry` in `TwinMaterial.glsl`, the entry's index in the `MaterialEntry` uniform): set as uniforms they were 17 calls for every batch drawn. Materials of the same values share an entry (`MaterialTable.Key`, the scrolls only of materials that scroll), the scrolling ones get the UV offset of the frame's time before it's drawn (`Prepare`), and past 16384 entries (editing a material makes one of every value it goes through) the table starts over before a frame, every material looking its entry up again (`TwinMaterial.Resolve`, by the table's `Generation`).
- The models' vertexes are in one buffer per context (`Buffers/VertexPool`, one vertex array of the rigid layout, every model drawn from its `FirstVertex`, `RangeAllocator` handing out and taking back ranges): a vertex array per model made every draw switch arrays, which cost the driver more than the draw. Models made again in place (collision, the material preview, blend skins) keep a buffer of their own (`MeshBuilder`'s `ownBuffer`). With bindless textures (`BindlessTextures.Of`: ARB_bindless_texture, and NV_gpu_shader5 for handles that differ between the draws of a call; NVIDIA's drivers have both) the passes' batches are drawn with `glMultiDrawArraysIndirect` (`IndirectDraws`): batches in a row whose materials set the same GL state (`TwinMaterial.DrawsLike`) are one call, every draw reading its material entry and texture handle at `DrawBase + gl_DrawID` (binding 7, `MainPass.vert`), and what can't be (skins, billboards, previews, models of a buffer of their own, materials without a texture, that can't be made or that draw the fragments failing their alpha test apart, the first draw of a material taking a copy of the frame) is drawn the way it was, in its place. The calls are made again when the passes' renderables, the material table, a texture's handles or which batches draw meshes on their own change, otherwise only the draws of the batches written this frame change. Without bindless textures every batch is a draw of its own. On sch_hub (3440 draws, 55 calls) the render thread took 26 ms a frame in a Debug build (18.6 in Release) while the GPU took under 2: now 2.5 to 3 (2 in Release, 6.8 without bindless textures), and frames wait for the 60 FPS loop (2026-10-13).
- `PrimitiveRenderer` draws editor visuals immediately each frame: thick anti-aliased lines, boxes, spheres, cones, cylinders, quads and discs, and grids (one quad each, with the lines worked out per pixel), in the `World`, `WorldXRay` (faint where hidden) or `Overlay` (always on top) layer. Submit from `IPrimitiveRenderable.DrawPrimitives` (picked up when registered for rendering) or `Renderer.DrawPrimitives`, both on the render thread.
- Collision has nothing to light it by (its material is unlit, its colors the surfaces'), so its buffers draw with the editor's flat shading (`ModelBuffer.EditorShading`, `TwinMaterialDesc.EditorShading`, `twin_material.editor_shading`): `MainPass.frag` takes the triangle's normal from the position's derivatives (before the alpha test can discard any fragment) and lights it from above and from the eye, whichever way it faces.
- A dynamic scenery model's `BoundingBox` is in its own space (the game's are a few units around the origin while the animation moves the model far away), so the chunk viewport draws each box through its model's current transform (`Rendering/Objects/DynamicSceneryBounds`, `DynamicSceneryMesh.ModelTransform`, the "Dynamic scenery bounds" layer). The viewport plays a dynamic scenery model's animation the game's way (`DynamicSceneryPlayback.At`, the decomp's `DynamicSceneryNode::Animate`): 25 frames a second over the model's frames (`AnimatedFrames`, no more than its animation keeps), the time taken back a loop at a time once it's past the last frame, which blends into the first. It played 50 a second stepping a frame at most once an update and dropping the time past it, 1.2 times the game's rate at 60 FPS and slower as the viewport slowed down.
- Materials have a viewport (`[SupportsViewport]`, `MaterialData.GetViewportObjects`): a sphere standing on the floor drawn with the material (`Rendering/Objects/MaterialPreview`, `MeshFactory.CreateMaterialPreview`; its vertexes have the colors the game's models of the kind mostly have: 128 for the lit types, lit by the default lights, 255 for the rest), updated in place on the render thread when the material's data changes (`ModelBuffer.ReplaceMaterial` makes its looks again and moves the batch to the passes they draw in), a new sphere only when it turns lit or unlit.
- **Preview passes** (`Passes/PreviewPass`): what's about to be placed (a prefab dragged over a scene) is under a renderable that `DrawsAsPreview`, whose meshes get batches of their own (`BatchStorage` keys batches by model and `Renderable.IsInPreview`: a batch draws every mesh of its model in one draw, the scene's included) in two passes after the scene, once the depth is complete: the first draws them with their materials' shaders (`ModelBuffer.Bind(shader)`, a preview's pass has no shader of its own) and marks the pixels they show on in the stencil, the second draws them again without the depth test where the stencil isn't marked, in the instances' color (`DiffuseOnly`, the preview's tint is see-through) and incrementing the stencil, so every hidden pixel is blended once. The stencil state goes through `GlStateCache.SetStencil` (always passing and writing nothing outside them), the output framebuffer is depth 24 stencil 8 (`ViewportHost`).
- Triggers' and cameras' boxes are volumes (`LabURI.Volume`), drawn after the scene and its particles without writing depth, their insides and then their outsides (`VolumePass`, culling front faces and then back faces), so each pixel blends in the same faces whatever order the triangles are in. Their faces are wound counter-clockwise seen from outside, like `PrimitiveMeshes`, which GL renders as front faces (only `FrameCamera` mirrors).
- **Skydomes** (verified in the PAL executable, `Ghidra Stuff/Engine_RE`): a chunk with a sky draws it first instead of clearing the frame (`FUN_001ba350`): the parts of its meshes in their order, at the camera's position (the model matrix is only that translation), into a buffer of half the screen's size (`FUN_001ba488`), then copied over the whole screen two pixels for one with the depth reset (`FUN_001ba6c0`), so the level always draws over it. Every retail sky material is shader type 10 in bucket 0 testing no depth, some blended. The type 10 program (VU1 code 0x2e3ec0) takes its matrices from the 9 quad words 78 past the buffer's base (`3(vi00)`) that only the sky's drawer uploads (`FUN_001c1f90`), never the model's own block (`2(vi00)`, which the level's drawers write): a type 10 material on anything else draws with the last sky's matrix, around the camera at half size in the middle of the screen, and a sky part of another type with whatever object block was left. TT Lab draws every type 10 shader around the camera in one `SkydomePass` (`FollowsCamera` in `MainPass.vert`, `ModelBuffer.NamedPassOf`/`SkyPriorityOf`, `PassService.RegisterBatch`), in the order of the sky's meshes and parts (`ModelBuffer.DrawOrder`), into a half size buffer blitted over the frame (`Renderer.RenderSkydome`). The frame's alpha isn't shown (`ScreenHorizontalFlip.frag`): GL blends it along with the color, and the alt earth sky's subtracting sun left pixels the window showed through. The PS2's fog goes over the sky and the cleared background in a pass of its own (`Renderer.RenderBackgroundFog`, see the game's look).
- **The game's look** (the decomp's renderer, checked on 2026-10-12 against PCSX2 pictures of the beach, Alt Earth's hub and High Seas taken from the game's own camera: the harness's `pcsx2look` mode saves `G_RendRel`'s matrices next to its pictures, and the game squeezes its 4:3 view into the letterbox band at a level's start). Sampling (`GsTextureFiltering`, `TextureSamplers`, the decomp's `MakeSettings`): the magnifying filter is the shader's bit, and the types that minify through mips pick the level by the distance alone, LOD = log2(clip w)·2^L + K (TEX1's L and K as the game ORs them in sign-extended), the nearest level filtered bilinearly, from as many levels as the PS2 build gives the texture (`PS2AnyTexture.LevelsOf`, down to 8 pixels; GL averages them); retail K is -69/16, sharp up to 28 units. The environment, metallic, particle, sky and UI types draw the largest level, the metallic and UI types and the screen copies clamp. The alpha test (`GsAlphaTest`) compares the GS's alpha (TT Lab's times 127 rounded down, 128 being 1) with the reference byte by the method, a failing fragment written by what its AFAIL keeps of what the passing ones write (`GsAlphaTest.FailDrawOf`, `AlphaFailDraw`): left out (KEEP, ZB_ONLY without depth writes), drawn with the passing ones (FB_ONLY without depth writes) or apart, where it writes something else (FB_ONLY and RGB_ONLY without the depth the passing ones write, RGB_ONLY without alpha, ZB_ONLY only depth): GL can't leave a write alone for some fragments of a draw, so such a part is drawn twice a triangle at a time like the GS writes them, the triangle's passing fragments with the material's writes, then its failing ones with their AFAIL's (`RenderBatch.DrawApart`, `TwinMaterial.BeginPassing`/`BeginFailing`, `ModelLayout.frag`'s `AlphaSubpass`), and such batches stay out of indirect runs: drawn an instance at a time, like PCSX2's hardware renderer draws them, an earlier triangle's failing texels covered later triangles behind them, which the nitro crate's broken pieces show through them (13% of a piece's pixels from one side). A flat part (`MeshBuilder.IsFlat`, no triangle over another: the school's billboards) or one of more than 256 triangles is drawn an instance at a time. The see-through texels of the school's landscape billboards (GEQUAL 125, FB_ONLY, writing depth: roof01, roof03, roof05, buschase, crgpa04) were drawn with their depth and hid the billboards and particles drawn after them (8 retail shaders draw apart; it compared against the reference over 255 whatever the method before). The depth test applies whether the depth is written or not. Scrolls (`ShaderScroll`, the decomp's `UpdateShader`): Linear wraps the phase (`UvScrollSpeed` X and Y moved on by Z and W turns a second), LinearPlus_1 is its sine, LinearPlus_2 its cosine into V's offset (V's own scroll takes over), added to the UVs and the environment maps' lookups; they all scrolled linearly before. Fog (`GameFog`, the scenery's `FogColor`, `SceneryData.GetFog` by the chunk's version, `RenderContext.Fog`): the PS2 version draws the frame over itself through the table once the buckets 0 to 3 are drawn (`FilterColours` in bucket 4, before its materials): bits 8 to 15 of the depth below 65536 (the lens's 0.1 to 1500, 2^23 - 1 times one minus the clip depth) pick the entry, nothing nearer than about 25.6 units, 12% at 50 units, 23% at a hundred, 40% at a thousand of the table's color, and the sky and the background (depth 0) 30% of entry 0's. The copy of the depth through 16 bit formats (`CopyDepthBuffer`, read back as PSMT8H) moves those bits where the palette lookup reads them. TT Lab fogs the fragments of those buckets (`twin_material.fog`, not the editor's own visuals) and the sky and background in a pass of their own; the Xbox version (`DrawToTexture` 0x103f50, stage 1) blends a 256 texel ramp of the same tables, which its executable keeps in the PS2's palette order, over every 3D material's fragments by the clip depth times 0.02, a running mean of 16 entries' (0.5 - a/256): half as strong, all of it from 50 units on, the sky at its end. A chunk's viewport clears black like the game (`SetUpFrame`), the others stay grey. Checked by distant trees on the beach: (64, 56, 37) against the game's (64, 53, 33), (45, 42, 29) with the made-up fog before. LODs (`Objects/LodVisual`): a chunk's LODs (its scenery's and its links') draw the level the game picks by the camera's squared distance (`LodMeshAt`: the next level past each switch), here to the middle of the box the LOD is culled by, chosen on the render thread before the batches gather their instances. The game also draws none nearer than the nearest or past the farthest distance (-1 none), which the viewport only does while its toolbar's LOD culling button is on (`ViewportViewModel.CullsLods`, `RenderContext.CullsLods`, the `ViewportLodCulling` preference every viewport follows, off by default: the beach seen from far away leaves out 537 of its 774 LODs then); prefab pictures and previews draw the closest level. Not like the game yet: the characters' shadows (the scripts give each character its shapes), the 16 bit dithered output and the PS2's frame size, and the Xbox version's colors (drawn the PS2's way but for the fog). The editor's camera keeps its own 60 degree lens.

The scene viewport's one-key tools (Q, T, R, E, L, F; `ViewportViewModel.UseToolKey`) ignore keys pressed with Alt: Alt+Shift+L flipped the transform space too. `ProjectTreeLocateTests`.
- **Moving and duplicating** (`Assets/AssetRelocation*.cs`; renaming a folder in the tree is moving it into its folder under the new name, `AssetRelocation.RenameAsync`: only its alias changed before, the next look at the disk took it out and read the directory of the old name back; the tree's Duplicate and Move To... entries, rows dragged onto folder rows, which are marked while they'd take them): what the tree shows moves into a folder where Create Asset would make it (`Destinations`: chunks in a package's levels folder and the folders in it, folders in a package's folders, the other assets in folders outside the levels folders; not where something has its name) with everything under its directory (a chunk's folder takes its instances, scenery and materials, which no folder of the tree lists). They stay: the startup's Crash.ico, Frontend, Decal.ptc, Icons.psm, LevelSelect.txt and the default chunk (`FixedReason`), a folder holding one, instances (copied with Ctrl+D and as prefabs), packages (duplicated only, root packages not); PSMs, fonts and text files are duplicated but not moved (`StaysReason`: the build only writes the game's pictures, fonts and texts where they are), nor a folder holding one. Links follow as text (`AssetLinks`): every JSON string of an old URI in assets' metadata (`MetadataLinks`/`RemapMetadata`: references, a chunk's resources, versions, sky and own values, folders' children), their data files, model files' JSON headers (materials, collision surfaces), scripts (`BehaviourScriptLinks`, by the lexer: a URI string gets the new URI, a name that finds something else from where its script is now names what it found before), prefabs and build profiles. What links to what moves is found by what assets reference (their metadata), model files and scripts. Moving to another package takes along what it links to that the package can't link to (to the same place in that package, asked first; the other version's game objects, instances and behaviours whatever the package depends on) and asks to add the package as a dependency of the packages linking to what moves; a move within one package (a folder renamed too) adds none, what linked to it from a package that doesn't depend on it did before (`AddDependencies`: it was refused when a root package linked to it). A root package linking to what moves to another package refuses the move, and so does an asset of the old version using game objects, instances or behaviours that would become the other version's (`CheckVersions`). Chunks get their new path (their instances' `Chunk`, the assets in them `AdditionalPath`, the level select's line, `LevelSelect.MoveChunk`). Files move first and are put back when one fails (`FileJournal`), the editors of what's affected close first (asking about unsaved changes) and the move is planned again after them. Duplicates are made of what's saved, named the way Windows names copies (`Name (2)`, `Name (3)`, `SuggestName`) and given the lowest free IDs of their kind (`IdAllocator`, graphs odd ones); copies made together link to each other (scripts name a copy by its URI when its name isn't an identifier), a folder's or package's copies are named one by one or all at once, a chunk's contents keep their names and IDs, the SkipExport parts of the game's files (a PSM's or font's PTCs and their textures and materials) are copied along into a copy of their folder, copied chunks go into the level select, a copied package depends on what the original does and the project's package on it. The dialogues are hooks tests answer (`AssetRelocation.Ask`, `AskName`, `AskFolder`). `AssetRelocationTests`, `ProjectTreeDragTests`.
- **Open Asset** (Project > Open Asset..., Ctrl+Shift+O, `ShellViewModel.OpenAsset`, `Controls/QuickOpenDialogue`): a dialogue finding any asset of the project by a fuzzy search of its name (`Util/FuzzyMatch`: every character typed in order in any case, the best way of lining them up scored by runs, word starts, an early first match and a short name; `Assets/AssetSearch`: every word typed in the name or, at half the score, the asset's package and folders from its URI), Up/Down/PageUp/PageDown picking among the best 100, Enter or a double click opening it like the project tree does, Escape giving up. Offered: every asset but internal ones, folders, disc files and level chunks' resources (`SerializableInstance`s of a non-default chunk's path, edited in their scenes; the default chunk's open in their own editors). The assets are read and searched off the UI thread, a search starting 40 ms after the typing stops and dropping the one before it: in the app (2026-10-11, the user's PS2 project) the 27,555 assets offered were read in 0.16 s and a search took 60-190 ms after the last key (`QuickOpenTests`).
- **Names are plain ASCII** (`Util/NameRules`): the game keeps names and paths a byte per character, the characters past that became '?' in its files and two names differing only in them got the same path. Assets' aliases, materials', instance templates', particle systems', emitters' and decal types' names (`TextFieldViewModel.TextFieldAsciiOnly`), new assets and projects, renames in the project tree and the chunk's resources and the names of moved or duplicated assets refuse other characters, a paste turns them into '?' (listed with what it limits).
- **Hot reload** (`EditorsViewModel.ReloadChangedFiles`): data files another program writes under `assets` (`.data`, `.tlm`, `.lab`, `.png`, `.wav`, `.txt`, written, made or renamed over, once the writes stop for half a second) make the editors showing them again. TT Lab's own reads and writes are told apart by the file's length and write time (`AssetFileStamps`, recorded by `AbstractAssetData.Load` after what loading writes itself, and by `Save`), and a file written within 2 seconds of being recorded by its content as well: file systems keep write times to their clock's tick, and on Windows another program writing as many bytes right after TT Lab saved got the same length and time and went unseen. A changed asset counts while it's loaded or a tab shows it: its document reaches it (`GetReferencedAssets`) or its scene drew it (`RenderContext.ReadAssets`: the textures, materials and meshes the render services and `MeshFactory` read, which a chunk's document doesn't reach, `TabbedEditorViewModel.Shows`). - Log with `Log.WriteLine(text, Log.LogType.X)`. Every line is appended and flushed to a session log file straight away, together with unhandled exceptions. The Log panel gets the lines in batches, at most every 100 ms at background priority, the last 500 of them as one edit (`Log.FlushPendingLines`): a dispatcher job and an edit of the panel per line ran ahead of input and rendering, and 2000 lines a second froze the UI for 22 s (`LogPanelTests`). The tests' application has neither. ## Code style

Match the surrounding file. The codebase spans several eras, so consistency within a file matters more than uniformity across files. For new code:

- **Comments**: avoid verbose comments. Only add comments that describe hacks, workarounds, or code whose intent isn't obvious (bit layouts, format quirks, ordering requirements). Don't narrate what the code does and don't add XML doc comments to new members, except in TwinTech public interfaces or files that already document every member.
- **Namespaces**: use file-scoped `namespace X;` in new files. Don't convert existing block-scoped files unless you're rewriting them.
- **Braces/layout**: Allman braces, 4-space indent, braces even for single-statement `if`s. Prefer early-return guard clauses. Put a blank line after a closing block before the next statement.
- **Naming**: PascalCase for types, methods, properties and public/protected members. `_camelCase` for private instance fields. PascalCase for `private static readonly` fields. `UPPER_SNAKE_CASE` for game IDs in `Constants`. Interfaces for game items are `ITwinX`, PS2 implementations are `PS2AnyX`/`PS2X`, and asset data classes are `XData`.
- **Types**: `.editorconfig` doesn't force C# keywords. For binary-format fields and game data (TwinTech items, asset data mirroring game structs) use explicit BCL names (`UInt32`, `Int32`, `UInt16`, `Single`, `Byte`) so widths are obvious. Elsewhere, new code uses keywords (`string`, `bool`, `int`).
- `var` for locals, target-typed `new()`, and collection expressions (`[]`) in TT Lab. Not collection expressions in TwinTech (C# 11).
- Use hex literals for IDs, masks and bit shifts (`_header >> 0xB & 0x1`), and `{id:X}` when formatting IDs.
- `nameof(...)` for property-change notifications and attribute references.
- `Debug.Assert` for internal invariants. Throw exceptions for bad input or game data.
- `using var` for streams, readers and writers.
