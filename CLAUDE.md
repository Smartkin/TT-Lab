# CLAUDE.md

TT Lab is a modding toolkit/editor for **Crash Twinsanity** (PS2 and Xbox). It unpacks the game's disc files into an editable project of JSON assets, lets you edit them in an Avalonia UI with a 3D OpenGL viewport, and repacks them into game archives/ISO.

## Build & run

```bash
dotnet build "TT Lab.sln"
dotnet run --project "TT Lab/TT Lab.csproj"
```

- Targets .NET 8 (`global.json` rolls forward to newer SDKs).
- The build has around 3.4k pre-existing warnings, so only errors and new warnings in code you touched matter.
- Tests: `dotnet test "TT Lab.Tests/TT Lab.Tests.csproj"` (xUnit) and `python -m unittest discover -s tests` in `TT Lab/BlenderTools`. They never use game data. Build made-up data in the test instead (see `Support/TestAnimations.cs`).
  - `Support/TestProject` opens an empty project with the base packages in a temporary directory. `BuildProjectTree` creates the package folders the way opening a project does. Tests using it must be in `[Collection(ProjectCollection.Name)]`, because the opened project is global (service locator plus CWD).
  - `TT Lab` exposes its internals to the test project.
  - UI tests use `[AvaloniaFact]` and run in the headless `Support/TestApplication`, which renders with Skia (so bitmaps encode, textures need that) and has the app's `ViewLocator`, Dock theme and view registrations, so real editor panels and tabs can be shown and driven with key and mouse input. Tests creating ReactiveUI objects have to be `[AvaloniaFact]` too, so they run after the application set ReactiveUI's schedulers. The main thread scheduler is `Support/TestMainThreadScheduler`, not `AvaloniaScheduler`: the session resets `Dispatcher.UIThread` between tests, a thread pool thread asking then gets a dispatcher claiming every thread, so a code editor's live check finishing after its test ran on the pool thread, made Avalonia's `MediaContext` on that dispatcher and no later test's window laid out after `Show()` (the Windows CI runner's failures, `taskset -c 0` reproduces them). Wait for views and closed tabs by polling, not with fixed delays.
  - Rendering code that needs a GL context isn't tested, but its math is (`Rendering/`: camera projection, gizmo picking and dragging, splines).
  - Add-on tests import its modules without Blender through the fakes in `tests/fakes.py`.
- CI (`.github/workflows/build.yml`) only runs when started by hand (`workflow_dispatch`, the Actions budget is small). It runs both test suites on Windows and Linux, then publishes a framework-dependent build for `win-x64`/`linux-x64` as an artifact. Publishing for a runtime makes a single file (`PublishSingleFile` in `TT Lab.csproj`, symbols embedded in Release, no documentation files): only the native libraries stay next to the executable (bundled ones get extracted elsewhere, where Veldrid's SDL loader doesn't look), with `BlenderTools/dist` and `tools/`. Assemblies have no `Location` there (`EnableSingleFileAnalyzer` warns about it). Nothing is read from next to the executable but `settings.json`, `layout.json`, `tools/` and the add-on: `Media` (shaders, icons, pictures, not its unused fonts) and `Images/SadTransparent.gif` are embedded, read by their paths through `Util/ManifestResourceLoader` (which resolves shaders' relative includes, `ShaderSourceTests`), and TwinTech embeds its `.lab` definitions and three JSON files (`Libraries/EmbeddedFiles`, by file name). `_WINDOWS`/`_LINUX` come from the OS doing the build, so each platform has to be built on its own OS. `scripts/package_addon.py` zips the Blender add-on without the uv environment. `scripts/fetch_tools.py --os Windows|Linux --out publish/tools` downloads the twinstudio tools (twinmusic, twinpss: https://github.com/Smartkin/twinstudio/releases, zips named `<tool>-windows-latest.zip`/`<tool>-ubuntu-latest.zip`, each a bare executable with a `resources/` folder) into `tools/<tool>/` next to the published build, which is where `Tools/ExternalTools` looks for them (`AppContext.BaseDirectory/tools`; a local `TT Lab/tools/twinmusic` and `twinpss` are git-ignored and copied to the output, only those: the repository ignores case, and ignoring `TT Lab/tools/` hid the sources in `TT Lab/Tools/`, which were never committed). Tools > Install the tools does the same from inside TT Lab (`ExternalTools.InstallAsync`: the latest release's zip for this system, unpacked into the tool's folder in place of what's there, the executable bit set). The tools take no file on their command line, so opening a disc file starts the tool with the path as an argument anyway and on the clipboard.
- Platform-specific code is gated by `_WINDOWS` / `_LINUX` defines set in `TT Lab.csproj`. Native libraries (`PS2ImageMaker`) in `TT Lab/Libraries/Native/{Windows,Linux}` are copied into `runtimes/*/native` by the `CopyNativeLibs` target (an absolute `-o` folder included, they used to go into a folder of that name inside the project). When publishing for a runtime, the `PublishNativeLibs` target copies them next to the executable instead.
- The app requires OpenGL 4.6 (see `Program.cs`).

## TwinTech (game formats)

- `TwinsanityInterchange/Interfaces`: every game item is an `ITwinItem : ITwinSerializable`, implementing `Read(BinaryReader, int length)`, `Write(BinaryWriter)`, `GetLength()` and `Compile()`. `GetLength()` must exactly match what `Write` emits. Containers implement `ITwinSection`.
- `Interfaces/Items/**` defines platform-agnostic `ITwin*` interfaces (for example `ITwinTrigger`). `Implementations/PS2/**` (`PS2Any*`) and `Implementations/Xbox/**` implement them. `Implementations/Base/BaseTwinItem` and `BaseTwinSection` hold the shared logic. A section maps child item IDs to concrete types via `idToClassDictionary`, and anything unmapped falls back to a raw `BaseTwinItem`.
- `Common/` holds shared structs (`TwinTrigger`, `Vector3/4`, and so on) that implement `ITwinSerializable`.
- `Enumerations/Constants.cs` holds section and item IDs (`LEVEL_CODE_SECTION`, `LAYOUT_TRIGGERS_SECTION`, ...). `Enums.cs` holds game enums.
- `PS2Hardware/` contains the VIF/GIF/DMA packet code for PS2 model data. `TwinVIFCompiler` and `TwinSkinPacketDecoder` pack and read models, skins and blend skins exactly the way the game does, which `VifCodecTests` checks. A packet goes out with one DMA tag whose size field holds 65535 quad words: `TwinVifPacket.Writer.Finish` refuses more (the overflow once sent a fifth of a 35k vertex skin and the game hung waiting for the rest), so `PS2ItemFactory` spreads a part's batches over several sub skins or sub models of the same material when they'd go past `TwinVIFCompiler.MaxPacketBytes` (`SkinBatchBytes`/`RigidBatchBytes` are what the compiler writes per batch). `Libraries/` contains ADPCM, swizzling, hashing, quantization and the Xbox's DXT5 codec (`Dxt5`).
- **Xbox** (`Implementations/Xbox/**`): every file of the Xbox disc TwinTech knows reads and writes back byte-identical (`XboxFormatTests` covers each quirk with made-up data).
  - Most Xbox items subclass the PS2 ones. The Xbox's behaviour classes only swap the command table (`XboxBehaviourGraph.GetAgentLabDefs`, some commands take more arguments), the PS2 classes have the virtual hooks (`Defs`, `GetSize`, `Create*`) for it.
  - Models, skins and blend skins are plain vertexes drawn as triangle strips, one strip per group (`XboxSubModel`, `XboxSkinnedGeometry`). Normals are packed 11:11:10 signed fractions. A skinned vertex refers to up to 3 joints of its strip's palette by vertex shader register (16 + 4 per palette slot). Unused slots hold leftovers of the tools' memory (registers past the palette, weights near 0) which are kept for writing but read as joint 0 with no weight, like the PS2 version's. `ITwinStripGroups` marks Xbox geometry.
  - The Xbox's tools joined strips without keeping their triangles facing one way, the game draws them without culling.
  - Textures are DXT5 with only the largest mip (level textures) or plain BGRA (menus, fonts). The first header word is the length of the PS2 texture they were made from, and textures embedded in PTC files work out their length from it.
  - Fonts store every character's box as fractions of its page. Sounds are 16 bit PCM. Unknown header bits (dynamic scenery, trigger behaviours, the order of a scenery's lights) are kept as read, several of them only the Xbox version sets.
- PS2 textures (`PS2AnyTexture.FromBitmap`) get the game's layouts. The header has the texture's size twice, in blocks of 64 of the 32 bit pixels it uploads, which is what the game reserves GS memory by; 32 bit textures upload their whole image and textures without mips have their palette where the game's have it (`UnmippedClutPointers`). A wrong size made textures overwrite each other or go missing in game. The rest of the header is what the tools had in memory (`TwinTextureLeftovers`: the signature's low half, a slot number unique in each chunk, reserved words and 32 bytes after the header), worked out from every texture of the game. It's written back as read (`ITwinTexture.Leftovers`, kept in `Texture.Leftovers`). The PSM files' icons have zeros where chunk textures have an address of the tools' memory, textures made in TT Lab get the chunks' values.
- Behaviour starters get their script ID and their first assigner the ID two past theirs in `Compile()`, like every starter of the game. With a starter the `[Priority]` attribute is the starter's, `[GraphPriority(n)]` holds the graph's own priority (0, 1 or 3).
- Animations (both versions) count channels in their flags: every joint its amount (9, or a facial joint's shapes) and how many are animated (`animated << 4 | static`), the header the amount per joint. `Write` works them out, so animations made in Blender get them right.
- `AgentLab/` is the compiler/decompiler for the behaviour scripting language (AI graphs, starters, command sequences). The pipeline is `AgentLabLexer` → `AgentLabParser` (AST in `AbstractSyntaxTree/`) → `AgentLabSymbolTableBuilder` → `Analyzers/` → `AgentLabCompilerNodeVisitor`, which emits `ITwinAgentLab` objects. Visitors register handlers with `Visitors.Add(typeof(Node), VisitX)`. Reference resolution is abstracted behind `Resolvers/Interfaces`, which TT Lab implements in `TT Lab/Assets/Code/Resolvers`.
  - `ActionDefinitions{Ps2,Xbox}.lab` are **generated** by `LabActionGenerator.py` (run it in `TwinTech/`, it writes both) from `AgentLabDefs{PS2,Xbox}.json`. Edit the JSON and regenerate instead of hand-editing them. A command's `Arguments` are its dword types (`single`, `int32`, `hex`, or the tagged `tfloat`/`tint`/`tangle`), `ArgumentNames` its parameter names, `ArgumentFields` (by argument index) the fields of the dwords the game packs (flags, bytes, halfwords: `Name`, `Bit`, `Width`, `Type` `bool`/`int`/`sint`, together covering all 32 bits) and `Aliases` the names the command went by before, which old scripts still compile under (`AUnknown_N`, and the earlier name of a renamed command). `ConditionDefinitions.lab` is hand-maintained, one line per condition index, with the old names as aliases. Every command and every condition of the PAL executable has a name now; the ones found by reverse engineering (`Ghidra Stuff/AgentLab_RE`, `data/decisions.json` holds each with its confidence and what the code does) are mostly educated guesses, the ones the user had are kept.
  - Packed parameters are declared as `name { int slotCount : 4, bool blendTimeGiven, sint slotA : 16, ... }` (fields from bit 0 up, widths adding up to 32) and written in scripts as `{slotCount = 1, blendTimeGiven = true}` (any order, the fields left out are 0, `{}` for none; a plain int or hex literal is still taken for the whole dword). The decompiler prints the fields that aren't 0 in declaration order, `unused*` ones in hex, so scripts stay byte exact. The symbol pass checks the names, types and the range of literal values, the compiler packs them (`PackFields`), `PackedArgument.Format` unpacks them and completion suggests the fields inside the braces (`AgentLabCompletionKind.Field`).
  - A state's child behaviour is a name (`state S(COM_X)`, `BehaviourReferenceNode`) or a string for what only the resolver understands (`IStateGraphResolver`: a URI in TT Lab, an index in the default one). The decompiler writes bare what lexes as an identifier and isn't a keyword or a token type's name (`AgentLabLexer.IsReservedKeyword`), the rest quoted. `AgentLabCompletion.GetBehaviourReference` finds the reference at an offset, name or string.
  - What the game does with the bytecode (verified in the PAL executable): a body passes when its condition's result is above the threshold (`if X(p) > t`, `<` inverts), and among the passing bodies the largest `(result - threshold) * weight` runs, `weight` being 1/threshold unless written. `window` (the condition's first float) is a time window in seconds only the event conditions read, never a check interval. `else` is the fallback body (condition 2) and `completion` the first body of a state with bit 10, run when its control packet or child behaviour finishes (condition 0, never evaluated). `restart = true;` (body bit 8) makes a jump to the same state re-enter it. `[Interrupting]` (state bit 11) keeps the state's conditions evaluated while its child behaviour runs. State bits 5-9 (small leftover numbers, dropped: old scripts' `[Unknown(n)]` is accepted and ignored) and 13, and assigner locality/status/preference, are never read. An assigner's `RefListIndex` is the instance's RefListIndex a `GLOBAL_AGENT` receiver is, not an object. Tagged arguments (`TaggedValue`) are a literal of the parameter's type or `Prop(n)`, an instance property index; `Raw(0x...)` keeps bits as they are and hex literals always do. Many commands take a "designator" byte: a starter receiver index below 0xDE, or 0xFB the focus object, 0xF8/0xF7 AgentRef1/2, 0xF2 the player, 0xF4 the originator, 0xF6/0xFC the focus position, 0xFD/0xFE the next/current key, 0xFF none. The old spellings (`NonBlocking`, `interval`, `unknown`, `>=`, `GlobalObjectId = "uri"`) still compile, projects store behaviours as script text. Floats print so they lex as floats and reproduce their bits (`-0.0`, `2.0`), and bits no literal reproduces (NaN, infinities, denormal leftovers, `int.MinValue`) print in hex or `Raw(0x...)`; control packet data is written in float slot order. Every script of the PAL archive round-trips byte-identically but for those bits (`Ghidra Stuff/AgentLab_RE/scripts/harness`, modes `roundtrip`, `context`, `sample` and `locate`).

## TT Lab (editor)

### Project lifecycle (`Project/Project.cs`, `ProjectManager.cs`)
- **Create**: copy the disc contents, then `CreateBasePackages()` (Base, Global PS2/Xbox, PS2/Xbox packages), then `UnpackAssetsPS2()` and `UnpackAssetsXbox()`. Both go through `UnpackAssets`, which parses the chunks and runs `AssetResolvers/*` over each of them through `ResolverManager.PerformResolve`. The resolvers turn `ITwinItem`s into `IAsset`s. The PS2 version's files come from its `.BD/.BH` archive, the Xbox's are loose on the disc (`GetXboxDiscFiles` takes the Startup, Levels, Extras and Language folders, like the PS2 archive holds). Unpacking the Xbox disc enables its packages.
- **Both versions in one project**: their assets share IDs, so `AssetManager.GetUriByTwinId` only matches assets of the requester's package and the packages it depends on (then the ones depending on it), and code scanning every asset of a type for an import uses `GetRelatedAssetsOf<T>(package)`. `Project.GetPlatform(package)` tells which version a package is. The game also reuses texture IDs for other pictures in other chunks' sceneries (the hubs' 64x32 `671573F7` is a 128x64 texture of l03beach's scenery), so among the assets with the ID the lookup takes the requester's own folder (`AdditionalPath`: a scenery's material gets its scenery's texture, a PSM's its own) first, then the package's shared ones, and another chunk's folder last, in URI order; the order they were added in decided before, and the hub's `lambert46`/`lambert48`/`AC_AC_AC_lambert228` materials got the Totem's textures, which drew their model (the whack-a-worm HUD sign) from the wrong corner. Projects created before 2026-09-29 have those links baked in and have to be created again.
- **Build**: `PackChunk` and `PackAssets(platform)` (`PackAssetsPS2`, `PackAssetsXbox`) call `ResolveChunkResources(factory, section)` on each chunk's assets, using the platform's `ITwinItemFactory` to create game items. `XboxItemFactory` extends `PS2ItemFactory`, mapping its items and sections to the Xbox classes through `Create<T>`/`CreateSection<T>`, and has its own graphics, sounds, fonts and script descs. Assets the owner writes itself (`SkipExport`, a PSM's PTCs) aren't written on their own.
  - PS2: `.rm2`/`.sm2` files under `<project>/build/archives`, then `CreatePs2ArchivesAndIso` packs them into the disc folder's archive and produces the ISO.
  - Xbox: `.rmx`/`.smx` and global files under `<project>/build/xbox/files`, then `CreateXboxGame` copies the disc into `build/xbox/game` with the built files in place of theirs (the Xbox's file system ignores case, chunk paths are lowercase) and `XboxImageMaker` writes it as an XDVDFS image to `build/image`. Files already the same as their source aren't copied again.
- **Build profiles** (`Project/Build/BuildProfile.cs`, `BuildProfileLibrary`, one JSON each in `<project>/profiles`, hidden from the tree): the version to build and the chunks left out (`ExcludedChunks`, URIs, so new chunks get built). The Build menu's "Build..." opens `BuildDialogViewModel`/`Views/BuildDialogView` (profiles to pick, make and delete, a PS2/Xbox choice, every chunk of that version with a checkbox and a filter; `Preferences.LastBuildProfile` remembers the last one built with) and `ProjectManager.Build(profile)` runs `Project.Build` → `PackAssets(platform, profile)`. A chunk left out isn't written (`Project.LeftOutChunks`): its files stay while the build folder has them, the Xbox game takes the disc's file, and since the PS2 archive is made of `build/archives` alone, a left out chunk never built gets its files from the disc folder's `Crash.BH`/`BD` (`Project/Build/DiscArchive`, the last build's archive or the game's own, paths matched without case or separators) and is only written when that lacks it too, so a small profile on a fresh project builds its few chunks; every built chunk's links to it are dropped from the file without touching the asset (`ChunkLinksData.Export` reads `ITwinItemFactory.ExcludedChunks`, records what it linked in `LinkedChunks`), the cache keeping a `link:<uri>` dependency per linked chunk (`kept`/`dropped` against `BuildCache.ExcludedChunks`) so a chunk is rebuilt when a profile changes which of its links are dropped. Every build logs its total time. **Build failures** are `BuildException`s naming what failed and where (`WriteChunk` wraps each chunk resource as "<asset> of <chunk>", `ResolveGlobalAssets` each global file), a data file that can't be read names itself (`AbstractAssetData.Load`), and `ProjectManager.RunBuild` (every build menu entry goes through it) logs them as errors, a line each, in every configuration, then hands the project back (`WorkableProject`). It only caught them in Release builds before: in Debug a chunk's exception went nowhere, the build looked stuck after the chunks without the failing asset and the project stayed locked. The cache is saved and the empty chunk folders removed even when a chunk fails. A stored key renamed without converting the project does exactly that to every asset of the type (`[JsonProperty(Required = Required.Always)]`).
- **Build cache** (`Project/BuildCache.cs`, manifest in `<project>/build/cache/manifest.ttcache`): every chunk and global file records the assets it read, which `AssetManager.RecordAccessedAssets` collects from `GetAsset`/`GetAllAssetsOf` calls on the current async flow, and is skipped when none of their fingerprints (metadata JSON + data file hash) changed. Assets loaded when the build starts count as changed, and so does what was built from them while they stay loaded (they were recorded as volatile, which matched volatile, and a chunk built while its scene was open never got built again until the scene closed). Rebuilding TT Lab or changing its definition files invalidates the whole cache (the fingerprint is TT Lab's and TwinTech's module version IDs, which deterministic builds derive from their contents, embedded files included). Code that makes build output depend on anything other than assets fetched through `AssetManager` must add it to the fingerprints, or builds go stale.
- **Playing in PCSX2** (`Tools/Pcsx2`, the PS2 version's PAL 1.01, NTSC 1.00 and NTSC 2.00 releases: `GameRelease.Detect` tells them apart by SYSTEM.CNF's boot file and version and checks the executable's CRC, and holds each one's addresses, found by matching the PAL release's functions in the NTSC ones; the PAL addresses are given here): the chunk viewport's toolbar has Play, Reload and Stop (`ViewportViewModel.GameLaunch.cs`, Play disabled with the reason as its tooltip for chunks `Pcsx2Service.WhyNotPlayable` turns down, Reload and Stop only while the game runs, following `Pcsx2Service.Playing`), what PCSX2 and disc image it uses and whether saving reloads are in Preferences > Direct Game Launch. Play builds the chunk and the chunks it links (`Project.PackChunk`), fills `<project>/build/pcsx2` (`Pcsx2DevFolder`: every file of the disc's archive on its own in upper case, the way the game asks for them, the build's files over them, and the `Crash6` sound banks, which the game streams through the same loader and had no music without; only what changed gets written, moved into place) and boots it in PCSX2 in a window of its own (`Pcsx2Install`: the Flatpak, `pcsx2-qt` on the path, its install in Program Files on Windows, or the executable picked; its settings in the Flatpak's config, `~/.config/PCSX2`, `Documents\PCSX2` on Windows or next to a portable one; the disc image picked or the project's built ISO: the game streams its videos from it with `sceCdSearchFile`, past the patched loader, so an image of another release plays as well). The executable is patched (`GameExecutable`, verified in the PAL executable, `Ghidra Stuff/Engine_RE`): the loose loader's `cdrom0:\` (0x3069c0) becomes `host0:\`, so PCSX2's host file system (rooted at the executable's folder) serves the folder; the built-in launch arguments (0x2ec400, `Main` always parses them and never what the emulator passes) lose `batch=Crash6\Crash`, so no archive is used; the start chunk comes from unused bytes after .vutext (0x2e6ed0) that the code filling `G_StartChunk_Path` (0x178930) is pointed at; a word appended keeps the PS2 CRC (the XOR of the file's words) at 77AB0001 (NTSC 1.00 77AB0002, 2.00 77AB0003), so one game settings file per release (`gamesettings/77AB0001.ini`, PCSX2 names it by the CRC alone for an overridden executable; only TT Lab's keys set: `HostFs`, `EnablePINE`, `PINESlot` 28111) serves every chunk. TT Lab drives the game through PINE (`PineClient`, refused until the virtual machine runs; a Unix socket in the runtime folder on Linux, the Flatpak's reached through `/proc/<pid>/root`, a TCP port on Windows): the game controller's states (`RunningGame`: `G_GameController`+8 holds the next state in bits 50-55, applied the next frame; the NTSC releases' controller lacks the PAL one's first 8 bytes, the states are at +0 and the start's timer at +0xC, the state numbers are the same) go the way the main menu's new game does (`Pcsx2Session.NextOnTheWayToPlaying`): from the logos (4) to loading the start chunk (6, `FUN_00173d10` drops every chunk and loads `G_StartChunk_Path` with its links), from the title (7, "press start" over the start chunk) to a new game (10: the game's data made again, the player in character slot 0), from the intro movie's state (14, the movie only starts 0.6 s in) to starting to play (11, the player gets control) and on to playing (12), where the start's timer (+0x14) is zeroed so neither the level's title card nor the autosave notice comes up (making autosave look on could save into the user's slots). The title's character slot 4 plays its cinematic: going from the title straight to playing kept it running, and the beach got stuck after its "THREE YEARS AGO...". About 25 s from booting to playing. Saving anything while it plays (`DocumentViewModel.Saved`, when reloading after saving is on) or Reload builds the start chunk, its links and the chunks the game has loaded again (`G_ChunkManager`: the count in the low half of its first word, the chunk metas after it; dropping every chunk only zeroes the count, the old pointers stay), copies what changed (Windows doesn't replace a file the game has open, the move is tried again for 5 s) and, when anything did, asks for state 6 and then the same new game: a full reload of the chunks' files (about 12 s), the player back at the start chunk's start. Startup files (`Default.rm2`, fonts) are only read at boot, playing again picks them up. Every release boots, plays and reloads the beach and Totem Hokum's beach under the Linux Flatpak; the Windows paths (the install search, `Documents\PCSX2`, PINE over TCP) haven't run on Windows yet. **Level select** (the PAL release only, `GameRelease.LevelSelectPatch`): Play applies `Ghidra Stuff/Engine_RE/pnach`'s patch, a level select above the pause menu's options and save/load state (R2 + L2, L2 + Triangle), as `patches/77AB0001.pnach` (`Pcsx2Install.WritePatches`: the embedded `Tools/Pcsx2/LevelSelectPal.pnach`, which the pnach's `build.py --tt-lab` writes, lines outside a group so they're always on for the patched executable; `EnablePatches` in its game settings). It reads `Startup\LevelSelect.txt` at boot: Play writes the project's (`Assets/Global/LevelSelect`, the version's global package's `LevelSelect` text file) into the dev folder and builds the chunks it lists that the disc's archive lacks (`Pcsx2Service.ChunksTheDiscLacks`), which only play once built. Chunks made in TT Lab go at its end (`LevelSelect.AddChunk` from `AssetDataFactory.CreateChunkData`: `"name"<tab>""<tab>"levels\..."`, after a blank line when the last level is of another world, the folder after `levels\`, which names the patch's pages) and deleted chunks leave it (`AssetDeletion`), through the document when an editor has the file open. Picking a level starts a new game in it and then puts back the start chunk it replaced, so Reload still goes back to the chunk Play started.
- `Project.CURRENT_VERSION` is the only project version TT Lab opens. Bump it for changes that break how existing projects store their assets.
- These paths rely heavily on `Directory.SetCurrentDirectory`. Asset data load/save, `SerializableAsset.Delete` and package/chunk serialization resolve absolute paths and leave the CWD alone so they work from any thread, but a lot of older code is still relative to the CWD. Never change it from code a build or project creation runs in parallel.
- **Parallel builds**: `WriteChunks` builds the level chunks in parallel. Each chunk gets a factory of its own (`ITwinItemFactory.ForChunk`), whose `ChunkResolution` resolves every asset into a section once (an instance resolves its object, the next instance of it doesn't), guards against assets referring back to themselves and hands objects the references of the objects and graphs under them. Compiled behaviours are shared by the chunks of a build (`CompiledBehaviours`). Each chunk also gets an `AssetDataScope`: the data it loads and the internal assets that data makes stay in the scope (removing one, like a scenery's data deleting its collision and dynamic scenery when it's released, takes it out of the scope), which releases them once the chunk is written, so chunks never touch each other's data or the data editors have open (a build only reads that). `MemoryGate` starts more chunks while TT Lab is within `Preferences.BuildMemoryBudget` (2048 MB) and collects when it gets close. Asset storage takes a lock on every access.
- **Creation** stays within the same budget through a `MemoryGate`. The PS2 archive is read a file at a time, chunks are read for their behaviour starters and dropped, then read again a few ahead of resolving them. `CreationWriter` imports and writes every asset in parallel as soon as the disc's chunks are resolved and lets go of its data, each version of the game before the next disc is read, and the disc's variants are merged into their assets as chunks' overrides (see Chunk overrides). Internal assets get imported when a write first looks them up (`AssetManager.HookLookups`) and let go of once no write uses them, kept in their data file first because another write can find the same one by its ID (two OGIs, one rigid model); those files go with the internal assets. So `Import` must only read other assets' metadata and never touch the CWD, and writing an asset may only read the data of the internal assets it's made of.

### Assets (`Assets/`, `AssetData/`)
- `IAsset` / `SerializableAsset` is an asset's metadata (ID, URI, package, references, variation). It is serialized to `<Name>.json` with Newtonsoft (`MemberSerialization.OptIn`, `[JsonProperty(Required = ...)]`).
- `AbstractAssetData` subclasses hold the payload, stored in `<Name>.data` (JSON). Data is lazy: `asset.GetData<T>()` loads it, and `Serialize(SaveData)` saves and then **disposes** it unless `PreserveData` is passed.
- A new asset type usually needs:
  - an `Assets/<Category>/X.cs` class with `Section`, `IconPath` and `GetData()`, which recreates the data when `!IsLoaded || Disposed`;
  - an `AssetData/<Category>/XData.cs` class with a `[JsonConstructor] internal XData() : base(null)` ctor, an `Import(...)` that reads from `GetTwinItem<ITwinX>()`, and an `Export(ITwinItemFactory)`;
  - a resolver in `AssetResolvers/` and a factory method in `ITwinItemFactory`/`PS2ItemFactory`/`XboxItemFactory`.
- **Data lifetime**:
  - Open editors own the data they use: a document's property graph loads every linked asset's data, and `Save()` keeps it loaded (`PreserveData`).
  - When an editor closes, `EditorsViewModel.ReleaseUnusedAssetData` calls `UnloadData()` on every asset no open editor references (`TabbedEditorViewModel.GetReferencedAssets`). `UnloadData()` detaches without disposing, because renderers may still hold the data.
  - Internal assets (`IsInternal`) are never serialized. Loading an owner's data recreates them, so any code creating one must set `InternalOwner` to the asset whose data creates it; `AssetManager.RemoveOrphanedInternalAssets` drops them once their owner isn't loaded.
  - Project creation removes all internal assets once a disc's assets are written.
  - Assets never saved (`IsUnsaved`: a layout's instances until their chunk gets saved) keep their data, there's no file to load it back from. When a scene's tab closes, the instances made for its chunk that it no longer lists (their placing undone, the chunk closed without saving) leave the project (`AssetDeletion.ForgetUnsaved`): they stayed in the project tree and couldn't be opened. A tab whose data fails to load logs why and closes, it stayed loading for good.
- **Deletion** (`Assets/AssetDeletion.cs`): every asset referencing a deleted one is fixed by `DeletedReferenceFixer`, which walks the data by reflection and follows each `LabURI` member's `[OnReferenceDeleted]` policy: replace with a placeholder from `PlaceholderAssets` (the default), clear, or remove from the list. Annotate new `LabURI` members whose placeholder wouldn't make sense.
- **Textures** are PNGs that go through Skia unpremultiplied (`TextureData.FromPng`, `GetPngBytes`); Avalonia's bitmaps premultiply what they load and save and lose the color of transparent pixels, so `TextureData` keeps the exact pixels and only shows them through its `Bitmap`. `Texture.ReservesMemory` keeps the header's second size at 0 for Crash's textures every chunk has.
- Shader vectors (`LeftoverVector`, `ShaderColor`, `UvScrollSpeed`) often hold leftover bytes that are NaN as floats (every UI shader has them), and Newtonsoft would write them all as the same NaN, so `LabShader` stores their bits (`BitsVector4Converter`). What the PAL executable does with a shader's other values (`Ghidra Stuff/Engine_RE`): `LeftoverVector` is bits of the tools' strings, only compared when equal shaders get merged; only `ShaderColor.X`'s integer part reaches the VU1 program (0, the UI's materials 1); `UnusedValue` (the byte after the depth test, 4 or the UI's 6) and `UnusedFlag` are never read; `AntiAliasing` is the GS's PRMODE AA1; `AnimationDrivesColor` makes the animation's color track set `ShaderColor` every frame. A material's `DmaChainIndex` is which of the game's 28 render buckets its draws go into, drawn in bucket order: 0 skydomes, 2 opaque scenery and objects, 3 opaque global objects, 6-19 alpha-blended, 20 decals and layered materials, 22 particles, 24 the UI, 26 fonts. A bucket has no GS state of its own: every material sends its shaders' PRMODE, FBA, ZBUF (with the depth mask), ALPHA, TEST (the depth test always on), TEX1 and CLAMP with every draw (`SetShaderSettings`). What's fixed is what the game's code puts in (`RenderBuckets`): the frame's setup and clear at the head of 0 (`FUN_0019f958`), the debug drawing in 4 (off in retail), a darkening pass in 21 (`FUN_001f1a10`: extra geometry drawn into a second buffer, a quarter of it taken away from the screen), the particle pages' shaders in 22 (the particle code makes them, whatever the page material says), the Distortion particles in 23 and the movies in 27. The material's first 8 bytes (`ActivatedShaders`, a bit per shader type) are the key of the VU1 programs its bucket has loaded (`RenderMaterial`): the same key as the last material drawn in the bucket skips loading the shaders' programs and 1 never loads them, so `MaterialData.Export` writes `DeriveActivatedShaders` (the bits of the shaders' types, what all 10487 Xbox and every PS2 material have). The alpha presets (`TwinShader.AlphaBlendPresets`, `G_AlphaRegPresets` filled by `FUN_001daa68`) are 0 Mix (Cs - Cd)·As + Cd, 1 Add Cs·As + Cd, 2 Sub Cd - Cs·As, 3 Brighten Cd·As + Cd, 4 Darken Cd - Cd·As, 5 Scale Cd·As, and zeros past them on PS2 (Replace: the source as it is); the blended retail materials only use 0-2. `Rendering/GsBlending` turns them into GL's blend state for materials and particles. Shader animations (`TwinShaderAnimation`: six tracks U, V, R, G, B, A in 1/4096ths, static or per frame, looping at the header's frames per second, `AnimateShader` 0x297260) still run in retail: the `FromAnimation` scroll modes take the U and V tracks as the UV offset and `AnimationDrivesColor` the color. TT Lab edits them in the material's inspector (`LabShader.Animation`, the TwinTech classes are reflected) and the viewport plays them (`ShaderAnimationSampler` samples the tracks at the render context's `Time`, `TwinMaterial` hands them to the shaders as `uv_offset` and `animated_color`). **Cloth deformation** (types 0x17 `UnlitClothDeformation`: `IntParam` mode, `FloatParam` speed and one amplitude; 0x1A `UnlitClothDeformation2`: mode, speed, an amplitude per axis, `ReadPrecompShaderType_0x17`/`_0x1A`): the game keeps 16 rows of 3 phases, each starting at a random angle in [0, π), and every frame (`FUN_001d1cf0`) moves them all by speed × time × 2π (mode 2: × time, wrapped past 10π), hands VU1 sin of each (modes 1 and 2 cos, mode 2 times cos of a second random set sped up 2, 2.3 and 2 times) as 16 quad words next to the amplitudes (`FUN_001d1948`). The VU1 programs (0x21 and 0x1E, disassembled in `Ghidra Stuff/Engine_RE/VU1`, `vudis.py` is the disassembler) move every vertex by the amplitudes times a wave per axis whose row is the low 4 bits of the float bits of the coordinate × 0.000373 (`MTIR` of the scaled position): a hash of the position, so vertexes at the same spot move together and nothing tears. `MainPass.vert` (`ClothOffset`) does the same with `floatBitsToInt` and fixed pseudo-random phases (`twin_material.deform_mode/deform_speed/deform_amplitude`). The **environment map** (type 0x16, VU1 program 0x1D) is no sphere map: per vertex H = normalize(normalize(eye − P) + N), d = normalize(L0·H, L1·H, L2·H) with L the chunk's three strongest directional lights in the object's space (the light controller's slots 4-6, transposed into the object block by `SetRigidModelRenderDMA`), and the picture is read at (0.5 + 0.5 d.x, 0.5 − 0.5 d.y) clamped, plus the material's scroll: a lookup by the half vector's agreement with the two strongest lights. `MainPass.vert` (`EnvironmentUv`) does it in world space with `RenderContext.EnvLights` (`Rendering/EnvLights.Of`, set from the scenery's `DirectionalLights` when its objects are made, defaults without any).
- **Scenery lights** (`TwinTech/Common/Lights`, verified in the PAL executable): the header's low byte is the type the game lights by (`LightType`, written from the class), bit 8 `Enabled` is never read. `Intensity` multiplies the color of every kind; ambient lights are summed, of the others the 3 strongest at a vertex are used. Point and spot lights fall off by 25 / (d² + 25) raised to `AttenuationPower`. A spot light (`NegativeLight`, the tools' name) shines along `Direction` within `ConeAngle` (65536ths of a turn) fading out over `FalloffAngle`, but the game lights with `InnerConeCosine`/`OuterConeCosine`, which TT Lab makes again from the angles when a file's angles changed (`NegativeLight.ConeCosines`). A directional light's `Direction` is a unit vector pointing at where the light comes from. `BoundsMin`/`BoundsMax` are the tools' boxes the game works out again at load (`ComputeBounds`) and never reads. In TLM files a light's node points its Z axis along its direction (the add-on's arrow), the stored `Direction` is kept while the node still points along it, a stored direction of no length (the add-on writes lights made in Blender with one) while the node isn't turned.
- **Collision tree** (`AssetData/Instance/Collision/BvhBuilder.cs`, `BvhStats`; the game's `CheckCollisionRayCast` 0x27fb58, `FUN_0027f310`): triggers are the boxes of a binary tree, an inner node's `MinTriggerIndex`/`MaxTriggerIndex` are its children's indexes, a leaf's are both `~group`, a group a run of the (reordered) triangles. A query tests the segment against both children of every box it enters and every triangle of every leaf it reaches, a box query gathers at most 256 leaves. The retail files are balanced trees halved by triangle count until 30 or fewer (leaves of 13-31, all at the same depth, ~7-10% sibling overlap), which `Strategy.MedianBestAxis` with 30 makes again within a few boxes and the same cost per ray; `Sah` (binned) is there for comparison. The Command Interface's `bvhstats <chunk.rm2>` measures a retail tree against every strategy under the game's ray walk.
- **Collision surfaces** (`Enums.SurfaceCollisionFlags`, `ITwinSurface`, `CollisionSurfaceData`): the game plays a surface's sounds and particles by contact kind (0 impact, 1 and 2 steps, 3 land, 4 hard impact, 5 scrape: `Impact*`, `Step*`, `Land*`, `HardImpact*`, `Scrape*`), objects landing on it play 0 (4 when hard) and 5 while scraping, scripts play any kind with `DoSound`'s bits 19-22 (`unused3`, 0xF plays the slots), and the player's own footsteps come from the character's sound table by surface ID. Of the 10 floats (`PhysicsParameters`, `SurfacePhysics` indexes them) five are the kinds' volume scales (-1 leaves the volume) and only `Friction` (index 6: 1 on most, 0.05 on ice) is read of the rest. The flags are one bit per ray cast (`SolidToPlayerProbes` 4, `BlocksCamera` 5, `SolidToObjects` 6, `BlocksLineOfSight` 7), `SendsContactMessage` (9, the deadly surfaces), `Sticky` (10), `LeavesFootprints` (11) and `SolidToPlayer` (20); bits 12-19 are set on every surface and never read. The volumes live in the `PhysicsParameters` array. The particle IDs (`ImpactParticleSystemId` kind 0, `StepParticleSystemId` 1 and 2, `HardImpactParticleSystemId` 4; land and scrape have none, `GetSurfaceParticle` 0x282160) are indexes into the default chunk's particle systems: the game plays entry index + 1 of its table of systems (`FUN_00223ad0`), which the default chunk's fill first, 0xFFFF none (new surfaces). The inspector names them and picks them from the default chunk's list (`DefaultParticleSystemFieldViewModel`, `->` shows the system in the default chunk), an index past the list shows as broken.
- **Instance state flags** (`Enums.InstanceState`): the engine reads bits 0-18. `TracksMovement` (5) gives the instance a node keeping its previous transform, `SyncCrossChunkState` (6) a persistent flag slot of its chunk (scripts' `CheckPersistentFlagCondition`), `PersistentFlagInChunkStore` (7) keeps that flag in the chunk meta's own store, `SnapToGround` (18) places the instance on the ground below when created. Bits 19-31 have no reader, scripts can still test them with `CheckInstanceFlagSet`.
- **TT Lab model files** (`.tlm`, spec in `TT Lab/BlenderTools/TLM.md`): models, rigid models, meshes, skins, blend skins, OGIs, scenery, dynamic scenery, collision and skydomes are stored as a JSON tree of nodes with their arrays in binary data next to it, written and read through `AssetData/Graphics/TlModel/` (`TlmFile`, `TlmNodes`, `TlmTreeNode`, `TlmMeshes`, `TlmAnimations`, `TlmMaterials`). The file is the asset's data file itself (`DataExt => ".tlm"`). Users edit them in Blender through the add-on's own importer and exporter, so:
  - A node has a `kind`, a `name`, its Twin Tech values in `data` (the same keys the add-on's panels edit) and a transform relative to its parent. Names are cosmetic, the hierarchy is only read where it means something: an OGI's bodies, exit points and collision hulls name the joint they follow, a scenery LOD's levels are the meshes under it and scenery meshes are culled with the `tree_node` above them (TT Lab moves the ones that left their node's box, `SceneryData.ReadInstances`). Skins and shapes have no transform, the add-on bakes where their object is under the root into the vertexes (a modder's mesh is usually rotated and scaled against the skeleton), and works a body's or exit point's transform out from where the object follows its bone (Child Of constraint or bone parent) with the armature at rest (`_attached_placement`). An exit point's game matrix is the node's `matrix`, carried by the add-on without showing it, like the bones' binds. A blend skin has as many shapes as its mesh has shape keys (`BlendsAmount` is derived), the add-on writes every key's weights into the facial animations.
  - **Collision hulls** (`TwinCollisionHull`, the game's `ModelCollisionData`, verified in the PAL executable's `HullsIntersect`/`BuildBoxHull`/`PackBuiltHull`): convex hulls OGIs keep on their joints (`OGIData.CollisionHulls`/`CollisionHullJoints`, joint 0xFF = the model's space; the game makes a box of the OGI's bounds for OGIs without any), dynamic scenery models and chunk links (`TwinChunkLinkHull`) carry them too. The blob is vertexes, one outward plane per face (`n·p + w ≤ 0` inside), the unique edge directions and face normals (the separating axes of the SAT test: A's normals, B's normals, cross products of both hulls' edge directions), the faces' offsets, the faces (count then vertexes, counter-clockwise from outside) and the edges (vertex pairs). The retail files have no per-hull collision surface (the loader reads one only in another file mode). `hull` nodes in the files, wire meshes in Blender: TT Lab keeps the game's planes and axes while `twin_vertices`/`twin_faces` match and the node has no transform, else bakes the transform and works them out like the game's builder (`ComputeFromFaces`). The OGI viewer draws them (`Rendering/Objects/OGI.DrawPrimitives`). A chunk link's hulls are loading zones (`LoadLinkedChunks` 0x2aa118: the linked chunk only loads while the player's position is inside one of them, `IsPointInsideHull` reads only the planes; a link without hulls always loads its chunk), 55 of the PAL version's 337 links have them, all boxes. TT Lab keeps them as `ChunkLinkHull` (JSON, still under `ChunkLinksCollisionData`): a `Placement` the gizmo moves (a box's half extents are its scale) with the corners relative to it, and the game's hull kept while the corners are still where it has them (`ToTwin`). The chunk editor draws them (`LinkHullVisual`, the "Link hulls" layer) and the inspector lists them under the link, new ones are 2 unit boxes.
  - Parts refer to the project's `Material` assets by URI (`TlmMaterials`), so every chunk's materials and textures are assets of the project (a scenery's under its chunk's folder, a skydome's under `Skydome/<its ID>`: skies use the same texture IDs for other pictures, and materials find the texture in their own folder first), never internal ones. Materials made in Blender come embedded with their image and become assets of the owner's package when the file loads (`TlmMaterials.AddToProject`), the file is then written again to refer to them. They get the shader the game draws the part with (`TlmMaterialUse`: skins and blend skins `LitSkinnedModel`, the game's skinned shader is the only one that takes a skin's packets, the rest `StandardUnlit`) and the render bucket the game's own materials of the kind are in (2 opaque in a level, 3 in a global package, 16 or 14 blended). `SkinData` warns about parts of more than 8000 vertexes. Their images get the game's sizes (`TextureData.ResizedForTheGame`: powers of two of 16 to 256, a palette with mips only for the sizes the game's tools laid out, `PS2AnyTexture.HasPaletteLayout`). A missing material, or none on a part that needs one, becomes an internal placeholder (`TlmMaterials.GetRequired`).
  - Values the game stores that Blender changes are written next to what Blender shows (`twin_normal`, `twin_uv`, `twin_shapes`, a skin's raw `joints`/`weights` next to the vertex groups' `group_joints`/`group_weights`) and used while Blender's still match them. Blender's weights add up to anything (it scales them to 1 when deforming), TT Lab normalizes the 3 strongest (`TlmMeshes.ToJointInfo`), the game's stay while the shares match. Normals of zero length always stay. The add-on keeps the vertex order and writes a vertex once more for every other value its corners need.
  - Values the game stores next to what the file shows (bounds, joint world transforms, inverse bind matrices, the matrices of exit points and placed scenery, collision order) are kept in the node's data and reused while they still match (`TlmNodes.KeepStored`, `OGIData.IsSamePose`), so unedited assets round-trip byte-identical. Bones rest where the joints' bind poses put them without the scale bones can't have.
  - Parts keep the game's strips (`StripLayout`), reused while they still draw the part's triangles. Everything else, including every part made in Blender, gets new strips from `MeshProcessor/Stripifier`. Rigid models flip the triangles ending on an even position of their batch, skins the ones ending on an odd position of their strip (a strip starts two vertexes before one that draws after two that don't).
  - Xbox parts (`StripLayout.IgnoresFacing`) have one batch per strip, and skins keep every strip's joint palette (`StripBatch.Joints`). Their faces get turned by the vertexes' normals (`StripParts.FaceByNormals`), a triangle drawn from both sides keeps one of them turned around, and the layout only has to draw the same triangles. `XboxItemFactory.ToStrips` turns PS2-style layouts into strips that draw every triangle, with a repeated vertex where the facing would flip. Skins of both versions keep their normal in the position's W and the UV's Z and W. Xbox models, skins and blend skins come back byte-identical, but for the unused joint slots' leftovers.
  - `BlenderTools/twin_tech_tools/schema.json` lists every type's keys and the game enums the add-on edits, and the tests (`TlmSceneryTests.EverythingWrittenIsKnownToTheBlenderAddOn`, `SchemaTests`) fail when TT Lab writes a key or has an enum value it doesn't list. Add new keys there and to the fields in `schema.py`, new node kinds to the add-on's `tlm_blender.KIND_TYPES` and the test's list.
  - `TlmFixtureTests` writes `BlenderTools/tests/fixtures/ogi.tlm` and `scenery.tlm` (`TTL_UPDATE_FIXTURES=1`) and reads back what the add-on exported of them (`tests/blender_roundtrip.py`, run it in Blender after changing either side: plain, `--edit`, `--customize` (skin object moved, shape key and bodies and an exit point added on bones, exported while posed), `--swap` (skin and shape swapped for meshes made in Blender) and `--retarget` (the animations retargeted to a copy with a moved and a renamed bone), the last three write the expected numbers next to the fixture as JSON). `tests/blender_templates.py` makes both templates and exports them as `ogi_template.tlm` and `scenery_template.tlm`, which `TlmFixtureTests` reads as a model and a scenery (`OgiTemplateMadeInBlenderIsAModel`, `SceneryTemplateMadeInBlenderIsAScenery`), `tests/blender_retarget.py` runs the replace button on a changed copy of the fixture.
  - The add-on's Twin Tech Model panel exports the model. **Add > Twin Tech** makes new models to build on (`tlm_templates.py`: an OGI with one joint, a box skin weighted to it and the empty holders of bodies, exit points and hulls; a scenery with lighting on, a tree node holding a 20 unit ground, an ambient and a directional light, the ground as the collision with a `SURF_DEFAULT_0` material and an empty dynamic scenery), laid out like imports so they export the same way, to a file the user picks (an asset's file in a project replaces that asset; TT Lab can't make a new asset from a file). The Twin Tech Animation Retargeting panel has one button, **Retarget Another TLM And Replace The Current Model** (`TTT_OT_RetargetAndReplace` → `tlm_blender.retarget_and_replace`): it imports the picked model file, drops the file's own animations, names its bones like the model's joints (`assign_joints`: `retarget.match_joints`, Blender-free: by joint index, then name, then the place in the hierarchy, the rest new joints, the matched ones get the original joints' settings), retargets every animation of the model to it (`retarget_animations`: a copy of each action in which every matched bone (joint index, then name) turns from its own rest, in the world, as much as the original's does on every frame and moves as far beyond where its nearest matched ancestor's turn leaves its rest offset, times `retarget.size_ratio` (the matched rests' extent): `retarget.retarget_pose`/`world_deltas`, Blender-free, on floats or numpy arrays of a whole animation, every source bone sampled since unmatched ones still turn what's under them; bone axes don't matter, non-uniform scale is copied as it is; shape keys by order), then removes the model with its own actions (`remove_model`, its meshes and armature and its collection once empty) and gives the new one the model's file, name and collection, the copies becoming the model's under the originals' names with their IDs (`RETARGETED_PROPERTY` taken off, Blender's `.001` numbers dropped where the names got free). Nothing stays twice, so a model retargeted again is just the model. Exporting warns about modifiers other than the armature's, meshes are written without them. Meshes of more than `MAX_EXPORT_VERTICES` (4096, the game's biggest skin has 2716) are written decimated (a collapse in a temporary copy, `_decimated`) with a warning saying so, meshes with shape keys only get the warning.
- **OGI animations**: animations aren't assets. Each OGI keeps the animations played on it (`OGIData.Animations`) in its file, under its armature (`TlmAnimations`). Game objects pair a model with an animation in `ModelSlots` (the OGI's URI and the ID of one of its animations), the game never has an animation without a model. Creating a project gives every OGI the animations game objects play on it, so animations shared by several OGIs get copied. Building puts each slot's animation into the chunk through `OGIData.ResolveAnimation`, where copies that are still the same go in once and edited copies of an ID get a free one. The OGI editor plays them (`OgiAnimationsViewModel`) and the slot's animation is picked from the OGI's (`OgiAnimationFieldViewModel`).
  - Every animation has the game's bytes (`exact`) next to every frame's local transform of every joint and its per-animation flags (independent scaling, additional rotation). The add-on turns the keys into poses of the bones and back and carries the game's bytes with the action. Reading keeps the game's values of every joint, frame and track whose keys still round to them, rotations closer than half of a raw unit, so an unedited animation is its bytes and editing one bone changes only that. Animations without an ID (made in Blender) and copies of one get a new one from 0x8000 up, and loading an OGI writes its file again when it had any. Rotations become the game's Euler angles through `GlmExtensions.ToEulerAngles`, because GlmSharp's `quat.EulerAngles` gives NaN at gimbal lock.
  - A joint with independent scaling still moves with its parent's whole transform (its offset gets the parent's scale), only its own axes leave out the parent's scale, like Blender's "None" scale inheritance the add-on sets. OGI 393's first animation scales the joint above everything to 0.3 and each part to 0.32 and ends on the bind pose at that size. The viewer's `TwinBone` keeps each bone's world rotation apart from its matrix, because animations hide joints by scaling them to nothing and joints under them that don't inherit scale still turn with them.
- **Cameras** (`CameraData`, TwinTech `Common/CameraSubtypes`, verified in the PAL executable, `Ghidra Stuff/Engine_RE`): a camera trigger runs up to two subtypes, each giving the camera's position for the player's. Points (`CameraPoint`, `CameraPoint2` with a `Distance` and `Mode`), lines (`CameraLine` sliding to the player's nearest point plus the base `Offset`, `CameraLine2` sliding by the player's flat distance between `NearDistance` and `FarDistance`), paths (`CameraPath`: the AI paths' B-spline with the same `Parameters`), sampled splines (`CameraSpline`: samples a `StepLength` apart with unit `Tangents`, `Parameters` like a path's, `SplineFlags` bit 0 takes the `Offset`), zones (`CameraZone`: where the player is within `TargetBox` along its X and Z axes is where the camera goes within `CameraBox`; a box is X, Y, Z axes, corner and sizes, `CameraBoxTransform`/`TargetBoxTransform` are them as matrices) and the boss camera (`BossCamera`: the player in arena space through `WorldToArena`, the camera `Orbit.Y` from the axis in the player's direction at the player's height plus `Orbit.Z` while under `Orbit.X`, back through `ArenaToWorld`). The main camera's `Flags` (`ITwinCamera.CameraFlags`) tell the camera controller what to take from it (`FUN_00274e08`): `SetsPitch`, `SetsYaw`, `SetsFov` and `SetsDistance` hand its three angle blenders and distance the `PitchStart`/`PitchEnd`, `YawStart`/`YawEnd`, `FovStart`/`FovEnd` (65536ths of a turn, the blenders are named by the levels' values: 20°, half a turn, 32°) and `DistanceStart`/`DistanceEnd` (5, 10, 4.5 units), as the two targets of a blend over `BlendTime` seconds or, with `ValuesAlongGeometry`, the values at the start and end of the camera's line, path or spline; `BlendsInFrom*` take the `BlendIn*` values while blending in, `NoBlendIn` cuts, `CutsFromSameKind` cuts between two cameras with it, `PassesValueToCamera1/2` hand `Camera1Value`/`Camera2Value` to the subtypes, `SetsYawExtra` gives `YawExtra` to the yaw blender, `NeedsRunningCamera` and `IgnoresPlayerState` gate acceptance (`FUN_001434a0`), the `Controller*` bits are copied into the controller's flags untraced. `Switches` (`CameraSwitches`, 0 on nearly all) has `SecondSlot` and `ResetsController`, `Group` keeps cameras of different nonzero groups from replacing each other, `LeftoverVector1/2` and `LeftoverFloat1/2` are the tools' memory. The camera's trigger has bits 18 and 20 set in the levels, never read. `CameraGeometry` derives what the game stores next to the geometry (a path's and spline's parameters, a spline's tangents and step, the boss camera's other matrix) when it changes, keeping the game's values otherwise. The game reads both boss matrices (`FUN_00279990` computes neither) and uses each as the other's inverse (`BossCameraAt` takes the target into the arena through `WorldToArena` and the camera back out through `ArenaToWorld`, `FUN_0027cfb8` keeps the previous position in arena space), the game's pairs agree to 6e-6, so `WorldToArena` is read-only and follows `ArenaToWorld` in the inspector like a chunk link's `ObjectMatrix` (`InverseMatrixChange`, through `ForeignPropertyAttributes`). `CameraGeometry` also makes the viewport's handles: a draggable point for every point and sample (`Position` nodes may be `Vector4`s, their W stays), a box for each zone box (`Transform` through the box matrices) and the boss camera's arena cylinder (`CameraArenaVisual`), all in the camera paths layer.
- **Triggers** (`TwinTrigger`, verified in the PAL executable): the header's low byte is the tools' `Kind` (50 on most), 0 makes the trigger a plain box of its chunk the sound code tests the player against (`FUN_0022f208`) instead of a trigger node, bits 8-11 are the message bits (`Enums.TriggerFlags`) and bit 12 `NotPolled`; `CheckInterval` is the seconds between two checks of the box (0.3), stored in ticks by the node (`FUN_001f5428`), `InstanceExtensionValue` the tools' list growth (10). **Chunk links**: `Visibility` (`ChunkLinkVisibility`, the flags' low 7 bits: 0 hidden, 1 always drawn, 2 drawn through the load wall as a portal, `FUN_001ea3a8`), `KeepLoaded` and `IsLoadWallActive` (bits 7-13, either makes the linked chunk's own links load a level deeper, `LoadLinkedChunks`), `LoadsWithoutPlayer` (type bit 1: a link with hulls loads its chunk while there's no player yet). A zero `LoadingWall` is no wall (the build writes none), links without one are stored without one (`ShouldSerializeLoadingWall`, a link read back got a zero wall every save wrote). **AI positions**: the game's nearest point search (`FUN_0023c288`, what `SetFocusPositionToNearestPoint`, `LinkToNearestPoint` and `SetNearestPointFlags` use) goes by the coordinates alone, and the W of the position (`AiPositionData.Radius`) is only read by the `NearestPointEdgeDistanceSquared` condition (`FUN_00225be0`), which takes it off the distance to the nearest point: the position's radius. The viewport draws it as a ring on the ground (a sphere while selected) and drags it by a handle on the ring's +X side (`AiPositionRadiusVisual`, `AiPositionRadiusHandle`). Their `Flags` (bits 1, 2, 4 in the levels) have no reader in the executable, an object's `SubType` (bits 12-19 of its header, 1 everywhere but the red wumpa's 17 and the projectiles' 18) only picks a pickup's node (16, 17) and drops its properties (16). The collision data's `Version` (3001) and the dynamic scenery's (0x10009) are read and never checked, a dynamic model's `LeftoverInt` (8) never read, its settings' `LeftoverByte` (22) never read and `ChannelCount` (7) turned into a mask nothing tests. A scenery's `UnusedByte` is never read, the root's `TreeDepth` is handed to the node search that ignores it, a tree node's `BoundsMin`/`BoundsMax` are its octree cell the search goes by, `BoundsCenter` (W the radius) and `BoundsHalfSize` the tools' values. A texture's `Reserved1`/`Reserved2` are 0 and unread, `SizeWords`/`ReservedBlocks` the sizes in blocks below.
- Instances belong to one of a chunk's 8 layouts (`LayoutID`, part of their URI and folder). The game doesn't name them, `ChunkLayouts` names them after what it keeps in each (0 main, 1 and 4 cameras, 2 and 5 crates, 3 extra actors, 6 AI navigation). Layout 7 only holds the default chunk's collision surfaces.
- **Chunk overrides**: a chunk keeps its own values of the assets it shares with other chunks (`LevelChunk.Overrides`, `AssetOverride`) instead of copies of them. Values are kept by their JSON path in the asset (`AssetOverrides`): its metadata without what makes it an asset of the project, and its data under `AssetData` when the data is kept as JSON the default way. Other data (models, pictures, sounds, code) can't have a chunk's own values, only the asset's metadata can.
  - Creating a project first makes a variant for each chunk after the first whose item has the same ID but other content (`Variation` is its chunk path, `GetUriByTwinId` finds the requester chunk's variants first). `VariantMerger` then turns every variant that only differs in values into an override of the first chunk's asset (a level's own version of a startup object into one of the global asset) for every chunk using the variant, and redirects what referred to the variant, including models' material URIs. A variant is often used by more chunks than the one it's named after, a later chunk with the same content found it by its hash; chunks use what they list in their resources and item versions and what those refer to down to other chunks. Variants no chunk uses (a chunk's model found the asset by its ID) go without values. Of the PAL version's 850 or so chunk variants only 5 textures of other pictures and 3 behaviour graphs of other code stay, the rest are 379 overrides of 111 chunks and every chunk builds byte-identical to before. A texture variant that stays is the chunk's own picture of an ID (the game reuses texture IDs, a hub's 16x16 `3B69A5CF` is a 32x32 one elsewhere) while the shared materials link to the base by URI, so the merger gives the chunk an override on every material linking the base with the link pointing at the variant (`LinkMaterialsToTextureVariants`), or the chunk built with the other picture, like hubd's whack-a-worm HUD did. Sounds were all the same, textures only differed in their header's leftovers, objects in their name, behaviour pack, template values and whether they list their resources.
  - Building a chunk exports its overridden assets as views (`ChunkOverrides`, `AssetOverrides.CreateView`): copies with the values, with the asset's URI and data file, made once per chunk because the chunk's resolution tells assets apart by their object. Views never save themselves.
  - A chunk's document edits the assets it shares through its views (`ChunkOverrideSession`, the property graph's `Overrides`), saving turns what they differ in into the chunk's overrides. The chunk's own assets (its resources, instances and what's in its folder) are edited as they are, and data without values of its own is the asset's, edited for every chunk. The inspector shows the chunk's own values with blue names, right clicking one puts the shared value back or shares the chunk's (`OverrideMenu`). A chunk reaches most of what it shares through links (an instance's object), their `->` opens the chunk's view in its inspector (`UriLinkViewModel.OpenDocument`) and an instance shows its object's view in the viewport. Links to a view the chunk has values of its own in are blue as well (`DocumentNodeViewModel.GetLinkedView`). Data marked `[NoChunkOverrides]` (objects' names, the game only goes by IDs) is left out of views and overrides. A view's own values are the ones the chunk has or changed that still differ from the asset (`ChunkOverrideSession.GetOwnValues`), the asset can change in its own editor while the chunk's document keeps its view. Deleting an asset fixes the values of chunks' overrides that link to it the way the asset's own would be (`LevelChunk.FixOverrideValues`).
  - Each chunk still lists the objects and sounds it has (`LevelChunk.ItemVersions`), the build treats a startup object a level has as the level's own (it lists its resources). Building resolves those through `ITwinItemFactory.ChunkVersions` (`SerializableAsset.ChunkVersionOf`), which only swaps in the variants that stayed. Behaviours are one asset per name: the PAL version's chunks only differ in leftover memory in unused parameters (the NTSC version has the `0xCD` fill there).
- **What a chunk holds** (checked on every chunk of the game): the behaviours objects list, and the OGIs, animations and sounds they list or name in their slots. A graph's starter makes the game run the graph on its own and is only in chunks with objects listing it, so objects keep the graphs they list without their starter (`GameObjectData.GraphsWithoutStarter`) and put the starters in (`BehaviourGraphData.AddStarter`). High Seas' rats spawned with another chunk's starter running `COM_GENERIC_CREATURE_DESTROY` on them. The game's copies of the startup chunk's objects in levels list nothing (`ReferencesResources` off, not edited: chunks keep the disc's values as their own, and a startup object a level gets without having it on the disc is a copy, `GameObjectData.ListsResources`). Those, and startup objects a level has no version of its own of, bring no behaviours into it, only their slots' OGIs, animations and sounds and the objects they or their behaviours spawn (a crate's extra life). Instance templates (only the startup chunk's crates have behaviours in them) and instances' spawn scripts refer to starters, the ID before their graph's. The game reads templates into a table nothing looks up (`LoadInstanceTemplate`), so a template is its object, its `BehaviourStarters`, its `InstanceStateFlags` and properties; the tools' copies of the object's header bytes and list headers are written again from the object on build (`InstanceTemplateData.Export`).
- **Particles** (`TwinParticleSystem`, `TwinParticleEmitter`, `Rendering/Particles/ParticleSimulation`), worked out from the PAL executable (the Ghidra project's `GameParticle`/`ParticleInstance` structs and `GenParticle_*`/`GenerateParticles`/`BuildParticleRenderTable` functions, notes in `Ghidra Stuff/Particles_RE`): emitters (`ParticleSystemInstance`) play the system they name, their chunk's own or the default chunk's (`DefaultParticles`, one per version, `ParticleData.GetUsableSystems`/`FindSystem`, `ParticleSystemFieldViewModel`). Everything runs in frames of 1/60 s. An emitter on makes `GenRate` particles a frame (one every that many frames when negative, none at 0) for `EmitterOverTime` frames, waits `EmitterOffTime` (plus 1 to the random extras), the cycle shifted by the timing offsets against the frame counter, and only while the camera is between `CutOnRadius` and `CutOffRadius` (drawn within `DrawCutOff`). `MaxParticleCount` is what one lifetime makes times the ghosts (`TwinParticleSystem.ComputeMaxParticleCount`, the game recomputes it at load and TT Lab on write), the ring of slots that new particles write over, at most 1024. A particle is a start, a velocity and a spawn time: position = start + velocity·t + (0, `Gravity`, 0)·t² in the emitter's gravity space (the acceleration is twice `Gravity`; drips and splashes have negative gravity, fire and steam positive), the gravity rotation turning that space into the world. Rotations are 65536ths of a turn applied tilt (about Z, the up leans towards -X), yaw (about Y), roll (about X); the emit rotation turns the start and velocity within the gravity space. `GenSort` picks the generator (`GenSortType`: box, ranges, radial ring/cone with `RandomStart` = radius, yaw, tilt and `RandomEmit` = speed, yaw and tilt spreads, rotor, spheroid, plane bouncers with the emitter's `PlaneOffset`/`BounceFactor`/`BouncePlaneAngle`, area-even sphere, star), `GenCode` a fixed velocity-from-start rule (always 0 in the data). Ghosts are copies spawning `GhostSeparation` apart. Sizes and jibber amplitudes are ten thousandths of a unit, jibber frequencies cycles per life, colors bytes with 128 leaving the texture as it is, curves keys of a life fraction and a value sampled at 64 steps (the first pair of keys enclosing the step, 0 outside), texture rectangles pixels plus 2^19 (2^18 in a few systems; the game adds 2^19 and keeps the low 10 bits, `ParticleEmitter.TexturePixel`), `TexturePage` one of the default chunk's three pages. **Blend modes** (`ParticleBlendModes`, picked by name with `ByteChoiceFieldViewModel`): loading a page (`FUN_0019d9d8`) makes its four shaders in bucket 22, all dropping alpha under 5/128 and testing depth: 0 Additive (preset 1, 629 retail systems), 1 Subtractive (preset 2, the skid marks and the warp splash), 2 the page material's own first shader with those bits forced (normal blending in retail: smoke, dirt, feathers) and 3 Cutout (no blending, writes depth, unused); 0-2 don't write depth, 4-6 read the next page's IDs as the shader. 7 Distortion (unused) draws hexagons in bucket 23 through shader type 0x18, which copies the frame first (`FUN_001d6aa8`): the VU1 program (0x2e0960, `Ghidra Stuff/Particles_RE`) makes six triangles inside the particle's quad pointing along its height, the middle showing the copy where it is with the particle's alpha, the rim alpha 0 showing it moved by the corner's offset times (`Distortion.X` / 16384, -`Distortion.Y` / 4096), fading out with the depth to nothing at 40 units. `DrawFlag` is the draw list: the game draws list 0 (the modes in the order 3, 2, 1, 0) and list 2 (only mode 7, every mode 7 system is put there at load), never list 1. The `Unused*` fields and the tools' size/rotation ranges are never read by the game, `TextureFrame*` are recomputed and then never read (probably a texture animation), the switches and groups of emitters aren't read either. The retail data only uses GenSorts 0, 6, 7, 8, 9 and 11, version 0x1E, and no gravity rotation, roll, offset or plane on any emitter. Chunk viewports run the emitters' systems and draw them in their own pass with the default chunk's texture pages: the emitters queue their particles and `ParticlePass` draws them at its end in the game's order of the modes, each with its blending (`ParticleEmitter.DrawQueued`, `Particle.vert`/`.frag`; the page material's preset for mode 2, `ParticleData.GetPageBlends`), the hexagons over a copy of the frame (`ParticleDistortion.vert`/`.frag`), and leaves out what the game never draws (`ParticleBlendModes.IsDrawn`). The simulation reads the systems and emitters every frame and lines its cycle up again when the timing changes (`ParticleSimulation.Rephase`), so every edit shows right away; the default chunk's viewport plays every default system on a grid ignoring the camera (`DefaultParticleData.GetViewportObjects`). The curves are edited on a graph (`CurveGraph`) and the color on a gradient bar with a color picker (`GradientBar`), both through `ParticleCurveKeys`, which keeps the keys in order and the curve's end at 1; a key put in or taken out with the keys it moves is one step, so is a drag. A system's picture (`TexturePage`, `TextureStart`, `TextureEnd`, the corners hidden with `[EditorHidden]`) is edited as a rectangle of pixels on the page (`ParticleTextureRect`: `FromGame`/`ToGame` keep a corner's offset and fraction while its pixel stays, a start after the end mirrors) with `ParticleTextureViewModel` and `Controls/ParticleTexturePage`: the default chunk's three pages to pick from, the page with the game's pictures outlined (`ParticleTextureBank` clusters the usable systems' rectangles within 3 pixels) to click, the rectangle and its corners to drag (one step each), typed pixels and mirroring. Every particle item of both discs round-trips byte-identically. Systems', emitters' and decal variants' names are read up to their NUL (`ParticleNames`), what the tools left in the 16 (8) character buffer after it (the default chunk's systems, some level emitters) is kept in `NameLeftover` and written back, an emitter's name has to match its system's. A system's name is its own in its version of the game (`ParticleSystemNames`: the loaded particle assets as they are, the others by the names in their files, read in the background when a name is first checked and again when a file changed): the name field refuses a name another system has and says whose (`ParticleSystemNameFieldViewModel`, `TextFieldViewModel.CanCommit`), a system put into a list gets a free one (`NEW_SYSTEM`, `NEW_SYSTEM_2`, numbered within the 16 characters), and renaming one takes its emitters along (`ParticleSystemLinks`, one per document): the emitters of the same particles that played it as part of the rename's step, and once a renamed system of the default chunk is saved, the emitters of every other chunk of the version that play it (not those whose chunk has a system of that name, which they play instead), in the background, through the document of a chunk that's open, logged when done. The retail data names 47 systems more than once (four `XXX` in the default chunk, default systems that levels have copies of), their fields show it.
  - The default chunk's particle data also holds the **decal** system (footfalls, ripples): `UnusedDecalInt`, the `DecalUvPacket` (a VU1 packet of UV rectangles the game writes its GIF tag over), 16 `DecalTypeMarkers` (the tools' pointers, nonzero means a type follows) and the `DecalTypes` (`TwinDecalType`, 0x890 bytes: DMA tag, 15 variants of 4 color keys with alpha in W and 4 size keys with the time in W and the lifetime in the first's, the count, the variants' names). The game DMAs a type into VU0 memory and runs a microprogram per decal, so what the variants' vectors do beyond the lifetime is read off their values. The retail data has one type, "Ripple" and "FootFall".
- **Fonts** (`FontData`) are edited with `FontEditorViewModel` (`FontEditorDesc` on `CharacterData`): every page with its characters' boxes drawn over it (`Controls/FontPageEditor`: the game keeps its pages upside down, the editor draws them the right way up (`GetShownRect`, a box's top row shown at `height - Bottom`, dragging down lowers `Bottom`) while the page's texture and a replaced PNG stay the game's way; clicking picks the character, dragging moves the box, dragging its bottom right corner resizes it, one history step per drag), the character table (code, page, left, bottom, width, height, edited through the document's nodes), adding and removing characters at the end, and replacing the selected page's picture with a PNG (8 to 256 pixels, powers of two; it replaces the page's texture asset right away, which no history can undo).
- Text files (`TextFileData`, Latin-1, written back byte for byte) are edited with the game's fonts (`TextFileEditorViewModel`): `Controls/PsfGlyphs` cuts every character's glyph out of a font's pages and `Views/Editors/Global/PsfGlyphGenerator` draws the text with them, a toolbar inserts the characters the fonts draw as controller buttons (`PsfGlyphs.ButtonCharacters`, the same ones in both versions), then every other symbol the font draws (`PsfGlyphs.Characters`, what a keyboard has no key for) and `~`, which the game starts a new line on. Undo is the document's history like the code editor's (the editor's own stack is off, `TextFileEditorViewModel.OnCurrentValueChanged` hands the text back to the view, typing at one place is one step until the caret moves). A font's table starts at the space, a character's box goes up from its bottom left corner (the page has it upside down), and page 0 and 1 are the first page, 2 the second and so on (the PS2's fonts number from 1 and give characters without a glyph 0, the Xbox's use 0 for the first page as well).
- Sounds are one asset per language and content, a sound item's hash doesn't cover its samples. A PS2 sound plays at its `Pitch` (`ITwinSound.PitchOf`: the sample rate times 4096 over 48000, truncated, handed to the driver by `FUN_001dfa38`), kept on the `SoundEffect` asset and set from the wav's rate when one is replaced; the Xbox item keeps the rate and derives it. `Param1` (32) goes to the driver with every play, `Param2`-`4` (16, 8192, 8192) and the `Header` (3, bit 0 clear = stereo) are read and dropped. Objects keep one sound per slot and chunks get every language's version of it. The startup chunk's sounds no object references (the game plays them itself) are its chunk resources. Without a playback device (the audio service throws when it opens none) sounds are still edited and replaced, only playing them is off (`SoundEffectViewModel.CanPlay`). **Loops**: a PS2 sound loops through its ADPCM blocks' flags (`TwinTech/Libraries/ADPCM`: blocks of 28 samples, bit 0 the last block played, bit 1 go back to the loop's start after it instead of stopping, bit 2 the loop's first block). Of the NTSC version's 812 sounds 717 play once (`00.. 01 07`: the last block flagged 1, then a silent block looping on itself; 166 have `00` there) and 95 loop from their second block to their last (`00 06 02.. 03`, nothing after); the Xbox's PCM sounds keep no loop. `ADPCM.Decode` includes the block ending the sound (the old decoder dropped it, 28 samples of every sound), `FindLoop` reads the loop and `Encode` writes both layouts, the loop's points rounded down to blocks and the samples after the loop left out; every retail sound comes back with its blocks' flags (the harness's `soundtrip` mode). The loop is the `SoundEffect` asset's `LoopStart`/`LoopEnd` (samples, the end exclusive, -1 without one), set on import from `ITwinSound.LoopStart`/`LoopEnd` and handed to `SetDataFromPCM` on build. The sound's editor draws the waveform (`Controls/SoundWaveform`) with the loop's handles to drag and buttons for the loop's start or end at playback, the whole sound or no loop (`SoundEffectViewModel`, whose node is the data's `[custom_editor]` one: the loop's nodes are the asset's), all in blocks of 28 samples through the document so undo covers them, and the preview plays the loop (SoundFlow's loop points); replacing the wav takes its sampler chunk's loop (`Riff.LoadRiff` reads chunks by their headers now) or loops the whole new sound when the old one looped.
- **List limits** (verified in the PAL executable): lists the game keeps in fixed places or counts in small fields have `[EditorParam(DocumentCollectionViewModel.MaxCount, n)]`; the inspector's add button stops there and says so (`CanAddItem`, `AddItemHint`), so do Ctrl+D and placing prefabs (`PropertyNode.MaxElements`/`IsFull`), undo and redo still put back what they took out, and a build refuses longer lists (`AbstractAssetData.CheckCount`, lists made before or by hand). A material has 4 shader slots with their count after them (`ReadMaterialShader` 0x1bbea0: a 5th pointer overwrote the count and the reader went on into the next material, retail materials have 1 or 2), a font 3 pages (`ReadFont`), the default chunk 16 decal types, the game's particle tables 300 systems and 768 emitters of every loaded chunk together (`ReadMainParticleSection`: systems past it are read and dropped, emitters not read; building a chunk warns when its systems and the default chunk's 255 go past 300), an object 255 of each slot, trigger message and instance property (its header counts them in bytes, like templates' and instances' property headers). A link hull's corners are moved, not added (its faces are made of them). TwinTech refuses collision triangles the packing can't hold (18 bit vertex indexes, 10 bit surface index) and hulls past its byte indexes and offsets. Paths, triggers' instances, instances' references and chunk links are allocated to their size.
- Link fields (`UriLinkViewModel`) browse the assets of their `BrowseType` in their `BrowseScope`: the project, the document's assets, or `Scope.Chunk`, the chunk the edited asset belongs to (an instance's or trigger's instances, positions and paths). A link without a type browses everything. `GetBrowseCandidates` is what the browser gets.
- Toggling a bit of a `[Flags]` value in the inspector sets the whole value as its enum (the bit's node `SetsParent`, so a click is one step, it was two). A node whose value gets replaced raises `Changed` on every node under it, so editors of its parts (the bits' check boxes, a vector's components) show what undo put back.
- **Linked fields** (`[EditorLinkedField]`, `IFieldChange`: a trigger's `Kind`, `NotPolled` and argument bits and its `Header`, a chunk link's `ObjectMatrix` following its `ChunkMatrix`, a boss camera's `WorldToArena` its `ArenaToWorld`) run `DataChanged` when the value they follow changes; what they write is a consequence (`PropertyChange.IsConsequence`) recorded in the edit's step (one undo of a header edit took back only the last field), and while undo and redo apply the graph `IsReplaying`, so only `Linked` runs and the values come back as they were (made again, a link's object matrix got other floats: it's its chunk matrix's inverse only up to rounding). Values compare by their bits (`PropertyNode.IsSameValue`), undo couldn't put a NaN of other bits back. They get linked whenever nodes go into the graph (`PropertyGraph.Index`, so placed and relinked resources have them too) and only `Linked` runs then, which sets up what editors show (read-only fields): values written while linking changed assets just by opening them (every camera opened and saved lost its trigger's kind, links' matrices drifted). The fields shown of a trigger's header aren't stored, `TriggerData.DeriveFromHeader` works them out in every constructor and on deserialization (`[OnDeserialized]`, a camera keeps its trigger in its own file). New triggers are kind 50 checked every 0.3 s (kind 0 is the sound code's plain box), new cameras' triggers `0x140000` with no interval, like most of the game's.
- **Combo box editors** (enums, sample rates, layouts, render buckets, a slot's animation) ignore what the combo box hands back while they show a value (`_isShowing`) and give it a new list only when the choices change: a combo box whose list changed handed its old pick back, which the OGI animation field and the value then passed back and forth until the stack ran out, and a list changed in place made it pick items it no longer had.
- Assets are addressed by `LabURI` (`res://...`), not by game ID. `AssetManager.Get()` is the global registry (`GetAsset<T>(uri)`, `GetUriByTwinId<T>(requester, id, layoutId)`). Mark data classes that hold `LabURI`s with `[ReferencesAssets]`.

### UI and MVVM
- `AvaloniaScheduler` (the main thread scheduler) runs work right away when it's already on the UI thread, so `ObserveOn` doesn't keep the order of changes raised on several threads (tabs load on the task pool). Use such changes to look at the current state again after `ObserveOn` instead of passing their values on (`ChunkResourcesViewModel.FollowActiveEditor`).
- Avalonia 11 + ReactiveUI, with compiled bindings on by default, so every `.axaml` needs `x:DataType`. Docking uses `Dock.Avalonia`, and the code editor uses AvaloniaEdit with TextMate. The AgentLab grammar is `AgentLab/agentlab.tmLanguage.json` (embedded resource), served through `AgentLab/AgentLabRegistryOptions.cs`. Scripts are checked live with `AgentLabCompiler.Check` against the commands of the asset's version of the game (`Project.GetActionDefinitionsFile`), and AgentLab errors are `AgentLabSyntaxException`s carrying the line and column. Objects' command packs can only be a list of commands, no commands included (`AgentLabCompiler.CheckCommands`/`CompileCommands`, the `AgentLabCommandsOnly` editor param). Completion suggestions and parameter hints come from `AgentLabCompletion` in TwinTech, which scans the text before the caret instead of parsing, because scripts being typed are rarely valid. `AgentLab/AgentLabCodeCompletion.cs` shows them in the editor: the parameter hint follows the caret into a call, fields are suggested inside a packed argument's braces and `Prop`/`Raw`/`Float`/`Int`/`Angle` inside calls, and the rows are cached per item. `AgentLabCompletion.Warm` parses the definitions off the UI thread when an editor activates, the first completion parsed them on the first keystroke before. `AgentLabHoverHints` shows `AgentLabCompletion.GetHover` (an action's or condition's signature, a field's type, a keyword's or attribute's meaning) as a tooltip while the pointer rests on a word. A state names the behaviour it runs (`state S(COM_X)`, the `"res://..."` strings of older scripts still compile), resolved by `BehaviourReferences` within the asset's package and the packages it depends on (`AssetManager.FindByName`/`GetAssetsInScopeOf`: the global packages depend on nothing so their scripts only name their own, the PS2 and Xbox versions never see each other's, a level's own graph of a global name wins and the global one is then written by its URI). Importing writes the name when it finds the graph from there (`BehaviourReferences.ReferenceTo`). Inside the parentheses completion lists the behaviours in scope (`CodeEditorViewModel.GetBehaviourSuggestions`), the live check reports names out of it (`AgentLabCompiler.Check`'s `behaviourExists`), hovering one shows its URI and Ctrl+click or F12 opens it (`AgentLabNavigation`).
- DI is set up in `App.axaml.cs` and `DependencyInjection.cs` (MS DI bridged to Splat). Every non-abstract class ending in `ViewModel` is auto-registered as transient, except `ShellViewModel` (singleton `ILabManager`) and the types in `DependencyInjection.SingletonViewModels`. Views are matched to view models via `RegisterViewsForViewModels`, and `Util/ViewLocator` falls back to a view registered for a base type. Service-locator access (`Locator.Current.GetService<ProjectManager>()`) is common.
- **Docking** (Dock.Avalonia, ReactiveUI model), with layouts built in code rather than XAML:
  - `ViewModels/DockFactory` owns the shell layout. Its panels are singleton view models that derive from Dock's `Document`: Project Tree, Log, the Scenes/Resources `EditorsViewerViewModel`s, Chunk Resources, Inspector and History (`ChunkResourcesViewModel`, `ChunkInspectorViewModel`, `HistoryViewModel`, tabs next to the Project Tree by default), and Prefabs (next to the Log).
  - Scene tabs only have their viewport. The Chunk Resources and Inspector panels show the document and inspector of the scene tab last worked on (`EditorsViewerViewModel.ActiveEditor`), inspecting something brings the Inspector's tab to the front (`DockFactory.RevealPanel`) and the resources panel keeps each chunk's view while its tab is open.
  - The chunk's `ChunkResources` are shown like the project tree (`ChunkResourcesTreeViewModel`, `Views/Editors/ChunkResourcesTreeView`): a folder for each kind of asset (level chunks always have the instance kinds, empty or not), the layouts of the kinds that have them, the resources in the chunk's order. Picking one inspects it (the viewport selects it), what gets inspected elsewhere gets its row picked and brought into view, a double click or Enter frames it in the scene, F2 renames it (its `Alias` through the document), Delete takes an instance of a layout out. A right click on a folder makes only its kind (`ViewportViewModel.CreateResource` of `CreatableTypes`, in the folder's layout or `DefaultLayoutFor`, the layout the chunk keeps most of the kind in; object instances of `DefaultObjectFor`, paths with four points, AI paths between the two selected AI positions), the links and particles folders add a link or an emitter. New resources go to the scene's cursor, in front of the camera without one (`NewResourcePosition`).
  - Layouts are serialized with Dock's Newtonsoft serializer, which resolves the panels through DI. `ValidateLayout` restricts which `$type`s are allowed.
  - The last layout is saved to `layout.json` next to the executable when the window closes, and restored on startup.
  - Each editor panel has its own `EditorTabsFactory`/layout, and its tabs are `TabbedEditorViewModel` documents (`SceneEditorTabViewModel`/`ResourceEditorTabViewModel`). Never share a factory between the shell and editor docks: Dock allows dragging between every `DockControl` that shares a factory.
  - Ctrl+S/Ctrl+W/Ctrl+Z/Ctrl+Y (and Ctrl+Shift+Z) are `KeyBinding`s on the tab views, which are `Focusable` so a click anywhere in an editor moves the focus into it. `EditorsViewerView` binds them as well for when the focus is on the tab strip, and the chunk's panels and History bind the undo keys for the active editor. Closing goes through `TabbedEditorViewModel.RequestClose`, the same path as the tab's close button, and moves the focus into the editor shown next (`EditorsViewerView.OnEditorClosed`), the next Ctrl+W had nowhere to go otherwise. They fire before AvaloniaEdit sees the key, and the code editor has no undo of its own (its `UndoStack.SizeLimit` is 0, it would undo the same typing again or the loading of the text): the document's history sets the code back, `CodeEditorViewModel.OnCurrentValueChanged` hands it to the view and `CodeEditorView.ApplyCode` replaces only what differs, with the caret at the change. Moving the caret somewhere else ends the step typing keeps changing (`UndoHistory.CloseStep`), so typing at one place is one step.
  - Saving a document saves every asset its edits touched (linked assets are edited in place) and clears `IsDirty`.
  - Every document keeps an undo tree (`DocumentViewModel.History`, `UndoHistory`) of the property graph's changes (`PropertyChange`: values, and elements put into or taken out of lists by their index). Changes of one value in a row (typing, dragging) are one step, `BeginGroup` makes one step of several (a gizmo drag, placing an instance and moving it to the cursor). Changing something after undoing starts a branch next to the undone one, `GoTo` goes to any entry, a change after a redo is a step of its own. Replacing a whole asset's data (textures, sounds) can't be undone and starts the history over. A value of another type (a camera's subtype picked or taken away) is a step like any other: its node makes its children again for the type it has (`PropertyNode.RebuildChildren`, `ChildrenVersion`) and composites showing them build theirs again, the old ones showed the old subtype's values. `IsDirty` is off again at the entry the document got saved at. When the inspected node leaves the graph (its resource deleted or its placing undone, its link pointed elsewhere) the inspector goes to what took its place or closes (`DocumentViewModel.FollowInspected`): editing it changed nothing the document had, and its steps' paths pointed at whatever came to its index. The viewport follows instances taken away or put back while undoing (`History.IsApplying`), placing and deleting them updates it directly. The History panel shows the tree of the editor last used (`EditorsViewerViewModel.Used`) and goes to the entry picked. It hears every change, typing included, so it only swaps the rows that differ while the tree stays the same.
  - Only `[DataMember]` properties of dockables are serialized, so view model state on panels stays out of layout files.
  - Dock keeps closed dockables alive through each `DockControl`'s control recycling cache and its private activation history. `EditorTabsFactory.ForgetDockControlReferences` evicts closed editors from both; the activation history is reached by reflection, so recheck it after updating Dock.
- **Tooltips** of the inspector (`DocumentCompositeView`/`DocumentModelView`, the `Hint`) sit on the property's name and a composite's header, not on the row: a row's tooltip showed while the pointer was anywhere in the rows under it and stayed until it left them all. They show after half a second, and popups are drawn in the window (`OverlayPopups` in `Program.cs`): every tooltip was a window of its own, and hovering across rows opened and closed one after another, which stalled the whole UI. Don't set `ToolTip.BetweenShowDelay` to 0: a tooltip closing and the next opening in the same tick made the next one instant.
- **Property graph paths**: a node's `Path` is its parent's plus its own `Segment` (`.Name`, `[index]`, `[data]`), worked out when asked and cached until the graph's `StructureVersion` changes (every insert, removal or attach), and `PropertyGraph.Find` walks the tree a segment at a time (`FindChild`, elements by index). There is no path dictionary: keeping one meant renaming and indexing everything under a big list on every change, and undoing fifty deleted instances of a chunk took seconds (`PropertyGraphListTests`). Code reacting to changes compares nodes and walks parents (`ViewportViewModel.IsWithin`) rather than paths.
- **Angles in degrees**: values the game keeps in 65536ths of a turn (cameras' pitch, yaw, fov and blend-in angles, emitters' gravity and emit tilt, yaw and roll, the bounce plane angle) are edited with `AngleEditorDesc`/`AngleFieldViewModel` in degrees, converted back to the property's integer type (unsigned ones wrap around the turn, `Int16` goes the shorter way). A sound's `Pitch` is picked as a sample rate (`SampleRateEditorDesc`, the known rates plus the current pitch when it's none of them).
- **Current editor system** (the one to use for new work) is document/property-graph based. Asset data properties carry attributes from `Attributes/` (`[Editable]`, `[EditorParam]`, `[EditorLinkedField]`, `[EditorHiddenIn]`, `[EditorReadOnly]`, `[ViewportEditable]`, ...). `PropertyGraphBuilder` reflects an `IDocumentModel` into `PropertyNode`s (TwinTech's types, which can't carry these attributes, are registered in `DocumentMetadataCache.RegisterForeignTypes` with every property shown, and `ForeignPropertyAttributes` gives single properties of them attributes: hints, links, read-only), and `EditorDescRegistry` maps property types to `EditorDesc`s, which create `Document*ViewModel` / `*FieldViewModel`s. Views derive from `DocumentBaseView<TViewModel>`. These view models use ReactiveUI source generators (`[Reactive] private bool _field;` on `partial` classes), `ReactiveCommand` and DynamicData.
  - Documents easily have thousands of editors, so editor view models stay cheap to create: `DocumentBaseViewModel` computes derived properties instead of observing them with `WhenAnyValue(...).ToProperty(...)`, creates its validation context on first use, and sub-editors (vector components, matrix columns) are made when shown. Only lists (`DocumentCompositeView` of a `DocumentCollectionViewModel`) of plain fields virtualize their items, lists of structs and models (`DocumentModelView`) never, whatever their length: a virtualizing panel takes the items it hasn't made for the average size of the ones it has, which is way off when items differ in size (a struct expanded among collapsed ones): lists jumped and dropped editors in sight, and with an expanded item near the end of a long list (the default chunk's 255 particle systems) the extent flipped as the panel made and dropped it, the scroll viewer clamped its offset each time and the layout cycled until the UI froze (`ListVirtualizationTests`). A collapsed model row costs 3 to 6 ms (mostly the Expander's template), so the Inspector panel keeps each document's inspector view and scroll position while its tab is open (`ChunkInspectorView`, like the resources panel) instead of building them again on every switch. Composites build their children once per expansion and keep them by the editors themselves: kept by their paths, which move when elements go in or out before them, a list's element put back by undo replaced the editor of the one that had moved to its path. List elements with a `Name` show it next to their index and follow it. Captions are at most 200 pixels wide and wrap, long ones squeezed the value next to them to nothing. An asset's data has no editor of its own, its properties are laid out after the asset's (`DocumentCompositeViewModel.EditorInline` on `AssetData`), and data with nothing to edit shows nothing. Its nodes are still under `AssetData` in the property graph.
  - A document has one scroll viewer (`Controls/DocumentScrollViewer`, in `DocumentView` and the Inspector panel, vertical only): composites and models have none of their own and every editor expands downwards, only custom editors that lay out on their own (font pages, animation lists, particle graphs) scroll inside it. Tests hosting `document.Inspector` wrap it in one like the panel does. `FitToScrollViewport` stays for editors inside a scroll viewer that scrolls sideways.
  - Code and text editors (`EditorDesc.ShowsInSidePane`: `CodeEditorDesc`, `TextFileEditorDesc`) of the document's own asset (not what it links to, nothing under a `[data]` node) go in the document's side pane (`DocumentViewModel.SideEditors`, the right column of `DocumentView` with a splitter, each with all its height, `DocumentNodeViewModel.IsInSidePane`) and are left out of the composites (`ShowsInSidePane`); in the inspector they stay inline with a fixed height.
  - Scrolling a long list recycles its rows' views: `Controls/RecyclingItemsControl` keeps a recycled row's content (ItemsControl clears it, which dropped the row's whole subtree, about 80 controls for a point, and made it again for the next item: 70 ms per wheel notch on a 3000 point path, 19 now), and the `ViewLocator` is an `IRecyclingDataTemplate` that hands an existing view of the type its next view model (`IRecyclableView`: `DocumentBaseView.Recycle`; ReactiveUI's bindings follow the view's `ViewModel`, only views whose activation decides something from it or whose controls reset while it changes, combo boxes, `RebindsOnRecycle` and get their bindings made again; custom editors with state of their own set `CanBeRecycled` false). `ListRecyclingTests` checks it.
  - `DocumentViewModel.OpenInspector(node, focus)` expands the inspector down to `focus`, highlights and expands it and scrolls it into view (without a focus it just expands `node`). Each composite hands its view a one-shot `NodeScrollRequest` that the view takes, since views of recycled items get created again and a lasting request made them scroll back. `DocumentBaseView.BringNodeIntoView` retries after each layout pass until the document's scroll viewer shows the target, virtualized lists realize it on the way.
  - A material's render bucket is picked from a dropdown of the game's 28 (`RenderBuckets`, `RenderBucketEditorDesc`), named after what the game's materials and code use them for. Bytes the game gives each value a meaning of (a particle system's blend mode and draw list) are picked the same way from `NamedChoice`s (`ByteChoiceFieldViewModel`, a value without a meaning still listed).
  - The inspector's rows go in the order their properties are declared, a base class's first (`DocumentMetadata`, `DocumentNodeViewModel.DeclarationOrder`), after the explicit orders (`EditorExplicitOrder`).
- **Legacy** Caliburn.Micro view models (`Screen`, `Conductor<>`, `BindableCollection`, `NotifyOfPropertyChange`, `[MarkDirty]`, `IEventAggregator`) remain in older editors such as `TriggerViewModel`, `ShellViewModel` and the resource tree. Keep that style when editing those files, but don't build new editors on it.
- The codebase was ported from WPF. Commented-out `DependencyProperty.Register` blocks are leftovers.

### Rendering (`Rendering/`)
- A custom Silk.NET OpenGL renderer draws to an offscreen framebuffer, which is shown in Avalonia via `Controls/Viewport.cs`. It uses render passes (`Passes/`), batches, a scene graph (`Scene/`) and gizmos. GLSL shaders live in `TT Lab/Media/Shaders`. Math uses GlmSharp (`vec3`, `mat4`), and `Extensions/GlmExtensions.cs` converts to and from Twinsanity vectors.
- GL work must be queued onto the render thread (`RenderContext.QueueRenderAction`), and UI work onto `Dispatcher.UIThread`. Scene graph structure (adding and removing children) changes on the render thread. Transforms, colors and visibility get set from the UI thread. What the render thread reads the UI thread may be changing: the selection it draws is an array replaced whole (`EditingContext`), a resource's objects are made again for the asset its node had when the rebuild got queued, not for whatever a later undo put at the node's index (that made another resource's objects twice), only while the node is still in the graph, and a rebuild reading the graph while the UI thread changes it (undoing many steps in a row) is tried again (`RebuildAttempts`); removals of gone resources are worked out when they run, and `Renderable.RemoveChild` only removes the child itself, never another one of its name.
- Each `ViewportViewModel` owns a `Controls/ViewportHost` for as long as its editor is open: the GL context, the render thread and the frames. The `Viewport` control only shows the host's frames and passes it the input while it's attached, so switching tabs or floating them never rebuilds the scene. The context's window is a hidden 1x1 SDL window only there to make the context current, frames go to a framebuffer of the host's (`RenderContext.OutputBuffer`).
  - The host renders at 60 FPS while it's shown and reads frames back through pixel buffers a frame late. A viewport that isn't drawn for half a second (a hidden tab) only processes its render queue until it's drawn again, and keeps invalidating its control meanwhile: Dock keeps the content of tabs that aren't shown, only hiding it, and a control shown again doesn't draw until something invalidates it.
  - SDL's GL driver stays loaded for the whole run: SDL unloaded it with its last GL window, which crashed the driver while Avalonia and other viewports still used it. Exceptions on a render thread and GL errors get logged instead of ending the application.
  - Viewports don't use ImGui, its one global context got corrupted by render threads using it at once. Overlays are Avalonia controls over the `Viewport` (`ViewportView`).
- Every draw is instanced. Before the passes, each `IInstancedRenderable` (`RenderBatch`, `BillboardSet`) writes its instances' model matrix and color into `RenderContext.Instances`, a storage buffer the shaders index with `gl_BaseInstance + gl_InstanceID`. A `RenderBatch` draws all meshes of a model with one draw per pass. Meshes that need their own uniforms (`RequiresIndividualDraw`: skins, blend skins, material overrides) get one draw each.
- Go through `RenderContext.State` (`GlStateCache`) for blend, depth, culling, polygon mode and programs, and never read GL state back in the render path, because it stalls the driver. Uniforms set every frame or draw are `KnownUniform`s whose locations get resolved when the program links.
- `PrimitiveRenderer` draws editor visuals immediately each frame: thick anti-aliased lines, boxes, spheres, cones, cylinders, quads and discs, and grids (one quad each, with the lines worked out per pixel), in the `World`, `WorldXRay` (faint where hidden) or `Overlay` (always on top) layer. Submit from `IPrimitiveRenderable.DrawPrimitives` (picked up when registered for rendering) or `Renderer.DrawPrimitives`, both on the render thread.
- Triggers' and cameras' boxes are volumes (`LabURI.Volume`), drawn after the scene's transparent surfaces without writing depth, their insides and then their outsides (`VolumePass`, culling front faces and then back faces), so each pixel blends in the same faces whatever order the triangles are in. Their faces are wound counter-clockwise seen from outside, like `PrimitiveMeshes`, which GL renders as front faces (only `FrameCamera` mirrors).
- **Skydomes** (verified in the PAL executable, `Ghidra Stuff/Engine_RE`): a chunk with a sky draws it first instead of clearing the frame (`FUN_001ba350`): the parts of its meshes in their order, at the camera's position (the model matrix is only that translation), into a buffer of half the screen's size (`FUN_001ba488`), then copied over the whole screen two pixels for one with the depth reset (`FUN_001ba6c0`), so the level always draws over it. Every retail sky material is shader type 10 in bucket 0 testing no depth, some blended. The type 10 program (VU1 code 0x2e3ec0) takes its matrices from the 9 quad words 78 past the buffer's base (`3(vi00)`) that only the sky's drawer uploads (`FUN_001c1f90`), never the model's own block (`2(vi00)`, which the level's drawers write): a type 10 material on anything else draws with the last sky's matrix, around the camera at half size in the middle of the screen, and a sky part of another type with whatever object block was left. TT Lab draws every type 10 shader around the camera in one `SkydomePass` (`FollowsCamera` in `MainPass.vert`, `ModelBuffer.PassOf`), in the order of the sky's meshes and parts (`ModelBuffer.DrawOrder`), into a half size buffer blitted over the frame (`Renderer.RenderSkydome`). The frame's alpha isn't shown (`ScreenHorizontalFlip.frag`): GL blends it along with the color, and the alt earth sky's subtracting sun left pixels the window showed through.
- The displayed image is mirrored horizontally. `FrameCamera` converts between world and viewport control coordinates (`WorldToScreen`, `ScreenRay`), so picking has to go through it.
- `EditingContext` owns selection and the `TransformGizmo` (translate, rotate and scale handles picked in screen space). `ViewportViewModel` disables the tools the selection can't use (`ViewportObject.IsTransformSupported`) and stands in the first usable one for the tool the user chose, which comes back once something that supports it is selected. Drags are worked out from where they started and written both to the `EditableObject` and to the viewport object's property nodes, so the inspector follows. Snapping (`GizmoSnapping`) snaps the move along the gizmo's axes, the angle and the scale factor to steps counted from the drag's start, and holding Ctrl inverts it. The selection gets grids on its three planes with a line every move step. Snapping settings are `Preferences` shared by all viewports. **Selection**: a click selects on release, dragging on the scene from empty space selects everything whose box center lies within the rectangle (`RubberBand`, drawn by `ViewportView` over the viewport), Shift adds to or takes from the selection, Ctrl+A selects every instance. The first object selected gets the gizmo (`EditingContext.SelectedInstance`), the others (`ExtraSelection`, `Selection`) follow its drag: the same offset, turns and scales about the first's place where the drag started (`GroupTransform`, applied to their nodes or matrices), Delete takes them out in one step: instances out of the chunk, objects standing for an element (an emitter, a link, a point of a path, which keeps at least 4; every point of it selected deletes the path) out of their list, handles of other parts stay (it used to take the whole resource, every emitter of the chunk with one). Ctrl+D copies every selected instance in place (`PlaceInstances`). Elements put into or taken out of a resource's lists from anywhere else (undo, the inspector's list buttons) make its objects again, what the viewport puts in itself it shows and selects on its own (`_isPlacingElement`). A right click that doesn't turn into a look around opens a menu of instances to make at the cursor (`ViewportViewModel.GetCreateMenu`, the cursor put where the click hit the collision): an object instance of the game's wumpa fruit (`DefaultObjectFor`: an object named WUMPA, else one containing it preferring the global package's `REDWUMPA`, else the first), a position, trigger, camera or AI position, an AI path between the two selected AI positions (`CreateAiPath`, in the first's layout), a chunk link (`CreateChunkLink`: to the first other chunk of the package until another is picked, both matrices at the cursor) and a particle emitter (`CreateParticleEmitter`, playing the first system the chunk can use); the last two are elements put at the end of their resource's list (`CreateElement`, `FindResourceData`), shown and selected like a placed prefab (`ShowPlacedElement`). The rotation rings turn as far as the mouse goes around the gizmo's center on screen (`TransformGizmo`: the angle from the last mouse position added up, so it goes past a half turn, the sign from which way a positive turn moves the grabbed point on screen). The palette (K/P) and the cursor grid (G, arrow keys) are gone, prefabs and snapping do what they did. Viewers of single models draw a `FloorGrid` sized to the model and turn their camera around it (`OrbitCamera`: it starts a little above the model, right drag turns it without going over the top, the wheel and W/S zoom, A/D pan), chunk viewports fly theirs.
- The scene's cursor (`EditorCursor`, where clicking the collision or dropping a prefab put it) is drawn by `EditingContext.DrawPrimitives` like Blender's 3D cursor in 3D: red and white dashed rings on the three planes with the axes sticking out, a fixed size on screen, in the overlay layer.
- Chunk resources show up through `GetViewportObjects`. A `ViewportObject` has a `Category` (toggled from the viewport toolbar), `Position`/`Rotation`/`Scale`/`Transform` nodes that the gizmo edits and `ViewportViewModel` re-applies when they change, an `InspectorFocus` for parts of a resource (a path point), and `RenderDependencies` plus `Refresh` for any other data its visuals use. Objects standing for an element of a list (an emitter, a point of a path, a link and its load wall) name it as their `DuplicatedElement`, Ctrl+D puts a copy of it right after it (`PropertyNode.InsertElement`), other objects of a layout's instances are duplicated as a new instance (`AbstractAssetData.CopyFor`). `Refresh` returning false recreates all objects of that resource, and showing a layer calls it again so objects re-hide what their data hides. A `TransformConverter` maps a `Transform` matrix that isn't one (a chunk link's load wall is its 4 corners, `LoadWallCorners`) and a `PositionConverter` a `Position` node that isn't a position (an AI position's radius handle: the node is the radius, the handle's distance from the position), handles with one aren't picked by the rubber band or Ctrl+A and don't move to the cursor with their object; nodes the inspector makes read-only can't be dragged. Paths are uniform cubic B-splines. Their parameters (`PathParameters`) are every segment's arc length from the start, then 1 over the steps it takes: at least 5, one per step length of the path, which isn't stored and gets worked out from them. The inspector doesn't show them, `PathData` makes them again when it's saved or built after the points changed.
- **Fuzzing the game** (`Ghidra Stuff/RoundTrip_harness`, `fuzzround.sh <label> <seed> <rate> <categories> [property regex]`): changes that share of the editable values of the start chunk's assets (`Fuzz.cs`, reflection over `[Editable]` properties of a copy of the user's project under `TT_Projects/Claude Fuzz root`), builds the ISO and boots it in PCSX2 (`Claude TLM scratch/pcsx2/fuzzrun.py`: the virtual pad skips the videos, PINE reads the chunk manager for the beach's data and the frame counter, screenshots show the intro's "THREE YEARS AGO..."). Found on 2026-09-29: changing objects' `Type` (crates into characters, the character into a pickup, and objects into projectiles, graples or grabbables) freezes the game at the loading screen, so the inspector shows it read-only; slot animations the OGI doesn't have are already written as none. Half of every other value of the beach's instances, triggers, cameras, positions, paths, links and particles changed at once still loaded and played the intro.
- **Prefabs** (`Project/Prefabs/PrefabLibrary.cs`, one JSON file each in `<project>/prefabs`): an instance of a layout, or an element of a list of a resource a chunk has once (a chunk link, an emitter), saved to be placed in any chunk of the same version of the game. `PrefabLibrary.TryGetSource` tells what the viewport's selection can be saved as (the resource node and its `DuplicatedElement`): scenery, dynamic scenery, collision, chunk links and particles themselves can't (`LayoutID == null`), nor a part of an instance or of another part (a hull of a link). `Capture` copies the data and strips every link to a layout instance (`StripChunkLinks` walks `[ReferencesAssets]` types like deletion does: lists lose them, single links become empty), everything else stays, a chunk link keeps the chunk it links to. `PlaceInstance` makes the instance in the target chunk's layout (not among its resources yet), `PlaceElement` inserts the element at the end of its list in the chunk's document (`ListPath`, relative to the resource's `[data]` node, found by the resource's type). A **group** prefab (`PrefabKind.Group`, `CaptureGroup`/`PlaceGroup`, `PrefabItem`s with where each stands from the first) is several selected instances saved together and placed around the cursor the same way. Saving renders the selection on its own for its picture (`Rendering/PreviewRender`, on the render thread between two frames: every other object hidden, the editor's visuals off (`Renderer.DrawEditorPrimitives`), the camera at a three quarter view framing the selection's boxes, one frame rendered with `Renderer.RenderNow` and read back, everything put back before the next frame; `Util/PreviewImage` takes the frame's middle square), a PNG next to the prefab's file (`Prefab.PreviewPath`) the panel's tiles show. The save waits for it (`SavePrefabAsync`), a viewport that isn't rendering gives none. The Prefabs panel (`PrefabsViewModel`, a dock next to the Log, Window menu) lists them as tiles with the picture and the name (the rest in the tooltip), saves the scene's selection (the viewport tells what it can be saved as, `ViewportViewModel.Prefabs.cs`) and places one at the cursor from its context menu; dragging a row into the viewport (`PrefabsViewModel.DragFormat`, dropped in `ViewportView`) places it where the drop's ray hits the collision (`ViewportViewModel.PlacePrefabAt`). Placing is one undo step, an element's objects are rebuilt and the ones with a `Position` moved to the cursor.
- There is no code reading older project formats: the current version was never released, so renames and format changes don't keep readers for what projects stored before. Bump `Project.CURRENT_VERSION` when they break existing projects.

### Misc
- **Project tree** (`ProjectManager.BuildProjectTree`/`ExploreFolder`): folders before assets, each in name order (`ResourceTreeElementViewModel.BuildChildren`, `AddNewChild` inserts new rows the same way), the project's `prefabs` and `profiles` folders hidden. `ProjectTreeWatcher` watches the project folder (asset JSON files, directories and the disc's music and video files, not `build`) and, once changes stop for half a second, `SyncProjectTree` on the UI thread adds what appeared (assets loaded from their JSON, folders explored like at opening) and removes what's gone (assets taken out of the `AssetManager` too). Folders are never written as files (`Folder.Serialize` does nothing: a folder's JSON in its own directory made the tree a cycle). A new asset is listed in the folder of the directory its file goes in (`AssetFactory.GetContainingFolder`: a chunk gets a folder of its own, a layout's instance the `<Type>/Layout_<n>` folders under its chunk's, made on disk right away), a layout's instance is only written when its chunk gets saved and is `SerializableAsset.IsUnsaved` until then, and the sync keeps unsaved assets and only takes an asset out of the project when its own file is gone (one listed in another folder than its file's just leaves that folder, `HasFile`). Instances placed in a chunk used to be listed in the chunk's folder, the first sync after saving (or before, when other files changed) took them out of the project, and closing the chunk's tab crashed looking them up (`PrefabLibraryTests.PlacedInstancesStayInTheProjectThroughSavingAndClosing`); `LevelChunk.Dispose` skips a resource the project doesn't have with a warning. The `disc` folders (`FolderMark.Disc`) list `DiscFile` rows, never assets of the project: an MH/MB music archive as one node (`Music.mh/mb`) and each PSS video, double clicked or opened from the context menu with its twinstudio tool (`Tools/ExternalTools.Launch`: `tools/twinmusic`, `tools/twinpss` next to the executable, the Tools menu starts them, opens the folder and the releases page). Chunks are only offered and made in the `levels` folder at the root of a package, any package, and the folders under it (`Folder.GetPathInLevels`), where the build finds them (`Project.GetLevelsFolders`: the levels folders of every enabled package of the version the project's package depends on), and a chunk's path is its own in its version of the game (another package's chunk at it is refused, the build writes the first). Packages are only made in the project's own `assets` folder, which offers nothing else (`FolderElementViewModel.ListAssetsToCreate`, `AssetDataFactory.CreatePackageData`): a folder of their own (`AssetFactory.GetContainingFolder`), named as typed, depending on the PS2 package (the Xbox one when only it is enabled) and added to the project package's dependencies; a package's own `assets` folder is a folder like any other. A package's settings tab (right click the package) closes without reading its file back from the wrong path (`Package.LoadPath`).
- Log with `Log.WriteLine(text, Log.LogType.X)`. Every line is appended and flushed to a session log file straight away, together with unhandled exceptions. The files live in `%LOCALAPPDATA%\TT Lab\Logs` on Windows and `$XDG_STATE_HOME/tt-lab/logs` (default `~/.local/state`) on Linux, and the last 5 sessions are kept. `Debug`/`Trace` lines only go to the file.
- User settings live in the static `Preferences` class, stored in `settings.json` next to the executable. The Project menu's Open Recent lists the last 10 projects opened (`Preferences.RecentProjects`, `ProjectManager.WithRecentlyOpened`), saved as soon as they change. Opening one closes the open project's editors first, like opening one from the dialog.

## Code style

Match the surrounding file. The codebase spans several eras, so consistency within a file matters more than uniformity across files. For new code:

- **Comments**: avoid verbose comments. Only add comments that describe hacks, workarounds, or code whose intent isn't obvious (bit layouts, format quirks, ordering requirements). Don't narrate what the code does and don't add XML doc comments to new members, except in TwinTech public interfaces or files that already document every member.
- **Namespaces**: use file-scoped `namespace X;` in new files. Don't convert existing block-scoped files unless you're rewriting them.
- **Braces/layout**: Allman braces, 4-space indent, braces even for single-statement `if`s. Prefer early-return guard clauses. Put a blank line after a closing block before the next statement.
- **Naming**: PascalCase for types, methods, properties and public/protected members. `_camelCase` for private instance fields. PascalCase for `private static readonly` fields. `UPPER_SNAKE_CASE` for game IDs in `Constants`. Interfaces for game items are `ITwinX`, PS2 implementations are `PS2AnyX`/`PS2X`, and asset data classes are `XData`.
- **Types**: `.editorconfig` doesn't force C# keywords. For binary-format fields and game data (TwinTech items, asset data mirroring game structs) use explicit BCL names (`UInt32`, `Int32`, `UInt16`, `Single`, `Byte`) so widths are obvious. Elsewhere, new code uses keywords (`string`, `bool`, `int`).
- `var` for locals, target-typed `new()`, and collection expressions (`[]`) in TT Lab. Not collection expressions in TwinTech (C# 11).
- Use hex literals for IDs, masks and bit shifts (`_header >> 0xB & 0x1`), and `{id:X}` when formatting IDs.
- `nameof(...)` for property-change notifications and attribute references.
- `Debug.Assert` for internal invariants. Throw exceptions for bad input or game data.
- `using var` for streams, readers and writers.
